Chunked Async Map with Fail-Fast

Problem: Processing large arrays with full parallelism causes DB/API overload; sequential processing is too slow.

Break the array into chunks of configurable size. Within each chunk, all items run in parallel via Promise.allSettled. Chunks execute sequentially. An optional failFaster flag stops processing on the first rejection.

// avise-shared-utils/src/promiseUtil/index.ts
async function asyncMapInChunks<X, Y>(
  array: X[],
  callback: (x: X, idx: number, sub: X[]) => Promise<Y>,
  chunkSize: number = array.length,
  failFaster: boolean = false,
): Promise<Array<Y>> {
  const results = [];
  for (let start = 0; start < array.length; start += chunkSize) {
    const subArray = array.slice(start, start + chunkSize);
    const res = await Promise.allSettled(
      subArray.map((elem, idx, sub) => callback(elem, start + idx, sub))
    );
    for (const settled of res) {
      if (settled.status === 'rejected' && failFaster) throw settled.reason;
      // collect results...
    }
  }
  return results;
}

avise-api/src/ai/index.ts avise-api/src/data/taskAccounts.ts avise-shared-utils/promiseUtil
When to use
  • Processing files, uploads, or DB writes in batches
  • External API calls with rate limits
  • Parallel work that could overload a connection pool
When NOT to use
  • When order of side-effects matters within a chunk — use asyncMapSequential
  • Tiny arrays where overhead isn't worth it

Exponential Backoff with shouldRetry Predicate

Problem: External API calls fail transiently. A generic retry loop doesn't know when to retry vs. bail out immediately.

A typed backoff utility accepts an optional shouldRetryFn predicate that receives both error and response. This covers both thrown errors AND non-throwing failures (e.g. a 200 with an error payload in the body). Delay doubles on each attempt starting from a configurable initialDelayMs.

// avise-shared-utils/src/exponentialBackoff/index.ts
await exponentialBackoff({
  func: () => callExternalApi(payload),
  shouldRetryFn: ({ error, response }) => {
    if (error) return isTransientError(error);
    // Also retry on soft errors in 200 responses
    return response?.status === 'RETRY';
  },
  initialDelayMs: 200,
  maxAttempts: 4,
});
Used in
avise-shared-utils/exponentialBackoff avise-api external integrations
When to use
  • Any external HTTP call (QBO, NS, LLM providers)
  • When the failure mode includes soft errors in 200 responses
When NOT to use
  • Internal DB calls — use Prisma's built-in retry
  • Idempotency not guaranteed on the target

Facet-Aware Lazy Singleton Config

Problem: One binary runs as multiple roles (REST API, BullMQ worker, Argo Workflow runner). Each role needs different env vars validated — but sharing one giant config makes all roles require all vars.

A facet env var identifies the current role at startup. Config is composed from modular ConfigSpec objects per category (ai, auth, redis, etc). Validation errors are fatal in production for the "main" facet but only warnings locally. The singleton is cached after first call via createLazyConfig.

// avise-api/src/config/index.ts
const facet = Config.config.facet || 'main';

if (isLocal && facet === 'main') {
  logger.warn('[Config] Invalid local config — see issues below.');
  // Show warnings, don't crash
  return;
}

if (facet === 'main') {
  logger.error('[Config] Failing fast: prod config error for main facet.');
  process.exit(1);
}
// Other facets: log and continue
Used in
avise-api/src/config/ avise-shared-utils/src/config/ qbo-sync, ns-sync, operation-tracking
When to use
  • One repo, multiple deployment roles
  • Gradual config hardening (warn local, fail prod)
When NOT to use
  • Simple single-role services

makeFake* Typed Test Factory

Problem: Creating test objects by hand is verbose, breaks when types change, and produces inconsistent defaults across tests.

Factory functions named makeFake{Entity} return a fully-typed object with sensible defaults. Tests pass only the fields they care about via a partial override. Used on both frontend (renderWithProviders, setupMsw) and backend (mockDataUnit) uniformly across the monorepo.

// avise-api/src/mockDataUnit/taskUnitData.ts
function makeFakeTask(overrides: Partial<Task> = {}): Task {
  return {
    id: 'task-123',
    status: 'open',
    assigneeId: 'user-456',
    companyId: 'company-789',
    dueDate: new Date('2026-01-01'),
    ...overrides,
  };
}

// In a test:
const task = makeFakeTask({ status: 'closed' });
Used in
avise-api/src/mockDataUnit/ avise-web/src/mocks/ test-toolkit workspace
When to use
  • Any new entity added to the system
  • Integration tests that need DB-seeded data
When NOT to use
  • Don't use in production code paths

Pluggable Tool Registry for LLM Agents

Problem: AI tools need to be registered, swapped at runtime (stub → full), and their schemas extracted — without the orchestration loop knowing the details of each tool.

A ToolRegistry class wraps a Map<name, tool>. Tools implement a GenericTool interface with a getSchema() method. The registry supports replace-or-skip registration, bulk schema export, and can produce a new registry with stub tools replaced by their full implementations mid-loop.

// avise-api/src/ai/tools/registry.ts
const registry = new ToolRegistry(allTools);

// Mid-loop: swap stubs for full tools
if (registry.areAnyToolsStub(toolCalls)) {
  toolRegistry = registry
    .getNewRegistryWithStubToolsReplaced(toolCalls);
  continue; // re-enter loop with full tools
}

// Export all schemas for LLM
const schemas = registry.getAllSchemas();
Used in
avise-api/src/ai/index.ts avise-api/src/ai/tools/
When to use
  • Any project with a dynamic set of LLM tools
  • When tools need context-dependent availability
When NOT to use
  • Static, never-changing tool sets — plain array is simpler

useXForm — Custom Hook Wrapping react-hook-form

Problem: Complex forms leak validation logic, field defaults, and submit handlers into page components, making them hard to test and reuse.

Each form gets a use{PageName}Form hook that wraps useForm, encapsulates validation rules and defaults, and exposes only what the UI component needs. For forms with nested table fields, the hook is combined with FormProvider so deeply nested fields can access the form context via useFormContext.

// avise-web/src/pages/tasks/useTaskForm.ts
function useTaskForm(task?: Task) {
  const form = useForm<TaskFormValues>({
    defaultValues: {
      assigneeId: task?.assigneeId ?? '',
      dueDate: task?.dueDate ?? null,
    },
  });

  const handleSubmit = form.handleSubmit(async (values) => {
    await createTask(values);
  });

  return { form, handleSubmit };
}

// In JSX:
const { form, handleSubmit } = useTaskForm();
return <FormProvider {...form}>...</FormProvider>;

avise-web/src/pages/ DESIGN-PATTERNS.md
When to use
  • Any form with 3+ fields or complex validation
  • Forms whose fields live inside tables
When NOT to use
  • Single-field forms — inline useForm is fine

Selective State Stripping Before Persistence

Problem: Runtime objects include S3 keys, file buffers, and provider credentials that must never be written to the database.

A cleanXForStorage function explicitly lists which fields to keep and drops everything else via object construction (not deletion). This makes what's stored intentional and auditable, not an accident of omission.

// avise-api/src/ai/index.ts
function cleanContextForStorage(
  context: AI.RequestContext
): AI.RequestContext {
  const cleanedFiles = context.attachedFiles?.map((file) => ({
    fileName: file.fileName,
    contentType: file.contentType,
    sizeInBytes: file.sizeInBytes,
    aviseFileId: file.aviseFileId,
    // Excluded: buffer, s3Key, s3Location, fileContent
  }));
  return { ...context, attachedFiles: cleanedFiles };
}
Used in
avise-api/src/ai/index.ts
When to use
  • Any object that mixes runtime data with persistent data
  • Before any DB write of AI/file context
When NOT to use
  • When the full object is always safe to persist

Lightweight Event Sourcing for Long-Running Operations

Problem: Long-running async jobs (sync, ingest, export) have no observable state — if they fail mid-way, there's no record of how far they got.

Each operation is a typed entity with a list of OperationEvents appended over its lifetime. Events are stored in the DB (or S3 for large payloads). The operation can be queried for its current state by replaying events. Used in Argo Workflow jobs and async AI operations.

// avise-shared-utils/src/operationTracking/index.ts
// Create an operation
const op = await createOperationAndEvents({
  operation: { id: uuid(), type: 'ingest', companyId },
  events: [{ eventType: 'started', createdBy: userId }],
});

// Append progress events
await saveEventForOperation(op.id, {
  eventType: 'file_processed',
  eventData: { fileId, rowCount },
});

// Later: resolve
await updateOperation(op.id, {
  resolution: 'success',
  completedAt: new Date(),
});
Used in
avise-shared-utils/operationTracking avise-api/src/argoWorkflows/ operation-tracking workspace
When to use
  • Any job running longer than a single request
  • When you need an audit trail of what happened
When NOT to use
  • Short synchronous operations — overhead not worth it

Allspice DSL — Type-Safe SpiceDB Bindings

Problem: SpiceDB (Zanzibar-style authorization) has no TypeScript SDK that enforces schema correctness at compile time — permissions can be mis-spelled, resources miswired.

Avise built a custom DSL compiler (allspice workspace) that reads the SpiceDB schema and generates fully-typed TypeScript bindings. Callers get compile-time guarantees that resource types, relations, and permissions are valid. The generated types (ResourceRelations, ResourcePermissions) are imported by the authorization client. This approach is unique in the ecosystem.

// avise-api/src/authorization/authorizationClient.ts
import {
  ResourcePermissions,
  ResourceRelations,
} from '../generated/allspice/types';

// All calls are type-checked against the schema:
await authzedClient.writeRelationships<
  ResourceRelations,
  ResourcePermissions,
  'task',        // ← compile error if not a real resource
  'assignee'     // ← compile error if not a real relation
>(relationships);
Used in
allspice/ workspace avise-api/src/authorization/ avise-api/src/generated/allspice/
When to use
  • Any new project using SpiceDB for authorization
  • Worth porting to any project where permission bugs are high-risk
When NOT to use
  • Simple role-based access (RBAC) — overkill

Stub Tool Pattern for LLM Token Budget Control

Problem: Giving an LLM 20+ full tool schemas in every request wastes tokens and degrades response quality — but the LLM needs to know what tools exist.

Stub tools have a tiny schema with only a name and minimal description. When the LLM calls a stub, the orchestration loop detects it, upgrades the registry to replace stubs with full implementations, and re-enters the loop with the same messages — the LLM then calls the real tool with full parameter knowledge. Token cost is paid only for tools actually used.

// avise-api/src/ai/index.ts (simplified)
// MAX_ITERATIONS accounts for extra stub-upgrade loops
const MAX_ITERATIONS = MAX_TOOL_CALLS + stubToolCount + 2;

// In the AI loop:
if (toolRegistry.areAnyToolsStub(toolCalls)) {
  toolRegistry =
    toolRegistry.getNewRegistryWithStubToolsReplaced(toolCalls);
  // Do NOT save messages — re-enter loop transparently
  continue;
}
Used in
avise-api/src/ai/index.ts avise-api/src/ai/tools/registry.ts
When to use
  • 10+ tools available to an LLM agent
  • When tool selection is highly context-dependent
When NOT to use
  • Fewer than 8 tools — full schemas are fine
  • When the LLM needs to see all options simultaneously

WebSocket-Based Async Event-Driven AI Chat

Problem: HTTP request/response for AI chat causes timeouts on long tool chains and gives no feedback to the user while the LLM thinks.

AI chat was refactored (SC-8148) from synchronous HTTP to a WebSocket-based event-driven model. The client opens a persistent connection, the server pushes typed events (thinking, tool_call, artifact, done) as they happen. This eliminates timeout issues, enables streaming feedback, and allows the frontend to react to intermediate states without polling.

// avise-shared-utils/src/websocket/ + avise-api/src/ai/
// Server pushes typed events as they occur:
ws.send({ type: 'tool_call', toolName: 'findJournalEntries' });
ws.send({ type: 'artifact', artifact: tableData });
ws.send({ type: 'message', content: assistantText });
ws.send({ type: 'done' });

// Client handles each event type independently,
// updating UI progressively without waiting for completion.
Used in
avise-shared-utils/src/websocket/ avise-api/src/ai/ avise-web AI chat panel
When to use
  • Any AI flow with tool calls that take 5+ seconds
  • When progressive feedback matters to the user
When NOT to use
  • Simple, fast AI calls — SSE or HTTP streaming is simpler

V2 Journal Entry API Has Large Sections Commented Out

The V2 JE endpoints have 8+ blocks of commented-out code in journalEntries.ts marked "Commenting this out until we get to supporting it." This means V1 and V2 coexist with overlapping responsibilities, increasing the risk of behavior divergence and making the codebase harder to reason about.

Suggested fix

Audit which commented-out V2 functions are still needed. Implement the missing pieces, then deprecate and remove V1 endpoints. Set a target date to complete V1 deprecation — the longer it runs in parallel, the more bugs will appear only on one version.

Reliability
High Effort: M

BullMQ Sync Jobs Not Yet Migrated to Argo Workflows

Both nsSyncCompany.ts and qboSyncCompany.ts have TODOs to migrate to Argo Workflow operations. Until then, sync failures don't benefit from Argo's retry/observability infrastructure. A failed BullMQ job silently stops while Argo would retry with full event tracking.

Suggested fix

Create Argo Workflow templates for NS Sync and QBO Sync following the existing argoWorkflowOperation pattern in avise-shared-utils. Wire up operation tracking events. Remove the BullMQ job implementations once Argo is confirmed stable.

Reliability

Missing Unique Constraint on Accrual Period-Number

A TODO in accrualReconciliationSummary.ts notes that there's no DB constraint enforcing only ONE accrual per period-accrual number. Without it, a race condition or bug can produce duplicate accruals that silently corrupt financial statements.

Suggested fix

Add a unique constraint on the (companyId, periodId, accrualNumber) columns in the accrual table via a Prisma migration. Run a data validation query first to confirm no existing violations before applying.

Tech Debt
Medium Effort: M

Business Logic Leaking Into Controllers

A TODO in journalEntryController.ts flags business logic (which JE statuses to use) sitting directly in the controller layer. This makes the logic harder to test in isolation and breaks when status semantics change.

Suggested fix

Extract the status selection logic into a service function with its own unit test. The controller should call the service and pass the result through — it shouldn't know the business rules for which status applies when.

Reliability
Medium Effort: M

Batch Updates Are All-or-Nothing — No Partial Success

The updateEntries service wraps all updates in a single DB transaction. A TODO notes this means callers can't distinguish "some succeeded" from "none succeeded". For large batches, one bad row rolls back everything.

Suggested fix

Decide deliberately: either keep all-or-nothing and document it clearly in the API contract, or split into per-item transactions that return { succeeded: [], failed: [] }. The current behaviour is a silent surprise — at minimum, document it.

Reliability
Medium Effort: S

Hardcoded Limit of 1000 Recurring Tasks

A TODO in recurringTaskController.ts acknowledges a hardcoded max of 1000 recurring tasks per update. As firms grow, hitting this silently truncates updates with no error surfaced to the client.

Suggested fix

Replace the hardcoded limit with a config value. Add a response field that indicates when the limit was hit (e.g. truncated: true, totalMatched: N). Long-term, implement cursor-based pagination for bulk recurring task updates.

Unnecessary Intermediate Types in JE Type System

Multiple TODO comments in avise-api/src/types/ and avise-api/src/services/types/ flag overly complex intermediate types (ShowableTask, Postable/Draftable casts) that add cognitive overhead without adding safety.

Suggested fix

Review each flagged type and determine if it adds value or is an artifact of past refactors. Consolidate where possible. At minimum, replace the cast patterns with proper type narrowing so the compiler enforces correctness instead of trusting the cast.

No Retry or Dead-Letter Queue for Failed Sync Jobs

Until NS Sync and QBO Sync move to Argo, failed BullMQ jobs have no standardized dead-letter queue or alerting. A sync that fails silently means customer data is stale with no notification to the team.

Suggested fix

Configure BullMQ's built-in removeOnFail: false and set up a dead-letter queue processor that fires a DataDog alert or Knock notification when a job lands there. This is a short-term fix until Argo migration is complete.
