Modul 1 din 7

Anatomia unui repo

Ce se sparge fara conceptul asta
Un coleg iti zice in standup: "am facut commit". Tu dai din cap. Apoi zice "dar nu e inca push-uit pe origin/main". Tu dai din cap din nou. Doua saptamani mai tarziu cere extensie de deadline pentru ca "munca lui locala s-a pierdut cand i-a murit laptopul". Tu nu intelegi ce inseamna asta - nu fusese deja livrat? Aici se sparge: codul nu traieste intr-un singur loc. Traieste in mai multe locuri simultan, si ce conteaza e in care loc se afla in fiecare moment.

Git vs GitHub - distinctia fundamentala

Git e instrumentul - un program care ruleaza pe calculatorul fiecarui dev si tine evidenta schimbarilor in fisiere. A fost creat de Linus Torvalds in 2005. Git nu are nevoie de internet ca sa functioneze.

GitHub e un serviciu online care gazduieste repo-uri Git si adauga lucruri peste: pull requests, code review, issue tracking, GitHub Actions (automatizari), Advanced Security. Daca Git e Word-ul, GitHub e Google Docs - acelasi document, dar acum partajat, comentabil, cu istoric vizibil pentru toata lumea.

De ce conteaza pentru tine: cand un dev zice "fac commit", vorbeste despre Git (local). Cand zice "fac PR", vorbeste despre GitHub (server). Doua actiuni diferite, in doua locuri diferite.

Cele patru zone unde traieste codul

Codul calatoreste prin patru zone. Fiecare zona are alt rol si alta vizibilitate.

1. Working Directory

Folderul de pe calculatorul dev-ului unde editeaza efectiv. Daca dev-ul a modificat 5 fisiere astazi, modificarile traiesc aici. Nimeni altcineva nu le vede inca. Daca laptopul moare acum, munca dispare.

2. Staging Area (sau "index")

Zona de pregatire. Dev-ul a editat 5 fisiere dar vrea sa "pachetizeze" doar 3 din ele intr-o livrare. Comanda git add muta cele 3 fisiere in staging. E ca atunci cand pui hainele in valiza inainte de a o inchide - nu inseamna ca ai plecat, doar ai ales ce iei cu tine.

3. Local Repository

Folderul ascuns .git din proiect. Aici se inscriu commit-urile - "fotografii" ale codului la un moment dat, cu mesaj. Comanda git commit face fotografia si o adauga la istoricul local. Munca e acum sigura local (chiar daca dev-ul sterge fisierele, le poate recupera), dar tot nu o vede nimeni altcineva.

4. Remote (GitHub)

Serverul. Aici ajunge codul cand dev-ul face git push. Acum exista pe GitHub, ceilalti colegi il pot vedea, descarca cu git pull, PR-uri pot fi facute pe el. Asta e "adevarul oficial" - cand un PO intreaba "e in repo?", de fapt intreaba "e pe remote?".

Ancora ta
🧳 VALIZA LA AEROPORT
Camera ta (working dir) = unde stau hainele. Valiza (staging) = ce ai ales sa iei. Sa o inchizi (commit) = e gata pregatita. Predata la check-in (push) = a plecat din mainile tale, e in sistemul aeroportului.
Contrast
Un coleg care zice "am terminat task-ul" inseamna lucruri diferite: poate "am editat in folder" (n-a salvat nimic), "am facut commit" (e doar la el local), sau "am facut push" (e pe GitHub si poate fi reviewuit). Doar a treia varianta e cu adevarat "terminat" din perspectiva ta de PO.

Comenzi de baza (daca vrei sa exersezi)

# Vad ce am modificat dar nu am stage-uit
git status

# Adaug fisiere in staging (un fisier sau toate)
git add fisier.txt
git add .

# Fac commit local cu mesaj
git commit -m "fix: corectie calcul TVA"

# Trimit commit-urile pe GitHub
git push origin main

# Aduc ce e nou de pe GitHub la mine local
git pull origin main
Tehnica de memorare

Metoda "Calatoria" - imagineaza-ti drumul

De fiecare data cand auzi "commit", refa mental drumul valizei: camera → valiza → casa → aeroport. Nu memora cele 4 zone ca lista. Vezi-le ca etape ale unei calatorii. Cand dev-ul zice "am commit-uit dar nu am push-uit", instant: valiza e gata in casa, dar nu a ajuns la aeroport.

Asta e memorie spatiala - creierul tine minte locuri mult mai bine decat liste abstracte. Tu esti vizuala, pattern-first; o secventa spatiala iti ramane.

Quiz - Interpretare

Un dev iti zice in stand-up: "am terminat task-ul, l-am commit-uit local dar nu am avut timp sa-l urc". Ce inseamna asta pentru tine ca PO?

Corect: "commit local" = pasul 3 din 4. Munca e sigura local (nu se pierde daca repornesc), dar e invizibila pentru oricine altcineva. Daca laptopul lui moare ACUM, munca se pierde. "Nu am avut timp sa urc" = nu am facut push. Ca PO, asta inseamna: nu pot testa, nu pot reviewui, nu pot conta pe ea pana nu apare pe GitHub.
Modul 2 din 7

Ciclul de viata al codului

Ce se sparge fara conceptul asta
Vineri seara dev-ul iti zice "am facut push, e gata pentru release". Luni dimineata, la demo, clientul observa ca o functionalitate nu merge. Tu te uiti pe GitHub - codul e acolo. Cum se poate? Dev-ul iti raspunde: "PR-ul meu nu a fost inca merged in main, sta in review". A facut push, dar pe un branch propriu. Tu credeai ca push = ajuns in produs. Sunt cinci pasi intre cei doi.

Ciclul complet: de la idee la productie

Sase pasi de la "am inceput" pana la "e in main". Push-ul (pasul 4) NU inseamna ca a ajuns in main. Asta vine la pasul 6.

Pasii explicati pe rand

1. Pull - sincronizeaza-te inainte sa incepi

Dev-ul aduce ultima versiune a codului din main pe laptopul lui. De ce primul pas? Pentru ca daca alti colegi au facut modificari intre timp, vrea sa porneasca de la cea mai noua versiune, nu de la una veche.

Daca sare peste asta, lucreaza pe cod vechi si la pasul 5 va avea conflict de merge - doi oameni au modificat acelasi fisier in feluri diferite, Git nu stie pe cine sa creada, cineva trebuie sa rezolve manual.

2. Branch - creeaza-ti ramura proprie

Dev-ul nu lucreaza direct in main (ramura principala, productia). Isi creeaza un branch - o ramura paralela unde poate experimenta fara sa strice nimic in main. Numele branch-ului include adesea ID-ul Jira: feature/IMK-123-add-stripe.

Imagineaza-ti un copac: trunchiul (main) creste mereu. Cand cineva vrea sa lucreze la o functie, creeaza o crengusa care porneste din trunchi. Cand termina, crengusa se "lipeste" inapoi in trunchi (merge).

3. Modify + Stage + Commit (de mai multe ori)

Dev-ul lucreaza pe branch-ul lui. Editeaza, face commit. Editeaza din nou, face alt commit. Un task complex poate avea 5-15 commit-uri inainte sa fie gata. Fiecare commit e o "fotografie" cu mesaj. Tot ce face pana acum e local pe laptopul lui.

4. Push - urca branch-ul pe GitHub

Cand vrea ca altcineva sa vada munca (sau cand isi face backup), face git push. Branch-ul lui apare acum pe GitHub. Important: branch-ul lui, nu main-ul. Codul nu e inca in productie, nu a fost reviewuit, nu a fost aprobat.

5. Pull Request - cere oficial intrare in main

Acesta e momentul critic. Pe GitHub, dev-ul deschide un Pull Request (PR) - o pagina dedicata unde:

  • Se vad toate modificarile fata de main, fisier cu fisier
  • Colegii pot lasa comentarii la linii specifice
  • Se ruleaza automat teste (CI - Continuous Integration)
  • Cineva trebuie sa apese "Approve" inainte sa poata fi fuzionat

Numele "Pull Request" e istoric si confuz - de fapt e o cerere de merge, nu de pull. Tradus pe romana: "Cer ca munca mea sa fie trasa in main".

6. Review + Merge - aprobat si fuzionat

Alt dev (sau mai multi) citeste PR-ul, lasa comentarii, cere modificari. Cand totul arata bine si testele automate trec, cineva apasa butonul Merge. Acum si doar acum, codul e in main. De aici, in functie de procesul echipei, poate ajunge in productie automat sau cu un pas suplimentar de deploy.

Ancora ta
🌳 ALTOI LA POMI
Trunchiul (main) creste mereu. Tai o crengusa (branch), o cultivi separat (commit-uri), o aduci inapoi la trunchi (push) si o altoiesti (merge). Pana nu e altoita, crengusa traieste separat. PR-ul = momentul cand pomicultorul verifica daca altoiul prinde.
Contrast
"Push" si "merge" suna similar dar sunt opuse ca semnificatie. Push = "am pus codul meu pe server, pe branch-ul meu". Merge = "codul meu a fost integrat in main". Intre ele sunt minute sau zile, depinde de cat dureaza review-ul.

Conflictele de merge - de ce apar si ce inseamna pentru tine

Doi devi pornesc de la aceeasi versiune a main-ului. Amandoi modifica linia 42 din acelasi fisier, fiecare in branch-ul lui. Primul face merge - linia 42 a lui devine oficiala. Al doilea cere merge - Git zice "stai, linia 42 e diferita acum decat cand ai pornit. Pe care varianta sa o pastrez?"

Cineva trebuie sa rezolve manual: deschide fisierul, alege ce versiune ramane (sau combina ambele) si face un commit de rezolvare. Pentru tine ca PO asta inseamna: un task care parea gata mai are 1-2 ore de munca. Nu e un bug, e o consecinta a lucrului in paralel.

Tehnica de memorare

Metoda "6 Degete" - acronim ritmic

Numara pe degete: Pull, Branch, Commit, Push, PR, Merge. Spune-le cu voce tare in ritm. PBCPPM. Cand cineva spune "am push-uit", degetul tau merge automat la pozitia 4 din 6 - mai sunt doi pasi pana la productie.

De ce functioneaza: memorie procedurala (miscare fizica) + memorie auditiva (ritm) se intaresc reciproc. Iti vor ramane chiar daca nu repeti zile in sir.

Quiz - Interpretare

In Avise, Harris zice "PR-ul meu e deschis de 3 zile, doi colegi au comentat dar nu au aprobat inca". La standup, Graham (CEO) intreaba: "deci feature-ul X e in productie?". Ce raspunzi?

Corect: PR deschis = pasul 5 din 6. Codul e pe GitHub (push-ul s-a facut), dar n-a fost merged. Comentariile fara aprobare = review activ, posibile modificari cerute. Pana la merge: codul nu e in main, nu e in deploy, nu e in productie. Raspunsul cinstit pentru Graham: "e in review activ, estimam X zile pana la merge".
Modul 3 din 7

Branch-uri si strategii

Ce se sparge fara conceptul asta
Echipa ta are 4 devi care lucreaza in paralel: unul la o functie noua, unul la un bug urgent in productie, unul la o experimentare care s-ar putea sa nu intre niciodata, unul la refactorizare. Daca toti scriu in acelasi fisier in acelasi timp pe acelasi main, e haos - codul unora il sterge pe al altora, productia se sparge la fiecare commit. Branch-urile sunt cum supravietuiesc 4 oameni la acelasi proiect fara sa se calce in picioare.

Anatomia unui branch

Un branch e o ramura paralela a codului. Pleaca de la un punct din main (sau alt branch) si traieste separat pana cand e fie fuzionata inapoi (merge), fie abandonata (deleted). Toate commit-urile facute pe branch raman pe branch - nu polueaza main-ul pana la merge.

Doua branch-uri: unul lung (feature) care a inceput devreme si s-a fuzionat tarziu, unul scurt (hotfix) deschis si inchis rapid. Productia urmeaza main.

Conventii de denumire (citeste-le ca PO)

Echipele bune folosesc prefixe ca sa se vada din nume ce tip de munca e:

PrefixTipCand se foloseste
feature/Functionalitate nouaStory nou din backlog
fix/ sau bugfix/Bug normalBug raportat, nu urgent
hotfix/Bug urgent in productieProductia e sparta, trebuie remediere imediata
chore/Mentenanta tehnicaRefactorizare, update dependinte, nu schimba comportament
docs/DocumentatieDoar modificari de README, comentarii, fara cod functional
release/Pregatire releaseStabilizare inainte de a iesi o versiune noua

Un nume bun: feature/IMK-247-stripe-billing-integration. Vezi imediat: e o functionalitate noua, ticketul Jira e IMK-247, si despre ce e vorba.

Doua strategii mari: GitFlow vs Trunk-Based

GitFlow - structurat, multi-strat

Branch-uri permanente: main (productie), develop (integrare). Branch-uri temporare: feature/*, release/*, hotfix/*. Codul migreaza: feature → develop → release → main. Fiecare release e o "lansare oficiala".

Cand functioneaza: produse cu release-uri planificate (lunar, trimestrial), versiuni multiple in suport simultan (ex: clienti pe v2.x si v3.x). Mai degraba enterprise sau B2B clasic.

Trunk-Based - simplu, rapid

Un singur branch lung: main. Toate feature-urile sunt branch-uri scurte (1-3 zile) care se intorc rapid in main. Deploy-urile se intampla zilnic sau de mai multe ori pe zi. Functionalitatile incomplete sunt ascunse cu feature flags (steaguri care le tin invizibile pana sunt gata).

Cand functioneaza: SaaS modern, echipe care livreaza des, produse cu o singura versiune in productie. Avise e probabil aici, IMK Portal Phase 1 probabil tot aici.

Ancora ta
🚂 GARA CU MAI MULTE LINII
GitFlow = gara mare cu peroane separate (develop, release, main) prin care trenurile (feature-uri) trec ordonat. Trunk-based = un singur peron cu trenuri scurte care vin si pleaca tot timpul. Ambele functioneaza, dar pentru trafic diferit.
Contrast
Un PO care intreaba "cand iese release-ul?" intr-o echipa trunk-based e ca cineva care intreaba la metroul bucurestean "cand vine urmatorul tren". Vine in cateva minute, mereu. In echipa GitFlow, release-ul e un eveniment cu data fixa. Trebuie sa stii in ce model lucreaza echipa ta inainte sa pui intrebari de planning.
Tehnica de memorare

Metoda "Doua peisaje" - vizualizare contrastiva

Imagineaza-ti doua imagini complete, una langa alta:

Stanga (GitFlow): un copac mare cu 4 ramuri principale lungi, multe crengute care urca si coboara intre ele. Ordonat, multi-etaj.

Dreapta (Trunk-Based): un trunchi gros cu zeci de crengute mici care apar si dispar, ca un copac batut de vant. Toate scurte, toate aproape de trunchi.

Cand auzi numele unei strategii, vezi instant peisajul. Memorie vizuala contrastiva - imaginile opuse se intaresc reciproc pentru ca creierul le proceseaza ca pereche.

Quiz - Interpretare

In sprint planning, Vlad iti zice: "lucram trunk-based, deploy zilnic. Stripe integration va fi in spatele unui feature flag pana la GA". Ce inseamna asta concret pentru release-ul de Phase 2?

Corect: Feature flag = codul exista, e deja in productie, dar e ascuns dupa un "intrerupator" care zice "afiseaza/nu afiseaza". Echipa poate merge inainte cu deploy-urile zilnice pentru alte feature-uri, fara sa astepte ca Stripe sa fie gata. Cand totul e testat, cineva apasa intrerupatorul - feature-ul apare instant fara deploy nou. Asta e marele avantaj trunk-based: nu astepti "release-ul mare".
Modul 4 din 7

Versionare: SemVer, hotfix-uri, release-uri

Ce se sparge fara conceptul asta
Un client integreaza cu API-ul tau folosind versiunea 2.3.1. Doua saptamani mai tarziu, echipa ta lanseaza 2.3.2 - "doar un bugfix". Clientul actualizeaza si... integrarea lui crapa. De ce? Pentru ca echipa a numit gresit versiunea: 2.3.2 nu era doar un bugfix, schimbase un nume de camp. Asta era o schimbare de major version, nu de patch. Numerele de versiune sunt un contract cu cei care folosesc codul tau. Daca numerotezi gresit, le inseli asteptarile.

Semantic Versioning (SemVer) - formula MAJOR.MINOR.PATCH

strica ce era inainte Ex: redenumire camp API, eliminare functionalitate MINOR (3) Functionalitati noi care nu strica ce era inainte Ex: endpoint nou, camp optional adaugat PATCH (7) Bugfix-uri, fara schimbari de comportament Ex: corectie calcul, fix bug de afisare
Fiecare cifra are inteles. Cand o cifra creste, cele din dreapta resetate la zero (3.4.9 → 4.0.0 la major bump).

Cum se incrementeaza in practica

De laLaCe s-a intamplat
1.2.31.2.4Patch: bugfix mic, fara schimbari de API
1.2.41.3.0Minor: feature nou (PATCH se reseteaza la 0)
1.3.02.0.0Major: breaking change (MINOR si PATCH se reseteaza)
2.0.02.0.1Patch: probabil un fix la noua versiune majora
Regula 0.x.y: Tot ce e sub 1.0.0 e considerat "in dezvoltare" - regulile nu se aplica strict. Cand un produs ajunge la 1.0.0 oficial, devine "stabil" si contractul SemVer incepe sa conteze.

Tags si Releases pe GitHub

Cum se materializeaza versionarea in GitHub:

Tag - o eticheta lipita pe un commit specific din istoric. Comanda: git tag v2.3.7. E ca un steag infipt: "aici a fost versiunea 2.3.7". Util pentru ca poti oricand sa te intorci exact la acel cod.

Release - pe GitHub, un tag poate fi promovat la "release", care e o pagina dedicata cu changelog, fisiere atasate (binare, instalere), si link permanent. Devine documentul oficial al lansarii.

Hotfix vs Feature Release - flow-ul diferit

Feature release (planificat)

Tu si echipa planificati: pana pe 15 ale lunii iese v2.4.0 cu integrarea Stripe. Flow: feature branch → develop/main → testing → release branch → tag v2.4.0 → deploy. Ai timp sa testezi, sa pregatesti documentatie, sa anunti clientii.

Hotfix (urgenta in productie)

Sambata dimineata, productia e sparta - un bug critic blocheaza login-ul. Nu poti astepta sa termini feature-urile in lucru. Flow: branch hotfix/v2.3.8-login-fix direct din main, fix scurt, test rapid, merge, tag v2.3.8, deploy imediat. Doar PATCH bump, nimic altceva nu intra.

De ce un branch separat: in main e posibil sa fie deja munca neterminata pentru v2.4.0. Daca faci deploy din main, urci si lucruri pe jumatate. Hotfix-ul porneste de la versiunea actuala de productie (tag v2.3.7) si se intoarce numai cu fix-ul, nimic altceva.

Ancora ta
🚗 NUMARUL DE INMATRICULARE AL MASINII
2.3.7 = trei cifre care identifica unic versiunea. Major = generatia (cum sunt B vs CT pe placutele Bucuresti). Minor = anul / seria. Patch = numarul individual. Schimbi placuta doar cand schimbi ceva esential.
Contrast
O echipa care nu respecta SemVer face "minor bumps" cand de fapt sunt breaking changes. Asta e periculos pentru clientii care integreaza - actualizeaza fara grija si lucrurile lor se sparg. Daca esti PO pe un produs cu API public sau cu integratori (ca IMK cu ThinkOut, CRIF, Stripe), trebuie sa ai grija cum numerotezi.
Tehnica de memorare

Metoda "Cele trei intrebari" - decizie ghidata

Cand vezi o versiune noua, intreaba in ordine:

  1. S-a stricat ceva ce mergea inainte? Daca da → MAJOR bump.
  2. Daca nu, e o functionalitate noua? Daca da → MINOR bump.
  3. Daca nu, e doar un fix? → PATCH bump.

Arborele de decizie are doar 3 noduri. Memorie procedurala - dupa ce-l aplici de 5 ori, devine automat.

Quiz - Interpretare

Avise e la versiunea 1.4.2. Echipa adauga un endpoint nou opt-in pentru integrare cu QuickBooks (clientii actuali nu sunt afectati). Ce versiune urmeaza?

Corect: Functionalitate noua + nu strica nimic existent = MINOR bump. Endpoint-ul nou e o adaugare; clientii care nu il folosesc nu sunt afectati. PATCH-ul (ultima cifra) se reseteaza la 0. Daca ar fi fost o schimbare la endpoint-uri vechi (ex: redenumire camp obligatoriu), ar fi fost 2.0.0 - major bump pentru breaking change.
Modul 5 din 7

Jira ↔ GitHub: legatura completa

Ce se sparge fara conceptul asta
Esti la mid-sprint review. Verifici in Jira: 7 task-uri "In Progress". Pleci linistita ca echipa lucreaza. La sprint end, descoperi ca 5 din ele sunt deja merged in main si deployed - n-a actualizat nimeni Jira. Ai luat decizii pe date vechi de o saptamana. Daca cele doua sisteme nu vorbesc intre ele, ai mereu doar jumatate de adevar. Integrarea Jira-GitHub face ca status-ul ticket-ului sa se sincronizeze automat cu starea codului.

Cele trei niveluri de integrare

Nivel 1: Doar legatura vizuala (default cand conectezi)

Dupa ce admin-ul conecteaza Jira cu GitHub, daca dev-ul mentioneaza ID-ul Jira (ex: IMK-247) intr-un commit message, branch name, PR title sau PR description, Jira detecteaza automat si afiseaza in ticket o sectiune "Development" cu link-uri spre acel commit / branch / PR. Nu se schimba status-ul automat, dar tu vezi in Jira ce s-a intamplat in cod.

Nivel 2: Smart Commits (transformare semi-automata)

Cu o sintaxa speciala in mesajul de commit, dev-ul poate sa:

  • Adauge un comentariu in ticket: IMK-247 #comment am implementat validarea KVK
  • Logheze timp de lucru: IMK-247 #time 2h 30m fix bug Stripe webhook
  • Tranzitioneze status-ul: IMK-247 #close sau IMK-247 #in-progress

Toate cele trei se pot combina intr-un singur commit. Cerinta: email-ul dev-ului din Git trebuie sa fie acelasi cu email-ul lui din Jira.

Nivel 3: Tranzitii automate prin reguli (cel mai puternic)

Configurezi in Jira: "cand un PR linkat la ticket e opened → tranzitioneaza ticket-ul la 'In Review'". "Cand PR-ul e merged → tranzitioneaza la 'Done'". Dev-ul nu trebuie sa atinga Jira deloc - actiunile lui in GitHub conduc automat workflow-ul Jira.

Asta inseamna ca atunci cand tu te uiti in Jira la sprint board, status-urile reflecta realitatea codului, nu cand a avut un coleg timp sa actualizeze manual.

Conventia "ID Jira in branch name"

Cea mai puternica conventie pe care o poti cere echipei: ID-ul Jira sa fie in numele branch-ului.

# Bun:
feature/IMK-247-stripe-billing-integration
bugfix/AVI-89-tva-calculation
hotfix/IMK-301-login-broken

# Slab:
my-stripe-stuff
fix-bug
ionuts-branch

De ce conteaza: GitHub si Jira folosesc ID-ul ca sa se gaseasca reciproc. Daca branch-ul are ID-ul, link-ul Jira ↔ GitHub se face automat fara ca dev-ul sa scrie nimic special. Daca lipseste, trebuie sa-l puna manual in commit messages, ceea ce de obicei uita.

Cum citesti Development panel in Jira

In fiecare ticket Jira conectat la GitHub, in dreapta apare sectiunea Development:

Ce veziCe inseamna
"1 branch"Cineva a inceput sa lucreze. Clik pe el iti arata branch-ul
"3 commits"3 commit-uri au mentionat acest ID; munca activa
"1 pull request - OPEN"PR deschis, in review. Codul e push-uit dar nu merged
"1 pull request - MERGED"Munca a fost integrata in main. Aceasta e dovada ca e "done" tehnic.
"1 pull request - DECLINED"PR-ul a fost respins. Decizia trebuie investigata
Ce sa intrebi cand un ticket pare "blocat": deschide ticket-ul, uita-te in Development panel. Daca PR-ul e OPEN de mult timp - blocajul e in review, nu in dev. Daca nu exista PR dar branch-ul exista de zile - dev-ul lucreaza inca local. Daca nu exista nimic - poate nu a inceput inca. Trei realitati diferite, trei conversatii diferite.
Ancora ta
🚇 STATIA DE METROU CU DOUA INTRARI
Jira si GitHub sunt doua intrari in aceeasi statie - tu intri din partea PO (Jira), dev-ul intra din partea developer (GitHub), va intalniti la peron (ticket-ul cu Development panel). ID-ul ticketului e cheia care deschide ambele turnichete.
Contrast
O echipa fara integrare are doua adevaruri paralele: Jira zice una, codul zice alta. PO-ul intreaba in stand-up "in ce status e X?", dev-ul raspunde "depinde unde te uiti". O echipa cu integrare are un singur adevar - status-ul Jira si starea codului spun aceeasi poveste, fara efort manual.
Tehnica de memorare

Metoda "Verificarea in trei pasi" - protocol de citire

De cate ori vezi un ticket "In Progress" care te ingrijoreaza, fa instinctiv aceasta secventa de 3 pasi:

  1. Branch exista? → daca nu, dev-ul nici n-a inceput
  2. PR exista? → daca nu, e doar la el local sau pe branch fara review
  3. PR e merged? → daca da, e tehnic done (poate doar deploy ramane)

Asta e memorie procedurala in trei pasi - dupa ce o aplici de 3-4 ori, devine reflex. Ai un protocol clar in loc sa pui intrebari vagi.

Quiz - Interpretare

In Jira, ticket-ul IMK-247 are status "In Progress" de 5 zile. In Development panel vezi: "1 branch, 8 commits, 1 pull request - OPEN (4 days)". Ce ipoteza cea mai probabila?

Corect: 8 commits = munca substantiala. PR OPEN de 4 zile = PR-ul exista pe GitHub dar nu a fost merged. Daca status-ul Jira ar fi automat, ar fi probabil "In Review", nu "In Progress" - posibil tranzitiile automate nu sunt configurate. Conversatia urmatoare nu e cu dev-ul ("de ce nu termini") ci cu cel care trebuie sa faca code review.
Modul 6 din 7

Fluenta PO-ului tehnic

Ce se sparge fara conceptul asta
Esti in standup. Dev-ul zice "PR-ul meu e blocat de un CI failure pe lint dupa rebase". Tu auzi cinci cuvinte din care intelegi doua. Ai doua optiuni: sa zici "ok" si sa pleci fara sa intelegi, sau sa pui intrebari de baza si sa pari ca nu stii nimic. Niciuna nu te ajuta. Fluenta tehnica nu inseamna sa scrii cod - inseamna sa intelegi suficient ca sa pui intrebari bune si sa iei decizii pe date reale.

Cum citesti un PR fara sa fii dev

Cand deschizi un PR pe GitHub, vezi cateva lucruri importante:

Titlul si descrierea

Titlul ar trebui sa fie clar si sa contina ID-ul Jira: IMK-247: Stripe billing integration for monthly subscriptions. Descrierea ar trebui sa explice de ce, nu doar ce - tu, ca PO, poti citi asta si intelege intentia, chiar daca nu intelegi cod.

Daca titlul e fix stuff sau descrierea e goala, e un red flag de calitate.

Status-ul CI (Continuous Integration)

In partea de jos vezi indicatori verzi sau rosii cu nume ca "build", "test", "lint". Astea sunt verificari automate care ruleaza la fiecare push pe PR:

  • build - codul se compileaza, nu are erori de sintaxa
  • test - testele automate trec (functionalitatea nu e stricata)
  • lint - codul respecta standardele de stil ale echipei
  • security scan - nu sunt vulnerabilitati cunoscute (GHAS face asta)

Daca vezi tot verde - codul e "tehnic safe" sa fie merged. Daca vezi rosu - ceva trebuie reparat. Asta nu inseamna ca e bug functional, dar inseamna ca echipa a stabilit ca nu merge inainte cu probleme nerezolvate.

Numarul de "files changed" si "+X / -Y" linii

"1 file changed, +10 -2" = PR mic, probabil un fix. "47 files changed, +2,341 -890" = PR mare, probabil un feature complex sau refactorizare.

PR-urile foarte mari sunt greu de reviewuit corect si ascund bug-uri. O echipa sanatoasa pastreaza PR-urile sub ~400 linii cand se poate. Ca PO, daca vezi PR-uri de 2000+ linii, poti pune intrebarea: "ar fi putut fi spart in PR-uri mai mici?"

Conversatia (Comments)

Aici se intampla code review-ul. Vezi cine a comentat ce, daca s-au cerut modificari, daca au fost rezolvate. Statusul aprobarilor e in dreapta sus: "Approved by 2", "Changes requested by 1", "Awaiting review".

Intrebari bune in standup (calibrate pe Git flow)

In loc de "esti gata cu X?"

Intreaba: "in ce stadiu e PR-ul - inca lucrezi local, e push-uit, e in review, sau urmeaza merge-ul?" Raspunsul iti spune exact unde te afli in cele 6 etape.

In loc de "merge?"

Intreaba: "ai vreun blocker? PR-ul tau e in review activ sau asteapta pe cineva?" Diferentiezi intre "dev-ul are probleme tehnice" si "review-ul e blocajul".

In loc de "cand iese?"

Intreaba: "cand estimati merge in main? E o diferenta intre merge si deploy?" Asta te ajuta sa intelegi daca dupa merge mai e un pas pana la clientul real.

Red flags in commit history

Daca te uiti la istoricul commit-urilor unui branch sau PR, anumite pattern-uri sunt semne de probleme:

  • Multe commit-uri "fix" consecutive ("fix", "fix again", "really fix") - dev-ul a avut probleme si a iterat prin incercari. Posibil ca nu inteleg problema fundamentala.
  • Mesaje vagi ("update", "changes", "wip") - nu poti reconstrui ce s-a intamplat. Greu de reviewuit, greu de debugat in viitor.
  • Commit-uri uriase (mii de linii intr-un singur commit) - imposibil de reviewuit corect, ascund schimbari mixte.
  • "Merge conflicts resolved" repetate - munca s-a tras prea mult timp, intre timp main a evoluat mult.

Tu nu trebuie sa stii medicina la fel de profund ca medicul, dar daca ai un stetoscop si stii sa-l folosesti, poti detecta cand ceva nu suna bine. PR-ul e pacientul; vocabularul minim e stetoscopul. Nu vindeci, dar identifici cand e nevoie de atentie.
Contrast
Un PO fara fluenta tehnica primeste informatie filtrata - dev-ul decide ce ii spune si ce nu. Un PO cu fluenta tehnica vede direct si poate distinge intre "lucrul merge incet" si "lucrul e blocat de o decizie care nu s-a luat inca". A doua varianta poate fi rezolvata; prima nu.
Tehnica de memorare

Metoda "Vocabularul in context" - asocieri concrete

Nu memora termenii din tabelul de vocabular ca pe definitii. In schimb, pentru fiecare termen, gaseste o situatie concreta din echipa ta unde l-ai auzit (sau s-ar putea sa-l auzi):

  • Rebase → "Janno a zis ca trebuie sa rebase-uiesc inainte de merge"
  • Squash → "Edi prefera sa squash-uiasca commit-urile inainte de PR"

Termenii devin parte din povestea echipei tale, nu carduri de memorat. Memoria episodica (intamplari) e mai puternica decat memoria semantica (definitii pure).

Quiz - Interpretare

Vezi un PR cu titlul "fix" si descriere goala, 47 fisiere modificate, 1,800 linii adaugate, 6 commit-uri toate cu mesajul "wip". CI-ul e verde. Care e raspunsul cel mai bun ca PO?

Corect: CI verde inseamna "codul nu se sparge tehnic" - dar nu spune nimic despre intentie, scope, risc, intelegere. Un PR de 1,800 linii, fara descriere, fara istoric clar, va fi imposibil de inteles peste 3 luni cand cineva debuga ceva. Ca PO, ai o voce legitima in standardele de calitate ale echipei, nu doar in continutul functional. Asta e parte din fluenta tehnica.

Aplicare: Avise & IMK Portal

Ce se sparge fara conceptul asta
Cunoasterea fara aplicare e doar zgomot. Ai parcurs 6 module despre Git si GitHub - dar daca maine la standup-ul Avise sau la planning-ul IMK nu schimbi o singura intrebare, nu te-am ajutat. Ultimul modul e despre cum sa pui ce ai invatat la treaba in contextele tale concrete.

Avise - context probabil si intrebari potrivite

Pe baza a ceea ce stiu despre Avise (SaaS de contabilitate, echipa mica, faza de supravietuire, ciclu rapid de iteratie cu CEO-ul implicat direct), e foarte probabil ca echipa lucreaza trunk-based sau ceva apropiat:

  • Un singur main ca branch principal
  • Feature branches scurte, life cycle de zile, nu saptamani
  • Deploy frecvent in productie (zilnic sau aproape)
  • Probabil putin proces formal de release versioning - nu sunt clienti enterprise care cer notice de major version

Intrebari utile in contextul Avise

Cand Harris zice "am pregatit un fix pentru AI hallucinations":

→ "E intr-un PR open sau deja merged? Daca e merged, e deja in productie sau e nevoie de deploy separat?"

→ Te ajuta sa stii daca poti demonstra fix-ul la Graham acum sau peste o ora.

Cand discutati despre cele 66 test cases pe Evalite:

→ "Suita de teste ruleaza ca parte din CI la fiecare PR, sau e ceva ce ruleaza separat manual? Daca un PR pica testele AI, e blocant pentru merge sau doar warning?"

→ Te ajuta sa intelegi gradul de protectie real al productiei impotriva regresiilor in comportamentul AI.

Cand un demo iese prost:

→ "Versiunea de pe demo era exact ce e in main, sau era pe alt branch / build vechi? Care commit a fost deploy-uit pe demo?"

→ Te ajuta sa separi "bug real" de "demo a rulat un build invechit".

IMK Portal - context probabil si intrebari potrivite

IMK Portal pare un context diferit: produs B2B Dutch, multi furnizori (ThinkOut, CRIF, Stripe, SnelStart), faze de release planificate (Phase 1, Phase 2), echipa mai mare (Vlad, Alexandra, Leo, Emanuel, Eusebiu, plus Janno pe Dutch backend). Foarte probabil:

  • Strategie de branching mai structurata (poate GitFlow sau o varianta)
  • Release-uri marcate cu versiuni (importante pentru integrari)
  • Mai multe medii: dev → staging → production
  • Code review formal cu cel putin un aprobator necesar

Intrebari utile in contextul IMK Portal

Cand planifici Phase 2 cu Vlad:

→ "Ce versiune o sa fie Phase 2? E un minor bump fata de Phase 1 (1.x → 1.y) sau major (1.x → 2.0)? Asta afecteaza cum comunicam cu integratorii ThinkOut si CRIF?"

→ Versiunea numerotata e un contract cu echipele externe care fac integrare.

Cand Stripe billing integration e in lucru:

→ "Lucram cu feature flag pentru Stripe sau e o release pe branch separat? Daca e flag, cine il activeaza la GA si cum testam in productie fara sa-l vada clientii?"

→ Te ajuta sa intelegi cum poti face dogfooding cu clientii pilot fara sa expui la toata baza.

In review de sprint:

→ "Hai sa ne uitam in Jira la Development panel-ul fiecarui ticket - cate au PR merged, cate au PR open, cate inca nu au branch. Asta ne arata unde e blocajul real al sprint-ului."

→ Schimbi conversatia de la "ce simt oamenii" la "ce arata datele".

Lucruri concrete pe care sa le pui in practica saptamana asta

1. La proximul standup Avise sau IMK

Cand cineva zice "am terminat" sau "e gata", pune intrebarea: "e push-uit, in PR, sau merged in main?". O singura intrebare, calibrata pe etape.

2. Deschide trei PR-uri reale (Avise sau IMK)

Citeste-le, identifica: titlul e clar? Descrierea explica de ce? CI-ul e verde? Cati aprobatori? Cate fisiere modificate? Daca PR-ul e mare, ar fi putut fi spart? Nu trebuie sa actionezi, doar sa antrenezi ochiul.

3. Verifica conventia de branch naming

Deschide branch-urile active in repo (in GitHub: tab "Branches"). Cate au ID-ul Jira in nume? Daca multe nu au, asta e o conversatie cu tech lead-ul - micro-ajustare cu impact mare asupra trasabilitatii.

4. Configureaza un Jira filter

Creeaza un filter in Jira: "ticket-uri 'In Progress' cu PR OPEN mai vechi de 3 zile". Asta iti scoate la suprafata blocajele in code review, nu in development. E o intrebare pe care n-o pune nimeni de obicei in stand-up.

Metoda "Recall la 24h, 7 zile, 30 zile" - spaced repetition

Fara repetare, 70% din continutul de azi se va sterge in 7 zile. Cu trei recall-uri scurte, fixezi 80% pe termen lung:

Asta e curba de uitare Ebbinghaus aplicata: nu inveti din nou, doar reintaresti cand pe cale sa uiti.
