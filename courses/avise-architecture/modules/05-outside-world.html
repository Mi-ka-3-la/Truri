Module 5

The Outside World

Avise doesn't do everything itself. Authentication is Auth0. Notifications are Knock. Errors are caught by DataDog. Feature rollouts are controlled by Split.io. Remove any one — a part of Avise stops working.

Like a supplier chain in any business: every external service falls into one of three failure categories. Know the category, know how to respond.

HARD — app breaks immediately

Auth0

Authenticates every user login via JWT.

Failure: nobody can log in

AWS S3

Stores all user-uploaded files. Every PDF, Excel file, and generated export lives here.

Failure: file uploads and downloads fail

SOFT — feature degrades gracefully

Split.io

Controls feature flags and rollouts.

Failure: reverts to safe defaults

Knock

Sends notifications — email and in-app alerts when tasks are assigned or completed.

Failure: notifications stop, app works

DataDog

Collects logs, traces, and metrics from every service. The engineering team's window into the system.

Failure: blind to errors, app works

ASYNC — catches up when restored

QuickBooks Online

Source of accounting data for QBO customers. Syncs journal entries and transactions.

Failure: sync pauses, catches up

NetSuite

Source of ERP data for NetSuite customers. Syncs the same types of accounting data.

Failure: sync pauses, catches up

TurboPuffer

AI vector search index. Powers semantic search in the AI assistant.

Failure: falls back to keyword search

Auth0 asks "Who are you?" — SpiceDB asks "What can you do?"

These are two completely different questions answered by two completely different systems. Confusing them is the most common architecture mistake in systems with user accounts.

Auth0 — Authentication

Authentication: "Who are you?" Validates credentials, issues a signed JWT token. Auth0 knows nothing about tasks or journal entries.

SpiceDB — Authorization

Authorization: "What can you do?" Checks your permissions for each specific resource. SpiceDB knows nothing about passwords.

1
User logs in

Auth0 validates email + password (or Google SSO). Issues a signed JWT.

2
User makes an API request

avise-api receives the request with the JWT in the header.

3
jwtAuthentication() — who is this?

Auth0 validates the token. If it's valid, we know the user's identity.

4
SpiceDB check — what can they do?

Inside the route handler, SpiceDB answers whether this specific user has permission for this specific resource.

avise-api/src/apiRouter.ts
1
r.use(jwtAuthentication());      // Step 1: Auth0 — who is this person?

Every request passes through this middleware first. Auth0 validates the JWT. If the token is missing or expired, the request is rejected here — before it reaches any route.

2
r.use(userIdentityMiddleware()); // Step 2: Look them up in our DB
// Then SpiceDB permission check happens inside the route handler

After Auth0 confirms identity, Avise looks up the user's full record in PostgreSQL. Then, inside each route handler, SpiceDB is called to check the specific permission needed for that action.

Separation is a security feature, not just a design choice.

If SpiceDB is compromised, passwords are still safe in Auth0. If Auth0 is compromised, permission rules are still safe in SpiceDB. Two separate attack surfaces are harder to break simultaneously than one combined system.

Split.io: the traffic controller for new features

Every significant new feature in Avise is gated behind a feature flag. This lets engineering roll out changes to 5% of companies first, then 50%, then everyone — and kill a feature instantly if something goes wrong.

When the flag toggles, the search path changes

Same user request — two completely different routes through the system.

graph LR
  A["User searches for concept"]:::active --> B["enableNewSearch = true"]:::active
  B --> C["AI search pipeline"]:::active
  C --> D["TurboPuffer vector query"]:::active
  D --> E["Semantic results returned"]:::active

When ON: the request routes through the new AI-powered search pipeline. TurboPuffer finds journal entries by meaning — not just matching words. A search for "capital expenses" finds entries about "equipment purchases" and "capex." 

graph LR
  A["User searches for concept"]:::active --> B["enableNewSearch = false"]:::active
  B --> C["Legacy keyword search"]:::active
  C --> D["PostgreSQL LIKE query"]:::active
  D --> E["Exact-match results returned"]:::active
  classDef active fill:#FEF3C7,stroke:#D97706,stroke-width:2.5px,color:#1F1D1B;

When OFF: the request uses the legacy keyword search. PostgreSQL runs a LIKE query — it only finds entries that contain the exact words typed. Simpler, faster, but misses synonyms and related concepts.

Flag: enableNewSearch. Default: false in production during rollout, true in staging. Safety net: FALLBACK_FEATURE_FLAGS activates when Split.io is unreachable — all flags revert to safe conservative defaults. The app never crashes because Split.io is down. Why it exists: gradual rollout (10% of companies first), instant kill switch if bugs appear, and A/B testing search quality.
avise-api/src/app.ts
1
await FeatureFlagsClient.waitUntilReady();
// App doesn't start until Split.io is ready

The server waits for Split.io to load all flag values before accepting any requests. This ensures that the very first request gets the correct flag state, not a stale default.

2
// avise-shared-utils/src/featureFlags/config.ts (conceptual)
// FALLBACK_FEATURE_FLAGS activates when Split.io is unreachable:
// All flags revert to their safe default values.
// The app never crashes because Split.io is down.

The fallback constant is the safety net. If Split.io is down, features revert to conservative defaults — usually "flag OFF" to keep the stable legacy path running. The app continues working; it just doesn't roll out new features during the outage.
