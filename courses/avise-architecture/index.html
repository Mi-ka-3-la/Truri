Layer 2: Axios wraps every request in a typed envelope

Before any data leaves the browser, it passes through a thin wrapper called Axios. Here is the actual wrapper from avise-web/src/api/apiClient.ts:

avise-web/src/api/apiClient.ts
1
const aviseApiConfig: AxiosRequestConfig = {
  baseURL: import.meta.env.REACT_APP_API_URL || "",
};

Create a config object with one setting: baseURL. This is the root address every request will be sent to. import.meta.env reads from an environment variable so the same code works in dev (localhost:3001) and in production (api.avise.com) without any changes.

2
const axiosInstance = axios.create(aviseApiConfig);

Create a single, pre-configured Axios instance. Think of this as a stamped envelope: every request that goes through axiosInstance already knows where it is going. You never have to repeat the base URL.

3
export const api = {
  post: <T>(url: string, data?: any, config?: AxiosRequestConfig<T>) => {
    return axiosInstance.post<T>(url, data, config);
  },
  get: <T>(url: string, config?: AxiosRequestConfig<T>) => {
    return axiosInstance.get<T>(url, config);
  },
};

Export an api object with typed post and get methods. The <T> is TypeScript generics — it lets the rest of avise-web call api.post<JournalEntry>(...) and get back a properly typed response. The whole codebase calls api.post instead of Axios directly, so if the underlying HTTP library ever changes, there is only ONE place to update it.

Wrapping a dependency is the single best architectural habit.

By never calling Axios directly — always via api.post — the codebase stays decoupled from any one library. This is called the Adapter pattern. You will see it in every mature codebase you encounter, under many different names.

Layers 3 & 4: The Express Router — every request passes through security first

When an HTTP request arrives at avise-api, it is routed through a chain of middleware functions before any business logic runs. Here is the router that defines that chain:

avise-api/src/apiRouter.ts
1
function apiRouter(): Router {
  const r = Router();

Create a new Express Router. This object will collect all the routing rules and middleware we attach to it.

2
  r.use(jwtAuthentication());
  r.use(userIdentityMiddleware());

Every single request that reaches this router hits these two layers first — no exceptions. jwtAuthentication() validates the JWT token attached to the request — is the caller who they say they are? userIdentityMiddleware() then looks up the actual user record in the database, so the rest of the code knows the full user object, not just their ID from the token.

3
  r.use("/organizations/:organizationId", organizationRouter());
  r.use("/companies/:companyId", companyContextMiddleware(), companyRouter());
  r.use("/notifications", notificationsRouter);

Once identity is established, requests are routed by URL path. Company-specific routes get one more middleware layer: companyContextMiddleware() verifies the user actually has access to the specific company in the URL before the request goes any further. Only then does companyRouter() handle it.

4
  return r;
}

Return the configured router so the main Express app can mount it. Every rule registered here applies to any request that hits this router.

Middleware is airport security — everyone passes through, and the order is law.

You prove who you are (JWT check), then the system looks you up in its records (userIdentity), then you proceed to your destination (your route). No gate-jumping. If jwtAuthentication rejects a request, it never reaches companyContextMiddleware or the actual handler. Order is architecture.

The startup order IS the dependency graph

Open avise-api/src/app.ts and the first thing you see is a sequence of imports. That sequence is not arbitrary — it is an architectural decision encoded directly in code.

avise-api/src/app.ts — startup order
1
import "avise-shared-utils/datadog";

Observability FIRST. DataDog must be initialized before any other service. If Prisma fails to connect but DataDog is not yet running, that connection error goes completely untracked — like a black box recorder that powers on after the crash.

2
import { FeatureFlagsClient } from "avise-shared-utils/featureFlags";

Feature flags second. The FeatureFlagsClient connects to Split.io. Subsequent startup steps may check whether a new feature is enabled — if flags are not ready, those checks silently default to the wrong state.

3
import prisma from "./prisma";

Database connection third. Prisma connects to PostgreSQL. Now that DataDog is running, any connection error here will be captured and visible in the monitoring dashboard.

4
import { buildApp } from "./buildApp";

Express app constructed fourth. Only once the database is ready does the HTTP server get built. This prevents requests from arriving before the app can handle them correctly.

5
import bullmq from "./libraries/bullmq";

Job queue fifth. BullMQ workers start picking up queued background tasks. Jobs submitted before this point will wait in Redis until the worker is ready.

6
import { initializeAuthClient } from "./authorization/authorizationClient";

Permission system sixth. The SpiceDB authorization client opens. No incoming request can bypass permission checks because the client is established before the server begins accepting traffic.

7
import { WebSocketServer } from "avise-shared-utils/websocket/server";

Real-time channel seventh. The WebSocketServer opens the persistent connections used by the AI chat. This requires the auth client (step 6) to already be running so incoming WebSocket connections can be authenticated immediately.

8
import { initializePublisher } from "avise-shared-utils/rabbitmq";

Message bus last. RabbitMQ is the broadcast channel between services. It comes last because all the services it connects to must be ready to receive messages before publishing begins.

The startup order IS the dependency graph

If Prisma connects before DataDog is running, connection errors go untracked. If the WebSocketServer starts before the auth client is ready, connections arrive unauthenticated. The import order in app.ts is not a style choice — it is an architectural constraint written as code. In any codebase, the startup sequence is one of the best places to quickly understand what depends on what.

avise-domains: the same types, used everywhere

Most codebases tie business logic to its delivery mechanism. avise-domains breaks that pattern — and the payoff is enormous.

The layered approach
1
HTTP Controller

Parses the incoming request — tied to Express.

2
Service layer

Business logic — knows about controllers above it.

3
Data layer

SQL — tied to PostgreSQL below it.

Each layer is tied to its neighbors. Reuse a type in a CLI script? Impossible without dragging in HTTP dependencies.

The domain-centric approach
1
Domain type: JournalEntry

Knows nothing about HTTP or SQL. Just business meaning.

2
REST controller uses it

Converts HTTP request INTO a JournalEntry domain type.

2
Background job uses it too

Same type — no modification needed.

The domain type is stable. Any consumer — REST, CLI, job — can use it without knowing about the others.

avise-domains — domain types in plain language
1
// avise-domains — domain types don't know about HTTP or databases

The types in this workspace describe the business — not the delivery. They do not import from Express, from Prisma, or from any database library.

2
// They describe business concepts in the language of accounting:
// A Schedule. A JournalEntry. A PreparedSchedule.

The vocabulary comes from the problem domain — accounting — not from the technology. A JournalEntry type describes what an accountant means by "journal entry," independent of how it is stored in PostgreSQL or sent over HTTP.

3
// The REST API, the CLI, and the background job all use the same types.

Three completely different execution contexts — an HTTP handler, a command-line script, a background worker — all import from avise-domains. They all speak the same language, which means any validation rule written once applies everywhere.

4
// Conversion to/from HTTP request/SQL row is handled OUTSIDE the domain.

Parsing an HTTP request body into a JournalEntry happens in the controller. Converting a Prisma database row into a JournalEntry happens in a mapper function. The domain type itself stays pure.

A domain type is like a word in a dictionary

It has a precise meaning that does not change depending on who is reading it. The REST API and the background job speak the same language because they share the same domain types. Wherever you see this pattern in any codebase, it signals a deliberate choice to make business rules portable — the team can change the delivery mechanism (swap Express for another framework) without rewriting the business logic.

REST: the phone call — you dial, you wait, you get your answer

Most interactions in Avise use REST. The browser makes a request, the server processes it, and the browser waits for the response before updating the screen.

avise-web/src/api/apiClient.ts — the HTTP wrapper
1
export const api = {
  post: <T>(url: string, data?: any) => axiosInstance.post<T>(url, data),
  get: <T>(url: string) => axiosInstance.get<T>(url),
};

A thin wrapper around Axios. Every API call in avise-web goes through this object — meaning things like authentication headers and base URL configuration are applied once and inherited everywhere. The TypeScript generic <T> ensures the response is typed, not just a raw object.

2
// Usage with React Query (useMutation):
const { mutate, isPending } = useMutation({
  mutationFn: () => api.post('/v1/companies/:id/journal-entries', payload)
});

React Query wraps the Axios call. useMutation is the hook used for operations that change data — creating, updating, or deleting. While isPending is true, the component can show a spinner. When the mutation resolves, React Query automatically updates any cached data that is now stale.

3
// While isPending is true, show a spinner.
// When it resolves, update the UI.

The caller is blocked until the response arrives — that is a feature, not a bug. The UI needs to know whether the save succeeded before it can confirm anything to the user. REST is correct here because the operation finishes in well under 5 seconds and the result matters immediately.

REST is a phone call — blocking is the point

You dial, you wait for the person to pick up, you get your answer, you hang up. The caller is blocked until the response arrives. For anything that finishes in under 5 seconds and where the UI must know the result before continuing, REST is exactly right. Choose a different pattern only when REST's blocking nature becomes a problem — like when the work takes 40 seconds or the server needs to push updates the client did not ask for.

WebSocket: the walkie-talkie — the channel stays open

The AI chat cannot use REST. The model sometimes thinks for 90 seconds and sends a dozen intermediate updates along the way. A WebSocket channel stays open for the entire conversation — the server can push events the moment they happen.

avise-api/src/app.ts + avise-api/src/ai/index.ts
1
import { WebSocketServer, AuthenticatedWebSocket }
  from "avise-shared-utils/websocket/server";

The WebSocketServer comes from avise-shared-utils — both avise-api and any future service that needs real-time communication import the same implementation. AuthenticatedWebSocket is a type that extends the standard WebSocket with a jwtPayload field, so every message received on the socket already carries the user's identity.

2
async function handleNewWebSocketConnection(ws: AuthenticatedWebSocket) {
  const idpId = ws.jwtPayload.sub;
  const identity = await identityService.getUserIdentityByIdpId(idpId);
  if (identity) ws.userId = identity.id;
}

When a new WebSocket connection arrives, the server immediately resolves the user identity from the IDP ID inside the token. This lookup happens once per connection — all subsequent messages on this channel are already attributed to the right user without re-checking auth.

3
// avise-api/src/ai/index.ts — server pushes typed events as the AI thinks:
ws.send({ type: 'tool_call', toolName: 'findJournalEntries' });
ws.send({ type: 'artifact', artifact: tableData });
ws.send({ type: 'message', content: assistantText });
ws.send({ type: 'done' });

Four event types flow down the channel. tool_call appears when the AI decides to search for data — the browser can show "Searching journal entries..." while the AI is still thinking. artifact carries structured data (a table, a chart). message carries the assistant's text. done signals the browser to stop the loading state.

WebSocket eliminated the AI timeout problem entirely

Before WebSocket, AI chat used HTTP requests — and HTTP requests time out after roughly 30 seconds. The LLM sometimes takes longer. WebSocket eliminates this entirely. The channel lives until either side closes it — meaning the AI can take 90 seconds, send ten intermediate events, and the browser receives every one of them without any timeout. This is the kind of architectural constraint that turns an impossible feature into a working product.

BullMQ and Argo: the inbox and the project board

When work takes minutes — or hours — you do not make the user wait. You drop it in a queue, continue the response immediately, and let a worker pick it up.

BullMQ — producer and worker pattern
1
// Producer (avise-api): add a job to the queue
await queue.add('processRecurringTask', { taskId, companyId });

The API immediately adds a job to the queue and returns a response to the user. The user does not wait for the work to finish — just for the job to be accepted. This takes milliseconds.

2
// Worker (separate process): pick up and process jobs
worker.on('completed', job => logger.info(`Job ${job.id} completed`));
worker.on('failed', (job, err) => logger.error(`Job ${job.id} failed`, err));

A separate worker process polls Redis for new jobs. completed and failed events fire once the work is done — both are logged so the team can track what happened to every job. If the server crashes mid-job, BullMQ marks it as failed and can retry automatically.

Choosing between BullMQ and Argo Workflows

BullMQ
1

Minutes-long jobs on a single server

2

Backed by Redis — jobs survive restarts

3

Recurring tasks, email sending, report generation

Argo Workflows
1

Hours-long jobs distributed across Kubernetes

2

3

The codebase has TODOs marking this in-progress migration

NS sync and QBO sync currently run as BullMQ jobs. There are explicit migration TODOs in the codebase moving them to Argo Workflows. The reason: these jobs sometimes run for 45+ minutes, need full observability, and must survive server restarts without losing state. BullMQ can handle them, but Argo was built for exactly this scale.

Module 4

Where Things Live

Avise stores data in 5 different places. That's not laziness — each storage system exists because it's the right tool for a specific job.

Think of a law firm's filing system: permanent case files go in locked cabinets, access badges live with security, faxes go in a shredder when done, and archived documents go in off-site storage. Everything has a place — because mixing them would be chaos.

PostgreSQL

Permanent records

Journal entries, tasks, companies, users — the source of truth for all business data. Medium speed, highly reliable.

SpiceDB

Permission graph

Who can access what resource — and nothing else. Very fast, completely separate from business data.

Redis

Fast temporary store

BullMQ job definitions, session cache. Extremely fast, not permanent.

AWS S3

File warehouse

Uploaded PDFs, Excel files, generated exports. Slow to retrieve, but very cheap at scale — exactly the right tradeoff for large files.

TurboPuffer

AI vector index

Semantic embeddings of documents for AI-powered search. Fast for "find similar meaning" queries that PostgreSQL cannot do.

Everything traces back to a Company

SpiceDB: permissions live in a completely separate database

When you ask "Can this user edit this task?" — Avise queries SpiceDB, not PostgreSQL. Business data and permission data grow at different rates and must stay separate.

avise-api/src/authorization/authorizationClient.ts
1
// SpiceDB is NOT PostgreSQL. It's a completely separate database.
// It stores ONLY relationships: "User A is an admin of Company B"

SpiceDB never holds a journal entry, a task, or a company name. Its entire job is to answer one question: "does this relationship exist?" — fast.

2
// When you ask "Can this user edit this task?" — the app queries SpiceDB.
// PostgreSQL never gets asked about permissions.
import { ResourcePermissions, ResourceRelations } from "../generated/allspice/types";

The types come from Allspice — Avise's own code-generation tool. It reads the SpiceDB schema and produces TypeScript types automatically.

3
// The Allspice DSL generates these types from the SpiceDB schema.
// Every permission check is type-safe at compile time:
// "task" and "assignee" are checked against the real schema.
export type WriteRelationshipsInput<
  Resource extends keyof ResourceRelations & string,
  Subject extends keyof ResourceRelations[Resource] & string,
> = WriteRelationshipsParams<ResourceRelations, ResourcePermissions, Resource, Subject>[];

The generic type ensures that "task" and "assignee" are real names from the SpiceDB schema — not strings you typed by hand. A typo becomes a compile error, not a runtime bug.

Avise invented Allspice to make permissions type-safe.

If you write a permission check for a resource that doesn't exist in SpiceDB, TypeScript catches it at compile time — before it ever hits production. Business data grows constantly. Permission data changes rarely. Mixing them in one database would cause either slow permission checks or slow business queries — so they live apart by design.

Three more storage systems — each solving a different problem

PostgreSQL handles permanent records. SpiceDB handles permissions. These three handle everything else — and each exists because the alternatives would be catastrophically wrong.

Redis — BullMQ backend

BullMQ stores job definitions in Redis. If avise-api restarts mid-job, Redis still holds the job. The next worker picks it up. Data survives server restarts without needing a full database.

When to use: any async work that must survive server failures.

AWS S3 — file warehouse

When a user uploads a PDF, the file goes directly to S3. Avise stores only the S3 key (like a library card number) in PostgreSQL — not the file itself. Storing a 50MB file in a relational database would be catastrophically slow.

When to use: any user-uploaded file, any generated export.

TurboPuffer — vector search

When the AI searches for "journal entries about rent expense," a SQL LIKE query won't work. TurboPuffer stores vector embeddings: mathematical representations of meaning. Similar meanings cluster together, so "rent" and "lease payments" match.

When to use: semantic or AI-powered search.

Avise doesn't do everything itself. Authentication is Auth0. Notifications are Knock. Errors are caught by DataDog. Feature rollouts are controlled by Split.io. Remove any one — a part of Avise stops working.

Like a supplier chain in any business: every external service falls into one of three failure categories. Know the category, know how to respond.

Auth0 asks "Who are you?" — SpiceDB asks "What can you do?"

These are two completely different questions answered by two completely different systems. Confusing them is the most common architecture mistake in systems with user accounts.

Auth0 — Authentication

Authentication: "Who are you?" Validates credentials, issues a signed JWT token. Auth0 knows nothing about tasks or journal entries.

SpiceDB — Authorization

Authorization: "What can you do?" Checks your permissions for each specific resource. SpiceDB knows nothing about passwords.

1
User logs in

Auth0 validates email + password (or Google SSO). Issues a signed JWT.

2
User makes an API request

avise-api receives the request with the JWT in the header.

3
jwtAuthentication() — who is this?

Auth0 validates the token. If it's valid, we know the user's identity.

4
SpiceDB check — what can they do?

Inside the route handler, SpiceDB answers whether this specific user has permission for this specific resource.

avise-api/src/apiRouter.ts
1
r.use(jwtAuthentication());      // Step 1: Auth0 — who is this person?

Every request passes through this middleware first. Auth0 validates the JWT. If the token is missing or expired, the request is rejected here — before it reaches any route.

2
r.use(userIdentityMiddleware()); // Step 2: Look them up in our DB
// Then SpiceDB permission check happens inside the route handler

After Auth0 confirms identity, Avise looks up the user's full record in PostgreSQL. Then, inside each route handler, SpiceDB is called to check the specific permission needed for that action.

Separation is a security feature, not just a design choice.

If SpiceDB is compromised, passwords are still safe in Auth0. If Auth0 is compromised, permission rules are still safe in SpiceDB. Two separate attack surfaces are harder to break simultaneously than one combined system.

Every significant new feature in Avise is gated behind a feature flag. This lets engineering roll out changes to 5% of companies first, then 50%, then everyone — and kill a feature instantly if something goes wrong.

Operation tracking: the flight recorder for background jobs

Long-running jobs — QBO syncs, Argo workflows, bulk imports — can run for minutes or hours. If one stops unexpectedly, operation tracking tells you exactly which step was last completed.

avise-shared-utils/src/operationTracking/index.ts
1
// Every long-running job creates an Operation.
// Events are appended over its lifetime.
async function createEventForOperationId(
  operationId: string,
  event: IncompleteOperationEvent,
): Promise<OperationEvent> {

Every long-running job first creates an Operation record. Then, as the job progresses, it calls this function to append events — one per meaningful step. The operation record is the thread; the events are the beads.

2
  const operation = await getOperation(operationId);
  // Each event: what happened, when, by whom, any data payload
  return createEventForOperation(operation, event);
}

Each event records what happened, when it happened, and any relevant payload. When a job stops unexpectedly, you query events ordered by created_at — the last event is the last step the job completed before going silent.

3
// To understand what a stuck job did:
// 1. Get the operation ID (from logs or DataDog)
// 2. Query operation events ordered by created_at
// 3. The last event tells you exactly where it stopped

This is the three-step playbook for any stuck job. You don't need to reproduce the failure — the events already recorded everything. A job that ran 3 hours and then stopped is no longer a mystery; it's a solved case waiting for you to query it.

Operation tracking is a flight recorder for background jobs.

The plane (job) already landed or crashed — but the recorder tells you everything that happened during the flight, second by second. Without it, a stuck job is a mystery. With it, it's a solved case. This pattern — event sourcing applied to background jobs — is one of the most powerful debugging patterns in distributed systems.
