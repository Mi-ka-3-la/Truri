Chapter 0 — Foundation

What even is an API?

Think of a restaurant. You don't go into the kitchen and cook. You talk to the waiter. The waiter is the API.

🍽️
You (Client)
Your app, mobile, browser. Asks for data. Doesn't know how the kitchen works.
🧾
The Waiter (API)
The contract between client and server. Speaks a clear language both sides understand.
👨‍🍳
The Kitchen (Server)
The database, business logic, the actual data. Hidden from the outside world.
"REST has been so utterly misused that it actually means nothing anymore. This book doesn't get hung up on politics — it gives you what actually works."
— Phil Sturgeon
💡
The whole book in one sentence Use HTTP the way it was designed: nouns as URLs, verbs as methods, status codes as meaning — then build a clean contract on top.
Chapter 2 — Planning

Designing Good Endpoints

The URL is a noun. Never, ever a verb. This one rule saves you from 80% of bad API design.

❌
Never put actions in your URL POST /sendUserMessage  or  GET /getUserById?id=5
URLs describe things, not actions. The HTTP method IS the action.
✅
Nouns only. Use HTTP verbs for the action. POST /messages  —  GET /users/5
endpoint-plan.txt — Your API action plan
// For any resource, you get these 5 actions:

POST /users // Create a new user
GET /users/{id} // Read one user
PUT /users/{id} // Update a user (full replace)
DELETE /users/{id} // Delete a user
GET /users // List all users

// Sub-resources for relationships:
GET /users/{id}/checkins // User's checkins
GET /users/{id}/favorites // User's favorites

Plural vs Singular?

📐
Always plural. Always. /users not /user. If everything is plural, there's no ambiguity. /user — is that "me"? One user? A collection? Confusing.

POST vs PUT — the eternal fight

POST
When you don't know the URL
Creating something new where the server assigns the ID. POST /users → server returns new ID.
PUT
When you know the full URL
Idempotent — do it 10 times, same result. PUT /users/5/settings → replaces entire resource.
PATCH
Partial update
Only send the fields you want to change. Not all APIs implement this but it's the "right" way for partial updates.
Chapter 2 — HTTP Verbs

HTTP Methods in Action

The verb is not part of the URL. It IS the URL. Click each method to see it in context.

Request
GET /users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer abc123
Accept: application/json
Response
HTTP/1.1 200 OK
Content-Type: application/json

{
  "data": {
    "id": 42,
    "name": "Mihaela"
  }
}
✅
GET is safe and idempotent — no side effects, can be called 100x, same result. Never use GET to modify data.
Request
POST /users HTTP/1.1
Content-Type: application/json

{
  "name": "Mihaela",
  "email": "m@example.com"
}
Response
HTTP/1.1 201 Created
Location: /users/43

{
  "data": {
    "id": 43,
    "name": "Mihaela"
  }
}
⚠️
POST is NOT idempotent — call it twice, create two users. The server assigns the new ID, which is why you see it in the response.
Request
PUT /users/42 HTTP/1.1
Content-Type: application/json

{
  "name": "Mihaela B.",
  "email": "new@example.com"
}
Response
HTTP/1.1 200 OK

{
  "data": {
    "id": 42,
    "name": "Mihaela B."
  }
}
💡
PUT replaces the entire resource. Omit a field? It gets wiped. Use PATCH for partial updates (only the fields you send get changed).
Request
DELETE /users/42 HTTP/1.1
Authorization: Bearer abc123
Response
HTTP/1.1 204 No Content

// Empty body — nothing to return,
// the resource is gone.
💡
204 No Content is the correct response for DELETE. The thing is gone — there's nothing to show. Some APIs return 200 with a confirmation message, which is also fine.
Chapter 4 — Errors

Status Codes & Error Handling

HTTP already has a language for "it worked" and "it broke." Use it. Don't return 200 OK with an error body — that's lying.

2xx
Success
It worked.
200
OK
Generic success. Good for GET and PUT.
201
Created
POST success. New resource was made.
204
No Content
Success but nothing to return. Use for DELETE.
301
Moved
URL changed permanently. Update your bookmarks.
400
Bad Request
Client sent garbage. Fix your request.
401
Unauthorized
Not logged in. Go authenticate first.
403
Forbidden
Logged in, but you don't have permission.
404
Not Found
That resource doesn't exist.
422
Unprocessable
Right format, wrong data. Validation failed.
500
Server Error
Something blew up on our side. Not your fault.
503
Unavailable
Server is down or overloaded. Try later.
☠️
The biggest sin in API design Returning 200 OK with "error": "Something went wrong" in the body. The status code IS the error. Use it.

Good error response structure

error-response.json — The right way
HTTP/1.1 422 Unprocessable Entity

{
  "errors": [
    {
      "status": "422",
      "code": "VAL-001", // machine-readable code
      "title": "Invalid email", // short human summary
      "detail": "'foo' is not a valid email address"
    }
  ]
}
💡
Always return multiple errors at once. If validation fails on 3 fields, tell the user about all 3 in one response — not one at a time. Returning errors one-by-one is lazy and wastes round trips.
Chapter 3 & 6 — Data

Input & Output Design

What you accept and what you return. The #1 mistake: dumping raw database rows directly into the response.

💣
Never do this return json_encode(User::find($id)->toArray())
This leaks password hashes, internal tokens, and fields you never meant to expose. The database schema is not your API contract.
transformer.php — Use a transformer layer
class UserTransformer {

  public function transform(User $user) {
    return [
      'id' => (int) $user->id, // ← cast to int
      'name' => $user->name,
      'email' => $user->email,
      'joined' => (string) $user->created_at
      // ← NO password, NO tokens, NO internal fields
    ];
  }
}

Response structure: always wrap in "data"

Single resource
{
  "data": {
    "id": 42,
    "name": "Mihaela"
  }
}
Collection
{
  "data": [{...}, {...}],
  "meta": {
    "total": 156,
    "page": 1
  }
}
🏗️
Why wrap in "data"? It gives you space. You can add pagination metadata, links, warnings — all alongside your data without breaking the structure. Start with the wrapper and you never have to break backwards compatibility.
Chapter 7 — Relationships

Data Relationships

A user has checkins. A place has photos. How you represent these relationships defines how painful your API is to consume.

🔗
Subresources
A separate URL for related data. Simple, clear. Extra HTTP request to fetch.
🔑
Foreign Keys
Include just the IDs. "checkin_ids": [1,2,3]. Client fetches what it needs.
📦
Sideloading
Include related data in a separate key. No duplication. Complex to implement.
🪆
Nesting/Embedding
Embed related objects inside the parent. Easy to read. Can get big and slow.

The tradeoff visualized

Subresources
GET /places/5 → place data
GET /places/5/checkins → 2nd request needed
GET /places/5/photos → 3rd request needed
Embedding with ?include= (the best of both)
GET /places/5?include=checkins,photos → 1 request, everything included

{
  "data": {
    "id": 5,
    "name": "Barcade",
    "checkins": [{...}, {...}], // only when asked
    "photos": [{...}]
  }
}
✅ Sideloading wins when...
  • Many items share the same related object (50 comments, 3 authors)
  • You want no duplication in the payload
  • Mobile clients need to minimize bandwidth
⚠️ Nesting hurts when...
  • Same sub-object repeats 50 times
  • Client doesn't need that data at all
  • Response balloons to megabytes
Chapter 9 — Security

Authentication & OAuth 2.0

Who are you, and are you allowed to do that? Two separate questions. 401 = who are you? 403 = I know who you are, still no.

🔑
API Keys
Simplest. One string that identifies you. Good for server-to-server. Bad for mobile apps (keys get stolen).
🎟️
Bearer Tokens
Short-lived token in the Authorization header. Modern standard. Issued by OAuth 2.0.
🔐
OAuth 2.0
The industry standard. Handles "Login with Google", app permissions, token refresh. Complex but right.

Chapter 10 — Pagination

Pagination — Never Return Everything

Your database has 10 million rows. The client wants a list. You don't send 10 million rows. You send a page.

📄
Offset Pagination
?page=3&per_page=20
Simple. Fast to implement. But page 3 shifts if new data is inserted. Classic for admin UIs.
🔖
Cursor Pagination
?after=abc123
Stable even when data changes. Used by Twitter/Instagram. The right choice for feeds.
Offset — Page 2 of 8
GET /posts?page=2&per_page=10
1
2
3
…
8
Cursor — "give me what comes after this"
GET /posts?after=eyJpZCI6MTUwfQ==
← prev  |  next →
pagination-response.json — Include navigation links
{
  "data": [{...}, {...}],
  "meta": {
    "total": 156,
    "per_page": 10,
    "page": 2
  },
  "links": {
    "self": "/posts?page=2",
    "next": "/posts?page=3",
    "prev": "/posts?page=1",
    "last": "/posts?page=16"
  }
}
Chapter 13 — Versioning

API Versioning — Change Without Breaking

You will need to change your API. Clients will not update immediately. Versioning is how you change the world without burning it down.

🛣️
URL Versioning
/v1/users
Most visible. Easy to route. Most developers use this. Not "pure REST" but very practical.
📬
Header Versioning
Accept: application/vnd.api+json;version=2
Cleaner URLs. Much harder to test (can't just paste in browser).
🔀
Content Negotiation
Like header versioning but uses mime types. Used by GitHub API. Elegant but complex.
🏆
Phil's recommendation: URL versioning is fine Yes, purists will complain. But your developers can read it, test it with a browser, and your ops team can route it. Pragmatism beats purity.

/v2/users is infinitely better than a broken API with no versioning at all.

The golden rule of versioning

✓
Additive changes — no version needed
Adding new fields to a response, new optional query params, new endpoints. Old clients ignore new fields — no harm done.
!
Renaming fields — bump the version
"username" → "handle" breaks every client that expects "username". This needs v2.
✕
Removing fields — always a breaking change
Never remove a field from an existing version. Clients depend on it. Deprecate it first, remove it only in the new version after warning clients.

The 10 Rules to Remember

1️⃣
URLs are nouns
Never put actions in the URL. The HTTP method is the verb.
2️⃣
Always plural
/users not /user. No ambiguity.
3️⃣
Use status codes correctly
200 with error body = lying. The status IS the message.
4️⃣
Always use a transformer
Never dump raw DB rows. Control every field you expose.
5️⃣
Wrap in "data"
Gives you room to add metadata without breaking changes.
6️⃣
Return all validation errors
Don't make users submit 5 times to discover 5 errors.
7️⃣
Tokens in headers, not URLs
URLs end up in server logs. Auth tokens don't belong there.
8️⃣
Always paginate collections
Never return an unbounded list. Always include navigation links.
9️⃣
Support ?include= for relations
Let clients ask for what they need. Don't force everything into every response.
🔟
Version for breaking changes
Adding = fine. Changing/removing = bump to v2. Never break old clients.
