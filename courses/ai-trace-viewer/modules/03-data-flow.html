The cache: how it stores and how it forgets

Here is the actual code that sets up caching — from services/trace-service.ts:

CODE 

const getTrace = unstable_cache(
  getTraceUncached,
  ["trace-detail"],
  {
    revalidate: CACHE_SECONDS.traces,
    tags: ["trace"],
  }
);
PLAIN ENGLISH

Create a cached version of the function that fetches a conversation.

Wrap the real function that does the database work.

Give this cache a name so Next.js can identify it.

Settings:

Automatically expire the cached result after 120 seconds — then fetch fresh data.

Tag this cache entry "trace" — this is how we can clear it on demand (see below).

That tags: ["trace"] is not just a label — it is a handle. When a reviewer posts a new comment, the notes feature calls revalidateTag("trace") — which tells Next.js: delete every cached result tagged "trace" right now. The next person to open that conversation gets fresh data from the database, including the new comment in the note count.

🏷️
Cache tags: the on/off switch

Automatic expiry (120 seconds) covers the normal case — data gradually goes stale. Tags cover the exceptional case — you know right now that specific data has changed. Together they give you both passive freshness and active invalidation. This two-pronged approach is used in production apps everywhere.

Two queries in one: messages and their artifacts

The function that does the real work is getTraceUncached. After fetching the conversation and messages, it does a second pass to collect any AI-produced artifacts:

CODE 

const artifactIds = conversation.messages.flatMap(message =>
  extractArtifactIds(message.metadata as ...),
);

if (artifactIds.length > 0) {
  const rows = await prisma.$queryRaw<...>`
    SELECT id, status, started_at, stopped_at, operation_data
    FROM   operations
    WHERE  id = ANY(${artifactIds}) AND
           operation_type = 'AIArtifact'
  `;
}
PLAIN ENGLISH

flatMap goes through every message and extracts the artifact IDs mentioned in its metadata — then merges all those ID lists into a single flat list.

Each message stores artifact references in its metadata field — a JSON blob that contains extra context about what the AI was doing.

Only run the next query if there are actually artifact IDs to look up — no point hitting the database with an empty list.

Ask Prisma to run raw SQL — useful when Prisma's standard API is not expressive enough for a specific query.

Fetch only the columns needed (status, timing, data).

From the operations table — a shared table that stores all kinds of operations, not just AI artifacts.

ANY(artifactIds) is a PostgreSQL shorthand: it matches any row whose ID appears in the list. More efficient than a long OR chain.

Filter to only AIArtifact rows — ignoring unrelated operation types in the same table.

Where all this code lives

The data-flow code is split across a logical feature-based architecture:

src/ All application source code
services/ Data fetching with caching — trace-service.ts, dashboard-service.ts, notes-service.ts
infrastructure/ Database connections — prisma.ts (PostgreSQL), sqlite.ts (notes + FTS5 index)
domain/ Pure business logic — filters.ts, traces.ts (artifact extraction), topics.ts
features/ One folder per feature: traces/ dashboard/ notes/ trace-detail/ reliability/
types/index.ts All shared TypeScript interfaces — FullTrace, TraceSummary, TraceFilters, etc.
🗺️
Why this matters when talking to AI coding agents

Knowing this structure means you can be precise: "Update the date filter logic in domain/filters.ts, add the date parameter to the Prisma query in features/traces/loaders.ts, and update the UI in features/filters/components/FilterBar.tsx." That specificity produces far better results than "add a date filter."
