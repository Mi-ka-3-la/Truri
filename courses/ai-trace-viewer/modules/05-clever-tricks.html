Notes, Search & Clever Tricks

Two databases, instant feedback, cache invalidation on demand, and a search engine built into the filing cabinet.

Why two databases? Because they solve different problems.

🏛️

PostgreSQL

READ ONLY Trace Viewer never writes here
PRODUCTION DATA Came from the live Avise platform
MILLIONS OF ROWS Needs a full server, indexes, complex queries
🗂️

SQLite

WRITABLE Only data the Trace Viewer creates
SINGLE FILE Lives on disk, needs no server process
FTS5 INDEX Built-in full-text search across all comments

Here is the SQLite schema for reviewer comments — from infrastructure/sqlite.ts:

CODE 

CREATE TABLE IF NOT EXISTS comments (
  id              TEXT    NOT NULL,
  conversation_id TEXT    NOT NULL,
  user_email      TEXT    NOT NULL,
  user_name       TEXT    NOT NULL,
  content         TEXT    NOT NULL,
  created_at      TEXT    NOT NULL,
  PRIMARY KEY (id)
);
PLAIN ENGLISH

Create this table if it does not already exist — safe to run on every server startup.

id: a unique identifier for this comment (like a serial number on a receipt).

conversation_id: which conversation this comment belongs to — a link back to PostgreSQL.

user_email: who wrote the comment — the identity key for the commenter.

user_name: their display name for the UI.

content: the actual comment text — what gets searched by the FTS index.

created_at: timestamp stored as text in ISO 8601 format (e.g. "2025-05-13T14:30:00Z").

PRIMARY KEY means id must be unique — the database refuses duplicate comment IDs.

The search engine built inside the filing cabinet

The Trace List keyword search finds conversations whose reviewer notes contain the search term — instantly, across thousands of comments. The mechanism is FTS5: a full-text search engine built into SQLite itself.

CODE 

CREATE VIRTUAL TABLE IF NOT EXISTS
  comments_fts USING fts5(
    content,
    tokenize = 'unicode61 remove_diacritics 1'
  )
PLAIN ENGLISH

Create a special virtual table (only if it does not already exist).

Name it "comments_fts" — it mirrors the content of the comments table as a search index.

We want to search the "content" field — the comment text.

"unicode61" handles international characters correctly. "remove_diacritics 1" means "cafe" and "café" match — the accent mark is ignored. This makes the search feel forgiving and natural.

📖
The book-index metaphor

Without an index, finding "reconciliation" in 100,000 comments means reading all 100,000. With FTS5, the database pre-builds a word list — like the index at the back of a textbook. You look up "reconciliation," it tells you exactly which comments contain it, done. This is why keyword search feels instant even on large datasets.

The keyword search that crosses two databases

The most architecturally interesting feature: when you type a keyword in the Trace List, the app searches two completely separate databases and merges the results. From services/trace-service.ts:

CODE 

const titleRows = await prisma.aiConversation.findMany({
  where: { title: { contains: kw, mode: "insensitive" } },
  select: { id: true },
});

const noteIds = commentsService.searchConversationIds(kw);

const keywordIds = [
  ...new Set([...titleRows.map(r => r.id), ...noteIds]),
];
PLAIN ENGLISH

Search PostgreSQL: ask Prisma to find conversations whose title contains the keyword.

"contains" = anywhere in the string. "insensitive" = upper/lowercase does not matter.

Only return the conversation IDs — we just need the list, not the full records.

End of the PostgreSQL search.

Search SQLite separately: use the FTS5 index to find conversation IDs whose comments contain the keyword. This is the cross-database join that the application code handles manually.

Now merge both result lists into one.

new Set() removes duplicates — a conversation that matched both a title search AND a notes search would otherwise appear twice. This is a union of the two result sets.

Why your comment appears instantly — optimistic updates

When you post a comment, it appears in the Notes panel before the server has confirmed it was saved. This is an optimistic update. From features/notes/components/NotesPanel.tsx:

CODE 

const optimistic: Comment = {
  id: `temp-${Date.now()}`,
  content: draft.trim(),
  // ...other fields
};
setComments(prev => [...prev, optimistic]);
setDraft("");

const saved = await postComment(...);
setComments(prev =>
  prev.map(c => c.id === optimistic.id ? saved : c)
);
PLAIN ENGLISH

Create a fake "optimistic" comment object right now, before saving to the server.

Give it a temporary ID using the current timestamp — just needs to be unique for now.

Use the text the reviewer typed as the content.

End of the fake comment.

Add the fake comment to the displayed list immediately — the reviewer sees it appear right now.

Clear the input field — the reviewer knows their message was captured.

Now actually send the comment to the server (this takes ~100ms over the network).

When the server confirms success, swap the temporary fake comment for the real one (with a permanent database ID). Visually, nothing changes — it just becomes permanent. On failure, the rollback code removes the optimistic entry.

The closing loop: how a new note clears the cache

After a comment is saved, something important happens that was easy to miss. The server-side action that saves the comment also calls revalidateTag — the on-demand cache-clearing mechanism first mentioned in Module 3.

Here is why this matters:

1
Reviewer Alice posts a note on conversation #abc

The Server Action postComment writes the comment to SQLite.

2
The Server Action calls revalidateTag("trace")

This tells Next.js: "Throw away every cached trace result right now." The in-memory store for all conversation traces is wiped.

3
Reviewer Bob opens conversation #abc 10 seconds later

The cache is empty — no stored result. Next.js re-fetches from PostgreSQL and SQLite. The fresh data includes the note count Alice just added.

4
The fresh result is cached again

And the 2-minute clock resets. The two mechanisms work together: tags for instant invalidation, time-based expiry for normal freshness.

🔄
Tags + time = a complete cache strategy

Without tags, you would wait up to 2 minutes for a new note to appear. Without time-based expiry, you would need a revalidateTag call after every conceivable data change. Together they cover both cases: known changes (tags for immediate clearing) and unknown drift (automatic expiry for everything else). This two-pronged pattern scales to any size of app.

How the app remembers who you are — without a login

The Notes panel asks for your name and email the first time — and never asks again. There is no login system. Instead, a custom React hook called useIdentity stores your details in localStorage:

🔍

On startup

useIdentity reads name + email from localStorage. If found, the comment input shows immediately — no prompt.

💾

On save()

Writes name + email to localStorage. Future sessions on this browser remember you automatically.

🗑️

On clear()

Removes identity from localStorage. Useful if someone else uses your machine or you need to switch accounts.

⚖️
The tradeoff: simplicity vs. security

localStorage is fast to build and fine for an internal team tool. But anyone who sits at your computer can post as you. For a public-facing tool, replace this with a proper authentication system. Knowing this tradeoff lets you make the right call consciously when building similar features.">
