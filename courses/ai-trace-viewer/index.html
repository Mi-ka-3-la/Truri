Avise is an AI assistant for accountants — it helps them reconcile accounts, generate journal entries, and run reports. Every conversation a real user has with it gets recorded. The AI Trace Viewer lets the team look inside those recordings: find errors, spot patterns, and leave notes for each other.

✈️
Think: airplane black box

After every flight, investigators can replay every instrument reading and every system event. The Trace Viewer does the same for AI conversations — full replay, message by message, with every tool call and every error recorded.

What a "trace" actually looks like in code

The server assembles all the data for one conversation into a FullTrace object before sending it to the browser. Here is its shape, directly from types/index.ts:

CODE 

interface FullTrace {
  conversationId: string;
  title: string | null;
  user: {
    id: string;
    fullName: string;
    email: string;
  };
  messages: TraceMessage[];
}
PLAIN ENGLISH

An interface is a contract — it defines exactly what fields a FullTrace must contain.

Every conversation has a unique ID — like a receipt number.

The title is optional — conversations might never get named (hence "or null").

A nested object holding everything about the person who had this conversation...

...their internal user ID,

...their display name,

...and their email address.

A list (array) of every message in the conversation, in order — user, assistant, and tool messages all mixed together.

End of the contract.

💡
Interfaces are checkable promises

A TypeScript interface is a promise the compiler enforces. Any function that says it returns a FullTrace will fail to build if it omits any of these fields. This catches bugs before they ever reach the browser.

The cache: how it stores and how it forgets

Here is the actual code that sets up caching — from services/trace-service.ts:

CODE 

const getTrace = unstable_cache(
  getTraceUncached,
  ["trace-detail"],
  {
    revalidate: CACHE_SECONDS.traces,
    tags: ["trace"],
  }
);
PLAIN ENGLISH

Create a cached version of the function that fetches a conversation.

Wrap the real function that does the database work.

Give this cache a name so Next.js can identify it.

Settings:

Automatically expire the cached result after 120 seconds — then fetch fresh data.

Tag this cache entry "trace" — this is how we can clear it on demand (see below).

That tags: ["trace"] is not just a label — it is a handle. When a reviewer posts a new comment, the notes feature calls revalidateTag("trace") — which tells Next.js: delete every cached result tagged "trace" right now. The next person to open that conversation gets fresh data from the database, including the new comment in the note count.

🏷️
Cache tags: the on/off switch

Automatic expiry (120 seconds) covers the normal case — data gradually goes stale. Tags cover the exceptional case — you know right now that specific data has changed. Together they give you both passive freshness and active invalidation. This two-pronged approach is used in production apps everywhere.

Two queries in one: messages and their artifacts

The function that does the real work is getTraceUncached. After fetching the conversation and messages, it does a second pass to collect any AI-produced artifacts:

CODE 

const artifactIds = conversation.messages.flatMap(message =>
  extractArtifactIds(message.metadata as ...),
);

if (artifactIds.length > 0) {
  const rows = await prisma.$queryRaw<...>`
    SELECT id, status, started_at, stopped_at, operation_data
    FROM   operations
    WHERE  id = ANY(${artifactIds}) AND
           operation_type = 'AIArtifact'
  `;
}
PLAIN ENGLISH

flatMap goes through every message and extracts the artifact IDs mentioned in its metadata — then merges all those ID lists into a single flat list.

Each message stores artifact references in its metadata field — a JSON blob that contains extra context about what the AI was doing.

Only run the next query if there are actually artifact IDs to look up — no point hitting the database with an empty list.

Ask Prisma to run raw SQL — useful when Prisma's standard API is not expressive enough for a specific query.

Fetch only the columns needed (status, timing, data).

From the operations table — a shared table that stores all kinds of operations, not just AI artifacts.

ANY(artifactIds) is a PostgreSQL shorthand: it matches any row whose ID appears in the list. More efficient than a long OR chain.

Filter to only AIArtifact rows — ignoring unrelated operation types in the same table.

The code that fires all 13 at once

The mechanism is a single JavaScript construct: Promise.all. From services/dashboard-service.ts:

CODE 

const [
  totalRow,
  activeUsersRow,
  avgRow,
  // ... 10 more ...
] = await Promise.all([
  prisma.$queryRaw`SELECT COUNT(ac.id)...`,
  prisma.$queryRaw`SELECT COUNT(DISTINCT ac.user_id)...`,
  prisma.$queryRaw`SELECT AVG(sub.cnt)...`,
  // ... 10 more queries ...
]);
PLAIN ENGLISH

Declare 13 named variables to hold the results — one per query.

Result 1 will hold the total conversation count.

Result 2 will hold the active user count.

Result 3 will hold the average message count. And so on.

Promise.all starts ALL 13 queries at the same time. We wait (await) until every single one has returned.

First query: COUNT all rows in ai_conversations.

Second query runs simultaneously: COUNT DISTINCT user_ids (no double-counting users).

Third query runs simultaneously: AVG of a sub-query that counts messages per conversation.

All 13 run in parallel. Total wait = the slowest single query, not the sum of all 13.

⚡
Serial vs. parallel: the numbers

If each query takes ~60ms and you run them in sequence: 13 × 60ms = 780ms. Run them in parallel with Promise.all: ~60ms total (the time of the single slowest query). This is the single highest-impact optimisation in data-heavy apps. When you notice a page loading slowly, "are these fetches running in parallel?" is always one of the first questions to ask.

The context health query: a two-stage SQL detective story

One of the most sophisticated queries is Context Health — it classifies each conversation by how close it came to hitting the AI context window limit. It uses a SQL pattern called a CTE (WITH clause):

CODE 

WITH peak AS (
  SELECT ac.id,
    MAX(...'inputTokens'...) AS peak_tokens
  FROM ai_conversations ac ...
  GROUP BY ac.id
)
SELECT
  CASE
    WHEN peak_tokens <  50000  THEN 'Healthy'
    WHEN peak_tokens < 100000  THEN 'Watch'
    ELSE                            'At Risk'
  END AS zone,
  COUNT(*)::int AS count
FROM peak GROUP BY zone
PLAIN ENGLISH

Step 1 — define a named intermediate result called "peak"...

For each conversation,

...find the single highest token count across all its messages (MAX = the biggest number in the group).

Join the conversations and messages tables to get token data.

One result row per conversation.

End of Step 1. "peak" now behaves like a temporary table.

Step 2 — classify each row in "peak" with a label...

CASE is SQL for if/else.

Under 50k tokens: the conversation used less than half the typical AI limit — safe.

50k–100k: getting close — worth watching.

Over 100k: at the limit — the AI may already be losing context.

Assign each conversation to its zone.

Count how many conversations fall into each zone. GROUP BY zone gives one result row per zone.

The performance tuning knob — one file controls everything

All cache durations live in a single config file, services/cache-config.ts:

CODE 

const CACHE_SECONDS = {
  dashboard: 120,
  errors: 120,
  notes: 120,
  referenceData: 900,
  traces: 120,
} as const;
PLAIN ENGLISH

A lookup object — think of it as a settings panel for how long each type of data stays cached.

Dashboard charts expire after 2 minutes (120 seconds).

Error data also refreshes every 2 minutes.

Notes counters refresh every 2 minutes so new comments appear quickly.

Reference data (org/company dropdowns) is cached for 15 minutes — it almost never changes.

Individual conversation traces also expire after 2 minutes.

"as const" tells TypeScript these numbers are compile-time constants — they cannot be reassigned accidentally at runtime.

🎚️
One file, one dial

If the dashboard feels stale, you lower dashboard: 120 to 30. If reference data is expensive to rebuild, you raise it to 3600. Centralising this config is a deliberate design choice — it makes performance tuning a one-line change instead of a codebase search. When you build similar apps, consider having a single cache config file from the start.

Notes, Search & Clever Tricks

Two databases, instant feedback, cache invalidation on demand, and a search engine built into the filing cabinet.

Why two databases? Because they solve different problems.

🏛️

PostgreSQL

READ ONLY Trace Viewer never writes here
PRODUCTION DATA Came from the live Avise platform
MILLIONS OF ROWS Needs a full server, indexes, complex queries
🗂️

SQLite

WRITABLE Only data the Trace Viewer creates
SINGLE FILE Lives on disk, needs no server process
FTS5 INDEX Built-in full-text search across all comments

Here is the SQLite schema for reviewer comments — from infrastructure/sqlite.ts:

CODE 

CREATE TABLE IF NOT EXISTS comments (
  id              TEXT    NOT NULL,
  conversation_id TEXT    NOT NULL,
  user_email      TEXT    NOT NULL,
  user_name       TEXT    NOT NULL,
  content         TEXT    NOT NULL,
  created_at      TEXT    NOT NULL,
  PRIMARY KEY (id)
);
PLAIN ENGLISH

Create this table if it does not already exist — safe to run on every server startup.

id: a unique identifier for this comment (like a serial number on a receipt).

conversation_id: which conversation this comment belongs to — a link back to PostgreSQL.

user_email: who wrote the comment — the identity key for the commenter.

user_name: their display name for the UI.

content: the actual comment text — what gets searched by the FTS index.

created_at: timestamp stored as text in ISO 8601 format (e.g. "2025-05-13T14:30:00Z").

PRIMARY KEY means id must be unique — the database refuses duplicate comment IDs.

The search engine built inside the filing cabinet

The Trace List keyword search finds conversations whose reviewer notes contain the search term — instantly, across thousands of comments. The mechanism is FTS5: a full-text search engine built into SQLite itself.

CODE 

CREATE VIRTUAL TABLE IF NOT EXISTS
  comments_fts USING fts5(
    content,
    tokenize = 'unicode61 remove_diacritics 1'
  )
PLAIN ENGLISH

Create a special virtual table (only if it does not already exist).

Name it "comments_fts" — it mirrors the content of the comments table as a search index.

We want to search the "content" field — the comment text.

"unicode61" handles international characters correctly. "remove_diacritics 1" means "cafe" and "café" match — the accent mark is ignored. This makes the search feel forgiving and natural.

📖
The book-index metaphor

Without an index, finding "reconciliation" in 100,000 comments means reading all 100,000. With FTS5, the database pre-builds a word list — like the index at the back of a textbook. You look up "reconciliation," it tells you exactly which comments contain it, done. This is why keyword search feels instant even on large datasets.

The keyword search that crosses two databases

The most architecturally interesting feature: when you type a keyword in the Trace List, the app searches two completely separate databases and merges the results. From services/trace-service.ts:

CODE 

const titleRows = await prisma.aiConversation.findMany({
  where: { title: { contains: kw, mode: "insensitive" } },
  select: { id: true },
});

const noteIds = commentsService.searchConversationIds(kw);

const keywordIds = [
  ...new Set([...titleRows.map(r => r.id), ...noteIds]),
];
PLAIN ENGLISH

Search PostgreSQL: ask Prisma to find conversations whose title contains the keyword.

"contains" = anywhere in the string. "insensitive" = upper/lowercase does not matter.

Only return the conversation IDs — we just need the list, not the full records.

End of the PostgreSQL search.

Search SQLite separately: use the FTS5 index to find conversation IDs whose comments contain the keyword. This is the cross-database join that the application code handles manually.

Now merge both result lists into one.

new Set() removes duplicates — a conversation that matched both a title search AND a notes search would otherwise appear twice. This is a union of the two result sets.

Why your comment appears instantly — optimistic updates

When you post a comment, it appears in the Notes panel before the server has confirmed it was saved. This is an optimistic update. From features/notes/components/NotesPanel.tsx:

CODE 

const optimistic: Comment = {
  id: `temp-${Date.now()}`,
  content: draft.trim(),
  // ...other fields
};
setComments(prev => [...prev, optimistic]);
setDraft("");

const saved = await postComment(...);
setComments(prev =>
  prev.map(c => c.id === optimistic.id ? saved : c)
);
PLAIN ENGLISH

Create a fake "optimistic" comment object right now, before saving to the server.

Give it a temporary ID using the current timestamp — just needs to be unique for now.

Use the text the reviewer typed as the content.

End of the fake comment.

Add the fake comment to the displayed list immediately — the reviewer sees it appear right now.

Clear the input field — the reviewer knows their message was captured.

Now actually send the comment to the server (this takes ~100ms over the network).

When the server confirms success, swap the temporary fake comment for the real one (with a permanent database ID). Visually, nothing changes — it just becomes permanent. On failure, the rollback code removes the optimistic entry.

The closing loop: how a new note clears the cache

After a comment is saved, something important happens that was easy to miss. The server-side action that saves the comment also calls revalidateTag — the on-demand cache-clearing mechanism first mentioned in Module 3.

Here is why this matters:

1
Reviewer Alice posts a note on conversation #abc

The Server Action postComment writes the comment to SQLite.

2
The Server Action calls revalidateTag("trace")

This tells Next.js: "Throw away every cached trace result right now." The in-memory store for all conversation traces is wiped.

3
Reviewer Bob opens conversation #abc 10 seconds later

The cache is empty — no stored result. Next.js re-fetches from PostgreSQL and SQLite. The fresh data includes the note count Alice just added.

4
The fresh result is cached again

And the 2-minute clock resets. The two mechanisms work together: tags for instant invalidation, time-based expiry for normal freshness.

🔄
Tags + time = a complete cache strategy

Without tags, you would wait up to 2 minutes for a new note to appear. Without time-based expiry, you would need a revalidateTag call after every conceivable data change. Together they cover both cases: known changes (tags for immediate clearing) and unknown drift (automatic expiry for everything else). This two-pronged pattern scales to any size of app.

How the app remembers who you are — without a login

The Notes panel asks for your name and email the first time — and never asks again. There is no login system. Instead, a custom React hook called useIdentity stores your details in localStorage:

🔍

On startup

useIdentity reads name + email from localStorage. If found, the comment input shows immediately — no prompt.

💾

On save()

Writes name + email to localStorage. Future sessions on this browser remember you automatically.

🗑️

On clear()

Removes identity from localStorage. Useful if someone else uses your machine or you need to switch accounts.

⚖️
The tradeoff: simplicity vs. security

localStorage is fast to build and fine for an internal team tool. But anyone who sits at your computer can post as you. For a public-facing tool, replace this with a proper authentication system. Knowing this tradeoff lets you make the right call consciously when building similar features.">
