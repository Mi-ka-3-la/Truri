AI PDF parsing — how dates appear automatically

When an accountant uploads an invoice PDF, Avise does not make them read it and type the dates manually. The function below extracts the text from the PDF and asks Claude to find the term dates. Here is exactly what the code does, line by line.

CODE 

async function askGptToReadFileAndReturnTermMeta(
  companyId: string,
  fileBuffer: ArrayBufferLike,
): Promise<PreparedScheduleTermMeta> {

  const allTextJoined =
    await pdfParsing.getTextFromFileBuffer(
      fileBuffer
    );

  if (!allTextJoined.match(/.*[0-9]+.*/)) {
    return logAndHandleExpectedError(
      "PDF did not include any numbers."
    );
  }

  const gptResponse =
    await sendConversationMessagesToProvider({
      companyId,
      singleMessageString: allTextJoined,
      systemPrompt: `
        You are a CPA aiding entry to an ERP system.
        You will be provided the text of an invoice,
        and you will respond with the term start and
        end dates in MM/DD/YYYY format. Provide the
        dates delimited by a comma with the term start
        date first. Include no labels or other
        formatting.
      `,
      context: { action: "generateScheduleDates" },
    });

  return getDatesFromGptString(
    gptResponse.content
  );
}
PLAIN ENGLISH

This function takes two inputs: the company ID (for routing the AI call to the right provider config) and the raw bytes of the uploaded PDF file.

Extract all the readable text from the PDF parsing library. The result is a single long string — all the words and numbers from every page joined together.

Safety check: if the extracted text contains zero numbers, it cannot possibly contain a date. Return a graceful fallback error rather than sending useless text to the AI. The accountant will need to enter dates manually.

Send the entire PDF text to Claude (referred to as "gpt" in the variable name — a legacy of the codebase). The text is the user message; the system prompt tells Claude exactly what to do with it.

The system prompt is intentionally terse: act as a CPA, return only two dates in MM/DD/YYYY format separated by a comma, no labels, no other text.

Parse the response from the LLM using getDatesFromGptString. This parser checks for exactly one comma and exactly two date values. If Claude did not follow the format instructions, this returns an expected error and the accountant enters dates manually.

💡
Why such a terse system prompt?

The system prompt says "Include no labels or other formatting." This is intentional. Getting structured output from an LLM requires being extremely prescriptive. The parsing code (getDatesFromGptString) checks for exactly one comma and exactly two date values. If Claude deviates — even with a helpful "Start date: " prefix — the parse fails and the function returns a graceful failure. This is production-grade LLM usage: assume the model can get it wrong, and build a clean fallback for when it does.

Source lines — the financial paper trail

A source line answers the question: "where did this balance come from?" Follow the chain from invoice to zero.

1
Invoice arrives — accountant posts a journal entry to Accounts Payable

DR Prepaid Expense $12,000 / CR Accounts Payable $12,000. The credit line in this entry is a source line. It represents a real obligation the company has — they owe the vendor $12,000.

2
Accountant creates a schedule and links it to that source line

The schedule stores the source line's ID in its sourceLines array. This proves the schedule is backed by a real transaction. It is not a number entered out of thin air — it traces directly to the original invoice entry in the general ledger.

3
Each month, the schedule posts an entry that draws down the balance

DR Insurance Expense $1,000 / CR Prepaid Expense $1,000. This entry is recorded as a ScheduleLinkedTransaction. The Prepaid Expense balance falls from $12,000 toward zero over 12 months.

4
The Roll-Forward Report traces the full journey

Opening balance → monthly entries → closing balance. At the end of the term the balance reaches zero and every entry links back through the schedule to the original source line. An auditor can trace from the final $0 balance all the way back to the original invoice.

TYPE 

type ScheduleWithJournalEntriesAndFullSourceLines = {
  id: string;
  name: string;
  termStart: Date | null;
  termEnd: Date | null;
  dimensionValueId: string | null;
  companyId: string;
  scheduleLinkedTransactions:
    ScheduleLinkedTransaction[];
  sourceLines: FullSourceLine[];
  totalAmount: number | null;
};
PLAIN ENGLISH

This TypeScript type describes the full schedule object that the system loads when you open a schedule detail view. It combines the schedule record itself with all its linked data in one shape.

termStart and termEnd are nullable — they can be null if the accountant has not entered dates yet (or if PDF date extraction was needed but failed).

dimensionValueId is nullable — a schedule can exist without a dimension (no cost-centre tag), though that is uncommon in practice.

scheduleLinkedTransactions — the list of all journal entries this schedule has generated. Each element is a join record pointing to an actual JournalEntry (which may be scheduled, posted, or deleted).

sourceLines — the source lines attached to this schedule. Each is a ScheduleSourceLine joined with its journalLine — the raw accounting line from the original transaction.

totalAmount is the controlling total — the sum of all posted entries must eventually equal this number. It is nullable only while the schedule is still being set up.

The Roll-Forward Report — balance movement over time

The Roll-Forward Report takes all journal entries generated by schedules, groups them by period, and shows three numbers for each period. Here is what it looks like for a $12,000 prepaid insurance schedule.

Period Opening Balance Entries Posted Closing Balance
Jan 2024 $12,000 ($1,000) $11,000
Feb 2024 $11,000 ($1,000) $10,000
Mar 2024 $10,000 ($1,000) $9,000
… Apr – Nov follow the same pattern, $1,000 each month …
Dec 2024 $1,000 ($1,000) $0 ✓
Opening Balance
What was on the books

The balance in the account at the start of the period — i.e. what the previous period's closing balance was.

Entries Posted
What changed

The net total of all journal entries posted by schedules in this period. Shown in parentheses to indicate a reduction of the asset balance.

Closing Balance
What remains

Opening balance plus entries posted. When this reaches $0 the schedule has fully amortised — no balance remains on the books.

📌
Why auditors love this report

Roll-forward reports are a standard accounting deliverable. They prove that a balance sheet account moved in the way it should have, entry by entry. This report is what turns a pile of journal entries into a coherent story about how a prepaid asset or deferred revenue balance changed over time. Without the Roll-Forward Report, you have journal entries — but no story.
