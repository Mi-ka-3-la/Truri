All or nothing

If any journal entry fails to create (step 4), the API immediately rolls back by deleting all the entries that did succeed, then throws an error. The user sees a clear message and no partial schedule is left behind in the database. This is an atomic safety guarantee.

Stamping entries with standard metadata

Before journal entries are sent to the database, the function transformEntriesForSchedule runs over every entry in the list and adds a standard set of fields. Here is the exact code from avise-api/src/preparedSchedules/helpers.ts:

CODE 

return entries.map((entry) => ({
  ...entry,
  status: forCreation
    ? JournalEntryStatus.Scheduled
    : entry.status === JournalEntryStatus.Quarantined
      ? JournalEntryStatus.Scheduled
      : entry.status || JournalEntryStatus.Scheduled,
  entryType: JournalEntry.Data.KnownEntryType.JournalEntry,
  platform: Platform.Avise,
  updatedBy: userId,
  description: HARDCODED_SCHEDULE_JE_DESCRIPTION,
  ...(forCreation && { createdBy: userId }),
}));
PLAIN ENGLISH

Go through every entry in the list and return a new version with extra fields added.

Keep all the original fields from the entry (spread operator).

Now decide the status. If this is a brand-new schedule (forCreation = true)...

...always use Scheduled status regardless of what was in the AI proposal.

For updates: if the entry was Quarantined (blocked from posting)...

...promote it back to Scheduled so it can be posted again.

Otherwise keep the entry’s existing status, or fall back to Scheduled if it had none.

Mark the entry type as a standard journal entry.

Record which platform created this entry -- Avise (not QuickBooks or another external source).

Record who last updated this entry (the user who clicked Accept).

Use the standard hardcoded description for all schedule journal entries.

For new schedules only: also record who created the entry (the user who clicked Accept).

The orchestration function, line by line

Everything in the pipeline flows through one function: createPreparedScheduleAndAssociatedJournalEntries in avise-api/src/preparedSchedules/crud.ts. Here is the core of it translated into plain English:

CODE 

const company = await companiesData.get(companyId);

await validatePreparedSchedule(
  company, entries, dimensionId, dimensionValueId
);

const transformedEntries = transformEntriesForSchedule(
  entries, userId, { forCreation: true }
);

const { success: newlyCreatedEntries, failure: failedEntries } =
  await v2JournalEntriesService.createEntriesEndpoint(
    company.id, Platform.Avise, transformedEntries
  );

if (failedEntries.length) {
  await cleanUpAfterCreationFailure(...);
  throw new DataConflictError(...);
}

const preparedSchedule = await preparedSchedulesData.create(
  name, company.id, { ... }
);

await preparedSchedulesData
  .linkJournalEntriesToPreparedScheduleOrNoopIfUpdate(
    ids, preparedSchedule.id
  );

if (artifactId) {
  await trackArtifactAcceptance({ ... });
}

return retrievePreparedSchedule(
  companyId, preparedSchedule.id
);
PLAIN ENGLISH

Load the company record from the database -- needed for validation rules specific to this company.

Run validation: are the accounts valid? Do the dimensions exist? Do the entries balance? If anything fails, stop here and throw an error.

Stamp every entry with Avise-standard metadata: status=Scheduled, platform=Avise, createdBy=userId.

Try to create all journal entries in one batch call. The result splits into two lists: the ones that succeeded and the ones that failed.

If any entry failed: delete all the ones that did succeed (cleanup), then throw a DataConflictError so the user knows what went wrong. No partial schedule is left behind.

Create the PreparedSchedule parent record in the database -- the container that groups all the entries together and holds the schedule name, dates, and dimension.

Link each journal entry ID to this schedule via the join table (ScheduleLinkedTransaction). This is a no-op on updates -- it only adds new links.

If this schedule came from an AI proposal: record that the user accepted it. This links the artifact ID to the new schedule ID for analytics.

Return the fully assembled schedule -- the parent record plus all its journal entries and source transactions.

Why a join table?

A join table exists when one thing is related to many of another thing. A schedule has many journal entries, and each journal entry belongs to one schedule. The join table (ScheduleLinkedTransaction) holds just two IDs: the schedule ID and the journal entry ID. This lets the database answer two questions efficiently: “Give me all entries for schedule X” and “Which schedule does entry Y belong to?”

Large schedules: background creation via Argo

When a schedule has a large number of entries, creating them inside a single HTTP request risks a timeout. Instead, the API hands off the work to an Argo workflow — a background job. Here is that code from avise-api/src/preparedSchedules/createScheduleAndNotifyUser.ts:

CODE 

async function argoCreateScheduleAndNotifyUser(
  args: CreateScheduleArgs
): Promise<void> {
  await submitArgoWorkflow({
    workflowName: "create-schedule",
    parameters: {
      scheduleParams: parameters,
    },
  });
}
PLAIN ENGLISH

Define a function that kicks off background creation for large schedules.

Submit a job to the Argo workflow engine.

Tell Argo which workflow to run: the one named “create-schedule.”

Pass all the schedule data as parameters so Argo has everything it needs to do the work.

This function returns immediately -- the HTTP request completes and the user gets a response. Argo does the heavy lifting asynchronously in the background. When it finishes, the user is notified.
