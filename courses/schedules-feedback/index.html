What Schedules Does

The happy path — from “I have a lease expense” to a fully-posted journal entry that repeats itself every month.

Schedules automate repeating journal entries

Prepared Schedule

A container that holds a recurring expense — like rent, insurance, or a software subscription — with all its entries pre-planned.

Journal Entries

Each month inside the schedule is one journal entry. Avise creates them all upfront in Scheduled status, then accepts them when periods open.

Source Transactions

The real transaction that started the expense — e.g., the invoice line. Linking it tells Avise where this schedule came from.

Think: a standing order at your bank

You set it up once — amount, account, frequency. The bank executes it monthly without you touching it. Schedules do the same for journal entries in your general ledger.

Three places to find Schedules in the UI

Prepared Schedules List

The main list view at /schedules/prepared-schedules. Shows all schedules as rows in a rollforward table — columns for each month, Additions / Scheduled / Ending Balance.

Single Schedule View (PreparedSchedulePage)

Click a schedule name to see its entries, source transactions, files, and entry-by-entry status. This is the detail page for one Prepared Schedule.

Rollforward Report

A pivot view grouped by dimension value — shows how all schedules roll forward over time within a dimension like Department or Vendor.

The export button lives on the Prepared Schedules list

An Excel (XLSX) file is generated when you click Export. It sends the same query params as the list view — same date range, same filters — to the backend’s report endpoint.

Meet the Actors

Six files do most of the work. Once you know which is which, you can tell engineering exactly where to look.

The six-file cast at a glance

Each of the six feedback themes maps to one or more of these files. By the time you finish this course you will be able to read a client complaint and immediately point to the node above that needs to change.

The tech stack, layer by layer

React Frontend (avise-web)

TypeScript + React. The PreparedSchedulesPage, SchedulePage, and CreateSchedulePageV2 folders. Uses TanStack Query for data fetching and React Hook Form for the create/edit flows.

Express API (avise-api)

Node.js + Express. The preparedSchedulesController handles REST endpoints. The preparedSchedules/ service folder owns business logic — create, update, delete, list. Feature flags (Split) gate async creation and multi-line schedules.

Prisma ORM (avise-domains)

TypeScript ORM over PostgreSQL. Three models drive the whole feature: PreparedSchedule, ScheduleLinkedTransaction, and ScheduleSourceLine. The data/ layer in avise-api wraps Prisma queries.

PostgreSQL

All schedule data lives here. Journal entries are in the journal_entries table; the schedule models are in prepared_schedules, schedule_linked_transactions, and schedule_source_lines.

Knock (Notifications)

When schedule creation finishes (async or sync), a Knock workflow fires to notify the user. Two workflows: prepared-schedules-create (success/failure variants).

Feature flags gate two major behaviors

The async-argo-schedule-creation flag makes creation run in the background via an Argo workflow (Kubernetes job). The schedules-multi-line flag enables the multi-line schedule editor. Both default to off — check with engineering whether they are on for a given client.

How the actors talk when you create a schedule

Frontend

User clicked ‘Save & Post’. Sending POST /v1/companies/abc/schedules with entries, name, termStart, termEnd, and source line IDs.

Controller

Request received. Validating query schema with Joi. Passing to crud.createPreparedScheduleAndAssociatedJournalEntries().

Service

Validating that all accounts are Balance Sheet type. Calling v2JournalEntriesService.createEntries — status = Scheduled for each entry.

Database

Created 1 row in prepared_schedules. Created 12 rows in schedule_linked_transactions (one per monthly entry). Created source line links in schedule_source_lines.

Argo

(if async-argo-schedule-creation flag is ON) Argo workflow kicked off in background. Controller already returned 201 to the frontend.

Knock

Schedule creation finished. Sending Knock notification to the user: ‘Your schedule is ready!’

The Data Model

Three tables. Everything else in Schedules is either querying them or joining to them.

Three tables, one schedule

Before reading any query, look at the schema. Every confusion about how schedules work — especially Theme D’s status mystery — makes sense once you see how the tables relate.

dimensionValueId is the ONLY dimension on a schedule

A PreparedSchedule can only be tagged with one DimensionValue — for example Vendor = ‘Acme Corp’. This single FK is why Theme A’s multi-dimension filter request is architecturally non-trivial: the schema itself only supports one dimension per schedule.

How the backend loads a schedule with its entries

When you open a single schedule page, this function in crud.ts runs. It fetches the schedule, then queries all source lines separately.

avise-api/src/preparedSchedules/crud.ts — retrievePreparedSchedule
1 Fetch the PreparedSchedule row 
async function retrievePreparedSchedule(
  companyId: string,
  preparedScheduleId: string,
) {
  const preparedSchedule = await preparedSchedulesData
    .getOrThrow(companyId, preparedScheduleId);

The data layer fetches the PreparedSchedule row including its scheduleLinkedTransactions (with full JournalEntry includes) and sourceLines (with journalLine). If not found, it throws a 404-style error.

2 Load source lines in a separate query 
  const trxQuery = await journalLines.queryJournalLines(
    companyId,
    {
      ids: preparedSchedule.sourceLines.map(
        (sl) => sl.journalLineId
      ),
      includeFileInfo: true,
      order: "asc",
    },
  );

Source transactions are loaded in a SEPARATE query. The IDs come from the ScheduleSourceLine join table. This two-step fetch (schedule first, then source lines) is the root of the “bouncing” bug (Theme E) — every time source IDs change in the form, this query refires.

3 Merge and return the combined shape 
  return {
    ...preparedSchedule,
    sourceLines: trxQuery.results,
    files: allFiles,
  };
}

The final return merges the schedule data with the freshly-fetched source lines. The shape returned is ScheduleWithJournalEntriesAndSourceTransactions.

Two separate queries, not one JOIN

The schedule and its source transactions are fetched in two round-trips to the database. This is a deliberate design choice (source lines need full journal line details including file info) but it means performance is O(schedule) + O(sourceLines) — relevant context for Theme E.

A journal entry’s journey through a schedule

1
Entry created as Scheduled

The default status assigned in helpers.ts when a schedule is saved. The entry exists in the database but has NOT hit the general ledger yet.

2
Period opens → entry becomes Posted

When an admin opens the period, all Scheduled entries for that period are bulk-accepted and become Posted. They are now in the general ledger.

3
Period soft-closed or hard-closed

No change to the entry status. Posted entries stay Posted.

4
Admin archives an entry → status becomes Deleted

The entry becomes Deleted in the database. But if it was already Posted in a previous period, archiving does not un-post it.

5
(Theme D) Period becomes inactive after acceptance

If the period is set to inactive AFTER entries were accepted, the entries remain Posted but the schedule view may still show them as ‘pending’ because the UI filters by Scheduled status, not by period status.

Scheduled ≠ Pending — but the UI conflates them

Users see a ‘pending’ label on the schedule page for entries that haven’t been accepted yet (status = Scheduled). If a period becomes inactive after acceptance, the entry is Posted — but users comparing the ‘pending’ count to the schedule row get confused. This is Theme D.

6 User Feedback Themes

Every client complaint about Schedules falls into one of these six buckets. Know the buckets, and you can triage any new ticket in under 30 seconds.

Six themes, ranked by severity

These themes were distilled from 10 Shortcut stories across multiple clients. Each pattern card shows the severity, the number of clients affected, and the one-sentence summary.

A — List View Too Rigid

LOW–MEDIUM · 4 stories · 3+ clients. The Prepared Schedules list is missing columns (Vendor, Debit Account) and can only filter by one dimension at a time.

B — Export Omits Dimensions

MEDIUM · 1 story · 3 clients. The XLSX export doesn’t include dimension data (e.g., Vendor) even when the dimension is visible in the UI.

C — Manual Journal Numbering

HIGH · 1 story · 1 client (Flueid). Users have to type ‘Description 2’, ‘Description 3’ manually. The system should auto-increment.

D — Entry Status Confusion

CHORE · 1 story · 1 client (J Cummins). Archiving an already-posted entry in an inactive period still shows the entry as ‘pending’ on the schedule.

E — Source Transactions Broken

HIGHEST · 2 stories · 2+ clients. The source transaction section flashes, bounces, and reloads when creating a schedule — especially for large clients.

F — Duplicate Companies

HIGHEST · 1 story · 1 client (Finstrat). Duplicate company records surfaced while viewing Leasehold Improvement schedules. Fixed manually with SQL — root cause unresolved.

Theme A — The list view doesn’t behave like a real data table

“It would be helpful to have a Vendor column on the Prepared Schedules screen without having to put the vendor name in the schedule name itself.”

Story #7410 — also reported independently by Jones. The workaround of embedding the vendor in the schedule name is fragile and hard to search.

Today
  • One dimension filter at a time
  • No Vendor column
  • No Debit Account column
  • No way to hide inactive schedules
What Users Want
  • Filter by multiple dimensions simultaneously (Vendor + Class + Account)
  • Persistent Vendor column
  • Persistent Debit Account column
  • Toggle to hide inactive schedules
Story 7410 Fixed Vendor column (Bleecker + Jones)
Story 7396 Debit Account column (Cellino)
Story 7397 Multi-dimension filter (Cellino)
Story 7411 Hide inactive schedules (Newlab)

Theme B — The export and the UI are out of sync

“The Vendor dimension is visible in Avise but when I export the Schedules report, Vendor is not in the file.”

Story #7398 — also reported by Bleecker and Jones. Three independent clients hit this.

The XLSX export only includes a ‘Dimension Value’ column when the dimensionName query param is passed to the report API. If the user never applied a dimension filter — or applied it inside the UI but it wasn’t reflected in the export request — the column is absent. Even when it IS included, all dimension values are collapsed into one comma-joined string, not separate columns.

Theme C — Journal entry names don’t auto-increment

“When adding a new entry to a schedule, if the first JE description is Description 1, the next should auto-suggest Description 2.”

Story #7742 — HIGH priority. The only HIGH-severity feature request in the backlog.

Currently, helpers.ts applies a single HARDCODED_SCHEDULE_JE_DESCRIPTION string to EVERY entry — it doesn’t use the user’s description at all for the entry’s internal description field. The JE name (used as display text) is a separate input field, and the user must type each one manually. Auto-increment would require the create/edit form to detect the pattern and pre-fill the next entry’s name field.

Theme D — The ‘pending’ label survives when it shouldn’t

This is a UX symptom of the underlying state model. The schedule page shows entries as ‘pending’ if their journal entry status is Scheduled. But when a period was opened and then made inactive, the entry is actually Posted — and archiving it doesn’t un-post it.

Active period — archive works as expected

1
Entry has status = Scheduled (not yet accepted)
2
User archives the entry
3
Entry status → Deleted. Schedule shows one fewer pending entry.

Inactive period — the confusing case

1
Entry had status = Scheduled, then period was opened → status = Posted
2
Period is later set to inactive
3
User archives the entry in the schedule view
4
Entry becomes Deleted, but it was ALREADY Posted. Schedule may still show it as ‘pending’ because the UI counts Scheduled entries, not period status.
Story #7763 — J Cummins

The user reasonably assumed that archiving the entry would make the schedule ‘clean.’ The UI never explained that the entry had already been accepted in a previously-open period. This is a CHORE: the fix is adding contextual messaging, not changing data logic.

Theme E — Source transaction section reloads on every keystroke

HIGHEST priority — affects Bleecker and Mission Driven (2+ clients)

Story #7769: ‘The source transaction section keeps reloading and bouncing up and down on the page when creating a schedule for a larger client.’ Story #7747 (internal): ‘Fetching your data glitches and flashes.’

The root cause: EditPreparedScheduleDetailsPage.tsx watches sourceIds via watch('sourceIds') from React Hook Form. Every time source IDs change — including on initial render — it triggers useJournalLinesByIdQuery with the new IDs. For clients with many transactions, this query is expensive and fires repeatedly. The keepPreviousData option helps but doesn’t prevent the flashing loading state. This is a race condition between the form state and the data-fetching layer.

Theme F — Duplicate company records

HIGHEST priority — Finstrat reported duplicate ‘Rivet Industries’ company records (Story #7358)

Discovered while viewing Leasehold Improvement A/D schedules. Fixed by manual SQL deletion but the root cause — likely in company import or schedule-company linking — was never addressed. The support dashboard now has ArchiveDuplicates tooling, but that targets schedule entries, not companies.

For each of the six themes, here are the files that would change, the type of change, and an honest complexity estimate.

Six themes mapped to the codebase

Use this as a reference when triaging a support ticket or writing a Shortcut story. The change type tells you who owns it (frontend vs backend vs infra). The complexity tells you how to size the sprint task.

A — List View Frontend · Medium · usePreparedSchedulesPageFilterSet.ts + PreparedSchedulesTable.tsx + backend query schema
B — Export Backend · Small–Medium · preparedSchedulesReportService.ts + utils.ts + XLSX formatter
C — Auto-increment Full-stack · Medium · helpers.ts (backend) + CreateSchedulePageV2 form (frontend)

Themes A & B — List view and export fixes

A — List view columns and multi-dimension filter

Change type: UI polish + minor backend

1
usePreparedSchedulesPageFilterSet.ts

The dimension filter today is connectedSelectAndMulti — one dimension name at a time. Adding multi-dimension support requires changing this to a repeatable filter group. The backend query schema also only accepts a single dimensionName param.

2
PreparedSchedulesTable.tsx

Vendor and Debit Account columns don't exist. Adding them requires knowing the account linked to each schedule (not currently in the report row type). The PreparedScheduleRow type in data/types/preparedScheduleReport.ts needs new fields first.

3
preparedSchedulesReportService.ts + SQL

The "hide inactive schedules" toggle needs a backend filter. The SQL query in preparedScheduleReportData.ts would need a new optional includeInactive param and a corresponding WHERE clause.

B — Export includes dimension column

Change type: Backend bug fix · Small

avise-api/src/services/reports/schedules/shared/utils.ts — getFullColumnDefsFromReport()
1
const dimensionCols =
  reportIsPreparedSchedulesReport(report)
  && report.includeDimensionValueColumn
  ? [{ key: "dimensionValues",
       header: "Dimension Value" }]
  : [];

The dimension column is only added when includeDimensionValueColumn is true — which is only set when the caller passes a dimensionName query param. If the user exported without filtering by dimension, this is false.

2
// In preparedSchedulesReportService.ts:
includeDimensionValueColumn:
  Boolean(validQuery.dimensionName)

The fix: always include dimensionValues in the XLSX if the schedule has a dimensionValueId — not just when a filter was applied. The report service should set includeDimensionValueColumn: true when any schedule in the result set has dimension data.

Theme C — Auto-increment journal entry names (HIGH priority)

Change type: New feature · Full-stack · Medium complexity

This is the only HIGH-priority feature in the Schedules backlog. Here is exactly where the logic would live.

avise-api/src/preparedSchedules/helpers.ts — transformEntriesForSchedule()
1
// TODAY — every entry gets the same hardcoded text
return entries.map((entry) => ({
  ...entry,
  description: HARDCODED_SCHEDULE_JE_DESCRIPTION,
}));

Every entry in every schedule gets the exact same description: "This entry is part of a Prepared Schedule. If you want to edit…". The user's own description input is not used here.

2
// PROPOSED — use user-provided name, incrementing per entry
return entries.map((entry, index) => ({
  ...entry,
  description: entry.name
    ? `${entry.name} ${index + 1}`
    : HARDCODED_SCHEDULE_JE_DESCRIPTION,
}));

If the user provided a base name, append the 1-based index. Fallback to the hardcoded text if no name was given. The frontend form would need a new "Base Name" field, and the create/edit form payload would pass it through.

Frontend changes needed

Add a "Base Name" input to CreateSchedulePageV2. The form should show a preview: "Description 1, Description 2, Description 3…"

Backend changes needed

Update transformEntriesForSchedule in helpers.ts to accept and apply the base name with index. Update the PreparedScheduleBody type in controllers/types/preparedSchedules.ts to include the optional field.

Themes D, E, F — Status UX, the reloading bug, and duplicates

D — Entry status messaging (CHORE · Small · Frontend only)

PreparedSchedulePage.tsx Add a tooltip or contextual message on entries that are Posted-in-inactive-period. No data model changes needed — the entry status is already correct.

E — Source transaction reloading (HIGHEST · Small–Medium · Frontend)

avise-web/src/pages/CompanyApp/SchedulesPages/EditPreparedScheduleDetailsPage/EditPreparedScheduleDetailsPage.tsx
1
// Line 166 — sourceIds re-derived on every render
const sourceIds = watch("sourceIds");

// Line 168 — query fires every time sourceIds changes
const query = useJournalLinesByIdQuery({
  companyId: company.id,
  ids: sourceIds,
  includeFileInfo: true,
}, { placeholderData: keepPreviousData });

watch("sourceIds") re-runs on every form render. Adding IDs (or removing them) triggers a new network request. For large clients the request is slow and the isFetching state causes the section to bounce.

2
// Proposed fix: debounce the IDs before passing to the query
const sourceIds = watch("sourceIds");
const debouncedSourceIds = useDebounce(sourceIds, 300);

A 300ms debounce means the query only fires after the user stops interacting for 300ms — eliminating rapid-fire refetches. Alternatively, move to a staleTime strategy so the previous data stays until the new fetch completes without flashing.

F — Duplicate companies (HIGHEST · Large · Needs investigation)

Root cause unknown — investigation required before estimating

The support tooling in supportUtils/preparedSchedules/archiveDuplicates.ts targets duplicate schedule entries — not duplicate companies. The company-level deduplication problem is separate and unresolved. An engineer needs to audit company creation/import to find where the duplicate originates before any fix can be sized.

The full prioritization picture

HIGHEST E — Fix source transaction reloading. Frontend debounce in EditPreparedScheduleDetailsPage.tsx. Ship fast — multi-client.
HIGHEST F — Investigate duplicate company root cause. Large unknown — needs engineering spike.
HIGH C — Auto-increment JE names. Medium full-stack change. helpers.ts + CreateSchedulePageV2 form.
MEDIUM B — Fix export dimension column. Small backend change. preparedSchedulesReportService.ts + utils.ts.
LOW–MED A — List view columns + multi-filter. Medium frontend + minor backend. Multiple files, multiple stories.
CHORE D — Add status context message. Small frontend change. PreparedSchedulePage.tsx only.
Severity and complexity don’t always align

Theme E (HIGHEST severity, source transaction bouncing) is actually a small-to-medium frontend fix. Theme F (also HIGHEST) is potentially a large investigation. A fast win can fix a critical client issue — always check complexity before assuming a high-severity issue is expensive to fix.
