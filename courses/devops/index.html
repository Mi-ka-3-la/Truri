The Monorepo

One repository. 24+ workspaces. A build system that knows exactly which packages to rebuild when you change one file.

What a monorepo actually is

One repo, many packages

Instead of separate Git repositories for the API, frontend, shared utilities, and sync service, everything lives in one repo. Each sub-folder is a workspace with its own build and test commands.

Shared code without publishing

Packages like avise-shared-utils and avise-domains can be imported directly by avise-api without publishing them to npm. Changes propagate instantly across the repo.

Think: a train yard, not individual trains

Each carriage (workspace) is self-contained and can be swapped independently. But they all run on the same track system (pnpm + Turborepo) and share the same maintenance depot (node_modules at the root).

The 12 key workspaces you need to know

avise-api

The main Express backend. Has its own Dockerfile, integration tests, and release pipeline. The biggest and most complex workspace.

avise-web

The React frontend. Deployed via AWS Amplify (not Kubernetes). Gets its own PR checks and prod deployment workflow.

avise-domains

The Prisma schema, migrations, and shared domain types. Every workspace that touches the database depends on this. Schema changes start here.

avise-shared-utils

Logger, config system, DataDog, feature flags, auth utilities — shared by avise-api, qbo-sync, and every other service that needs them.

qbo-sync

QuickBooks Online sync service. Its own Dockerfile, its own release pipeline, completely separate from avise-api.

avise-file-indexing

Indexes uploaded files for semantic search. Has its own Dockerfile and release pipeline.

operation-tracking

Tracks async operations (like Argo workflows) in a shared Drizzle+PostgreSQL layer. Used by avise-api for job tracking.

knock

Knock notification workflow definitions (email templates, in-app feeds). Deployed to Knock's platform, not Kubernetes.

Turborepo: the build system that prevents wasted work

Without Turborepo, running pnpm build would rebuild every workspace every time — even if only one file changed. Turborepo adds two things:

1
Dependency graph awareness

Turborepo knows that avise-api depends on avise-shared-utils, which depends on avise-domains. When you run pnpm turbo --filter avise-api build, it builds dependencies first, in the right order.

2
Remote caching

Build outputs are fingerprinted and cached. If the same inputs (source files + env vars) produce the same build, the cache is used instead of rebuilding. In CI, the remote cache runs at turbocache.avise-turbocache.svc.cluster.local — inside the Kubernetes cluster.

turbo.json — the task dependency graph
1
"remoteCache": {
  "apiUrl": "http://turbocache.avise-turbocache
            .svc.cluster.local"
},

The remote cache URL — an internal Kubernetes service. CI runners write and read from this cache. Local dev doesn’t connect here (different network), which is one of the architectural gaps.

2
"tasks": {
  "build": {
    "dependsOn": ["^build"]
  },

The ^build means “run build in all dependencies first.” When you build avise-api, Turborepo walks the dependency graph and builds avise-domains → avise-shared-utils → avise-api in that order.

3
  "check:format": {
    // No dependsOn: [] entry
    "env": []
  }

Tasks without dependsOn: ["^build"] don’t wait for dependencies. Format checking only looks at the workspace’s own files, so it can run immediately without waiting for upstream builds.

The CI/CD Pipeline

From a commit to a running container — two workflows, one for pull requests and one for releases, both driven by smart workspace detection.

The full pipeline map

graph LR
  A["git push\n(PR or main)"] --> B["detect-changes\nTurborepo --affected"]
  B --> C{Changed\nworkspace?}
  C -- "PR branch" --> D["workspace-pr-ci\nformat + lint + types + tests"]
  C -- "merge to main" --> E["workspace-release\nformat + lint + types + tests\n+ Docker build + ECR push"]
  E --> F["update-gitops-deployment\nKustomize image tag"]
  F --> G["Argo CD\npulls GitOps repo\ndeploys to K8s"]
  D --> H["Slack notification\nPR status"]
  E --> I["Slack notification\nDeploy ready DM"]
  A -- "avise-web" --> J["AWS Amplify\nbuild + deploy\n(separate pipeline)"]

Two separate GitHub Actions workflows handle the two events. Both start with the same smart workspace detection step.

Smart workspace detection — only test what changed

The first job in every workflow is detect-changes. It uses Turborepo’s --affected flag to figure out which workspaces are affected by the current commit — including transitive dependencies.

.github/workflows/pull-request.yml — detect-changes job
1
BASE_REF="${{ github.event.pull_request.base.sha }}"
affected_output=$(
  TURBO_SCM_BASE="$BASE_REF"
  pnpm turbo ls --affected --output=json
)

Turborepo compares the current commit to the PR base to find which workspaces have file changes. If you changed a file in avise-shared-utils, both avise-shared-utils AND all workspaces that depend on it (avise-api, qbo-sync, etc.) are included in the affected set.

2
if [[ -f ".github/actions/workspace/${workspace}/pr/action.yml" ]]; then
  has_action=true
else
  has_action=false
fi

Not every workspace has its own PR action — only ones with tests and build steps. The detection job records whether a workspace has an action file. The matrix job later only runs full CI for workspaces where both changed=true AND has_action=true.

3
matrix="[$(IFS=','; echo "${matrix_workspaces[*]}")]"
config="{\"workspaces\":{$(IFS=','; echo "${workspace_configs[*]}")}}"
echo "matrix=$matrix" >> $GITHUB_OUTPUT

The result is output as a JSON matrix. The next job uses strategy.matrix to spin up parallel runners — one per workspace. Unaffected workspaces get a “Skipping — no changes detected” log and exit immediately.

Secrets are fetched via OIDC — no stored credentials

Before running any workspace-specific step, the CI runner authenticates to AWS using OIDC and assumes IAM role github-actions-secrets-role. Then it pulls all secrets from monorepo/secrets in AWS Secrets Manager. No API keys live in GitHub Secrets.

The frontend — a separate pipeline via AWS Amplify

avise-web does NOT go through the release.yml workflow. It has its own Amplify-managed pipeline defined in amplify.yml:

amplify.yml — avise-web deployment
1
- env | grep -e REACT_APP_API_URL
       -e REACT_APP_AUTH0_CLIENT_ID
       -e REACT_APP_DATADOG_RUM_APP_ID
       -e REACT_APP_SPLIT_CLIENT_SIDE_KEY
       -e REACT_APP_KNOCK_API_KEY
  >> avise-web/.env.local

All environment variables are injected from Amplify’s environment at build time, written to a .env.local file. These include the DataDog RUM keys, Knock channel ID, Split.io client key, Auth0 config, and the API URL — all set per environment (dev vs prod) in the Amplify console.

2
- pnpm turbo --filter avise-web build

Turborepo builds avise-web — which first builds its dependencies (avise-shared-utils, etc.) because of the ^build dependency chain.

3
artifacts:
  baseDirectory: avise-web/build
  files:
    - "**/*"

Amplify takes the static build output and deploys it to its CDN. No Docker, no Kubernetes — it is a pure static site hosting setup. Amplify handles SSL, CDN distribution, and branch-based preview deployments automatically.

avise-web also has its own GitHub Actions PR workflow

.github/workflows/avise-web-test-lint-runner.yml and avise-web-prod-deployer.yml handle PR checks and prod triggers for the frontend specifically. The release.yml handles backend workspaces; Amplify + its own workflow handles the frontend.

Infrastructure

Kubernetes via GitOps and Argo CD, multi-stage Docker builds, AWS ECR, and the database migration story.

The GitOps deployment model

GitOps means the cluster’s desired state lives in a separate repo called AviseInc/gitops. Argo CD watches that repo and automatically applies any changes it finds.

What lives in the GitOps repo

Kubernetes Kustomize configs for every environment (dev, prod) and every app (avise-api, qbo-sync, etc.). Each app folder has a kustomization.yaml that specifies which Docker image tag to run.

What Argo CD does

Argo CD runs inside Kubernetes and polls the GitOps repo every few minutes. When it sees the image tag in kustomization.yaml change (committed by GitHub Actions), it applies the change to the cluster — replacing the old pod with the new one.

.github/actions/update-gitops-deployment/action.yml
1
- uses: actions/checkout@v4
  with:
    repository: AviseInc/gitops
    ref: main
    token: ${{ inputs.github-token }}
    path: ./.github/gitops

Check out the separate GitOps repository. This is a different repo from the monorepo — it only contains Kubernetes configs, no application code.

2
cd .github/gitops/apps/envs/${{ inputs.env }}/${{ inputs.app }}/
kustomize edit set image \
  ${{ inputs.ecr-registry }}/${{ inputs.app }}:${{ inputs.release }}

Navigate to the environment-specific folder (e.g. apps/envs/prod/avise-api/) and use kustomize to update the image tag in kustomization.yaml. The release version is the git commit SHA.

3
git commit -m "${{ inputs.release }} release of
${{ inputs.app }} for ${{ inputs.env }}
by ${{ inputs.author }}"

Commit the kustomization change and push. Argo CD sees this commit within minutes and begins the rolling deployment. Both dev AND prod get updated in the same release action run.

The Docker build — Turborepo pruning in action

The avise-api/Dockerfile uses a multi-stage build that leverages Turborepo’s turbo prune command to create a minimal image containing only what avise-api needs:

1
Stage: pruner

turbo prune --scope=avise-api --docker analyzes the workspace dependency graph and outputs two things: out/json/ (just package.json files for all dependencies) and out/full/ (all source files needed). Only the files avise-api actually needs — no unrelated workspaces.

2
Stage: install-generate

pnpm install --frozen-lockfile using the pruned package.json files. This creates a Docker layer that only invalidates when actual dependencies change — not on every code change. Prisma types and allspice types are also generated here.

3
Stage: builder

pnpm turbo build compiles TypeScript to JavaScript in all workspaces. All build outputs are then tarred into build.tar — capturing the dist/ and lib/ folders from each workspace.

4
Stage: runner (final image)

A minimal Debian slim base. Only copies node_modules and the build.tar output from the builder stage. The entrypoint is dumb-init node avise-api/lib/src/app.js. Runs as the node user (not root) for security.

Each Docker stage is its own layer cache

If you only change TypeScript source files, the install-generate stage cache is still valid. Docker skips re-running pnpm install and jumps straight to the builder. This is why the Dockerfile separates install from build — it makes rebuilds faster.

Database migrations — the schema change lifecycle

1
Create the migration files

pnpm turbo --filter avise-domains create-migration <name> generates two SQL files in avise-domains/migrations/sqls/: *-up.sql (apply the change) and *-down.sql (undo it). The engineer writes the actual SQL DDL statements in these files.

2
Update the Prisma schema

After writing the SQL migration, update avise-domains/prisma/schema.prisma to reflect the new table/column. This is the TypeScript-level representation — it generates the Prisma client types used by avise-api.

3
Integration tests validate the migration

In CI, integration tests spin up a fresh PostgreSQL container, apply all migrations via db-migrate, and run the test suite against the migrated schema. This ensures migrations are valid before any code reaches production.

4
Deployment runs migrations automatically

The avise-api container runs migrations as part of startup (before the Express server begins accepting traffic). This means schema changes are always applied before the code that uses them becomes active.

Config, Secrets & Feature Flags

How 50+ environment variables are validated, how AWS Secrets Manager replaces GitHub Secrets, how Split.io gates features, and the facet pattern for multi-role services.

The config system — Joi validation per concern

Every config value is validated by Joi before the application starts. Config is split into domain-specific modules — one per external concern:

appConfigBasic app settings: NODE_ENV, port, frontend base URL, facet identifier.
emailConfigSES_DOMAIN, SKIP_EMAIL_SEND flag. Defaults to dev.avise.ai domain for dev.
knockConfigKNOCK_SECRET_KEY, KNOCK_SIGNING_KEY for Knock notification webhooks.
aiConfigOpenAI API key, model settings, MCP server configs, tool limits.
featureFlagsConfigSPLIT_API_KEY for Split.io SDK initialization.
datadogConfigDD_API_KEY, DD_VERSION, DD_ENV for DataDog APM and tracing.
prismaConfig / drizzleConfigDATABASE_URL, connection pool settings for PostgreSQL.
redisConfigRedis connection URL for BullMQ job queues.
awsConfigAWS region, S3 bucket name, SES settings.
authorizationConfigSpiceDB (Authzed) endpoint and credentials for the authorization service.
argoWorkflowConfigArgo Workflow server URL for submitting async jobs.
operationTrackingConfigS3 bucket for operation event storage.
Fail-fast in production, warn-and-continue in local dev

If a required config value is missing in production, the app crashes immediately with a clear error. In local dev, invalid config logs a yellow warning and continues — so developers can run the app without configuring every external service.

The facet pattern — one process, three roles

avise-api can run in three different facets using the same Docker image:

main

The REST API server. Handles HTTP requests from the frontend and external services. This is the default when AVISE_FACET is unset. Strict config validation — missing required env vars crash immediately.

bullmq

Background job processor for BullMQ queues. Runs tasks like email sending, task review checks, and file processing. Does not listen on a port.

workflow

Executes Argo Workflow scripts — long-running async jobs like bulk period open or schedule creation. Spun up by Argo as a Kubernetes pod, runs to completion, then terminates.

One image, many roles — a classic ops pattern

Rather than building three separate Docker images, the facet pattern reuses one image. Kubernetes runs different instances with different AVISE_FACET values. This keeps Docker build time and ECR storage low, and ensures all roles always run the same code version.

Feature flags — Split.io controls everything at runtime

Avise uses Split.io for feature flags on both backend and frontend. Flags are evaluated per-request, per-organization — no redeploy needed to change behavior.

A
API Startup

Initializing Split.io SDK with SPLIT_API_KEY. Connecting to Split.io servers asynchronously. The app continues starting up while SDK initializes.

C
Feature Flag Code

Request comes in. Calling FeatureFlagsClient.flagEnabledForOrganization('ai-complex-schedules', organizationId).

S
Split.io SDK

Looking up ai-complex-schedules for organization org-abc. Rule: ON for organizations in the early-access list. Result: on.

C
Feature Flag Code

Flag is ON. Including proposeMultiLineSchedule tool in the AI tool registry. If flag were OFF: tool would be deleted from availableTools before the conversation starts.

F
React Frontend

Frontend evaluates the same flag client-side via REACT_APP_SPLIT_CLIENT_SIDE_KEY. Shows or hides UI elements based on the flag value — no server round-trip needed for UI gating.

Observability & External Services

DataDog for traces and RUM, Knock for notifications, QBO Sync for accounting data, Redis for job queues, SpiceDB for authorization, and MCP servers for AI tooling.

DataDog — traces, RUM, and source maps

APM Traces

The backend initializes dd-trace at startup (before any imports). Every HTTP request, database query, and external API call is traced automatically. Logs use facet tags to distinguish REST API, BullMQ, and workflow roles.

RUM

RUM is initialized in the React frontend using REACT_APP_DATADOG_RUM_APP_ID and REACT_APP_DATADOG_RUM_CLIENT_TOKEN. Frontend errors and performance data are correlated with backend traces.

Source Maps

The Amplify build uploads source maps to DataDog using DATADOG_SOURCE_MAP_UPLOAD_API_KEY. This lets DataDog translate minified production JavaScript errors back to the original TypeScript source code in error reports.

avise-shared-utils/src/logger/index.ts — Winston + DataDog JSON format
1
const logFormat =
  process.env["NODE_ENV"] === "production"
    ? winston.format.json()
    : winston.format.combine(
        winston.format.simple(),
        colorWinstonWithChalk,
      );

In production, logs output as JSON — DataDog can parse and index each field. In local dev, logs are colored terminal-friendly text. Same log calls, different output format.

2
const logger = winston.createLogger({
  level: process.env["LOG_LEVEL"] || "info",
  defaultMeta: process.env["AVISE_FACET"]
    ? { facet: process.env["AVISE_FACET"] }
    : undefined,
});

Every log line automatically includes a facet field from the environment. In DataDog, you can filter to facet:bullmq to see only background job logs, or facet:main for API logs. The log format follows [module:subModule] message [companyId:entityId].

External services map

Knock — in-app and email notifications

Knock handles all user-facing notifications: period status updates, AI chat summary, task review alerts, scheduled entry failures. Workflow templates live in the knock/ workspace (YAML definitions). The backend calls triggerNotification(workflowId, { recipients, data }) from avise-api/src/notifications/.

QBO Sync — QuickBooks Online integration

A separate workspace (qbo-sync) with its own Dockerfile and release pipeline. Runs as a separate Kubernetes service. Syncs journal entries, accounts, dimensions, and vendors from QuickBooks to Avise. Triggered by webhooks from QuickBooks or by periodic polling.

Redis + BullMQ — background job queues

BullMQ queues are used for email sending, task auto-review, and other async work. The bullmq facet of avise-api connects to Redis and processes these queues. Redis connection is configured via REDIS_URL.

SpiceDB (Authzed) — fine-grained authorization

All authorization checks go through SpiceDB. The schema is defined in avise-api/authorization-schema-test.yaml and validated in CI via authzed/action-spicedb-validate. API endpoints call companyAuthorization.checkAnyCompanyPermission() before processing requests.

Argo Workflows — long-running async jobs

Complex multi-step processes (bulk period open, schedule creation) are submitted as Argo Workflow jobs. The REST API triggers an Argo job and returns immediately. The workflow facet of avise-api executes the actual work steps as Kubernetes pods, tracked via the operation-tracking workspace.

AWS S3 — file storage

All user-uploaded files and AI-processed documents are stored in S3. Presigned URLs give the frontend temporary direct-upload access. File metadata (key, filename, content type) is stored in the PostgreSQL files table. The avise-file-indexing workspace processes files from S3 for semantic search.

MCP Servers — AI tool extension

External tools for the AI Chat are connected via the Model Context Protocol. MCP servers are configured via MCP_SERVERS env var (JSON). At startup, McpServerAdapter.initializeMcpServers() connects to each server and registers its tools. Supports stdio, SSE, streamable-HTTP, and WebSocket transports.

Gaps & Architectural Improvements

Seven honest gaps in the current DevOps setup — and concrete proposals for each one.

Seven architectural gaps

No staging environment Code goes: PR → dev → prod. There is no staging environment that mirrors production. Bugs that only appear under production-like data or load are found in prod.
No automated rollback If a deploy to prod breaks things, there is no automated rollback mechanism. Engineers must manually revert the GitOps commit and wait for Argo CD to redeploy the previous image.
Remote cache not available locally The Turborepo remote cache (turbocache.avise-turbocache.svc.cluster.local) is only accessible from inside Kubernetes. Local dev gets no cache benefit — every workspace rebuilds from scratch.
Frontend and backend have different deploy pipelines avise-web deploys via AWS Amplify while backend services go through GitHub Actions → ECR → GitOps → Argo CD. Two separate systems means two failure surfaces, two sets of env var management, and hard-to-coordinate deploys.
Single region — no disaster recovery Everything runs in us-east-2 (Ohio). AWS outage in that region takes down the entire product. No multi-region failover or even a documented RTO/RPO.
No canary or blue/green deployments Deployments are rolling updates — Kubernetes replaces pods one by one. There is no canary traffic splitting (e.g., route 5% of traffic to the new version first) or blue/green switch.
No centralized secret rotation Secrets in AWS Secrets Manager are static. If a key is rotated, all services must be redeployed to pick up the new value. There is no automatic secret rotation or live reload mechanism.

Proposed improvements

1. Add a staging environment

What: A third environment between dev and prod in the GitOps repo (apps/envs/staging/). Same Kustomize structure, production-scale data, separate secrets.
How: The release workflow adds a staging deploy step before prod. Prod deploy only happens after staging passes automated smoke tests.
Impact: Catches production-only bugs before real users see them.

2. Automated rollback on failed health checks

What: Configure Argo CD to automatically roll back to the previous image tag if the new deployment fails its readiness/liveness probe within N minutes.
How: Argo CD Rollouts plugin or Kubernetes native rollback policy. The GitOps commit includes the previous image tag as a rollback reference.
Impact: Reduces mean time to recovery (MTTR) from hours to minutes for bad deploys.

3. Expose Turbo remote cache to local dev

What: Use Turborepo’s token-based remote cache API via an HTTPS endpoint exposed outside the cluster (or via VPN).
How: Configure TURBO_TOKEN and TURBO_TEAM env vars locally. Or switch to Turborepo’s managed hosted cache (turbo.build).
Impact: Local developers benefit from CI build cache — avise-api build drops from minutes to seconds on cache hit.

4. Unify frontend and backend deploy pipelines

What: Move avise-web out of Amplify and into Kubernetes (e.g., nginx container or Next.js standalone mode) or at minimum into the same GitOps/Argo CD system.
How: Add avise-web to the release.yml workflow, build a Docker image, push to ECR, deploy via GitOps like the backend.
Impact: One deployment system to understand, one env var management story, coordinated backend+frontend deploys.

5. Canary deployments for avise-api

What: Route a small percentage of traffic (5-10%) to the new pod before completing the full rollout.
How: Argo Rollouts (already in the cluster) with a canary strategy. Define success metrics (error rate, latency) in the Rollout spec — Argo automatically promotes or aborts.
Impact: Bad deploys affect a small fraction of users before auto-abort, not everyone simultaneously.

6. Automatic secret rotation

What: Use AWS Secrets Manager rotation policies + Kubernetes External Secrets Operator to automatically reload secrets into pods without redeployment.
How: Install External Secrets Operator in the cluster. Define ExternalSecret resources in the GitOps repo. When a secret rotates in AWS, Kubernetes automatically gets the new value.
Impact: Zero-downtime secret rotation. Reduces the blast radius of a compromised key.

Priority matrix

P0 Automated rollback — reduces MTTR from hours to minutes. Argo Rollouts is already in the cluster; this is configuration, not new infrastructure.
P0 Staging environment — required before enterprise client growth. Prod bugs become much more expensive at scale.
P1 Canary deployments — high impact on deploy safety. Argo Rollouts config change, no new services.
P1 Turbo remote cache for local dev — high dev velocity impact. Requires VPN/auth setup or switching to turbo.build hosted cache.
P2 Unified deploy pipeline — valuable long term. Requires evaluating whether K8s-hosted frontend fits the team’s operational model.
P3 Secret rotation + multi-region — important for enterprise compliance but requires significant infra investment.
The fastest wins are configuration changes, not new infrastructure

Automated rollback (Argo Rollouts config) and canary deployments (Rollout strategy YAML) both leverage existing infrastructure. They require days of work, not months — and they directly reduce the blast radius of every future deploy.
