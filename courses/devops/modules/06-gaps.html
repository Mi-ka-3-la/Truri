Gaps & Architectural Improvements

Seven honest gaps in the current DevOps setup — and concrete proposals for each one.

Seven architectural gaps

No staging environment Code goes: PR → dev → prod. There is no staging environment that mirrors production. Bugs that only appear under production-like data or load are found in prod.
No automated rollback If a deploy to prod breaks things, there is no automated rollback mechanism. Engineers must manually revert the GitOps commit and wait for Argo CD to redeploy the previous image.
Remote cache not available locally The Turborepo remote cache (turbocache.avise-turbocache.svc.cluster.local) is only accessible from inside Kubernetes. Local dev gets no cache benefit — every workspace rebuilds from scratch.
Frontend and backend have different deploy pipelines avise-web deploys via AWS Amplify while backend services go through GitHub Actions → ECR → GitOps → Argo CD. Two separate systems means two failure surfaces, two sets of env var management, and hard-to-coordinate deploys.
Single region — no disaster recovery Everything runs in us-east-2 (Ohio). AWS outage in that region takes down the entire product. No multi-region failover or even a documented RTO/RPO.
No canary or blue/green deployments Deployments are rolling updates — Kubernetes replaces pods one by one. There is no canary traffic splitting (e.g., route 5% of traffic to the new version first) or blue/green switch.
No centralized secret rotation Secrets in AWS Secrets Manager are static. If a key is rotated, all services must be redeployed to pick up the new value. There is no automatic secret rotation or live reload mechanism.

Proposed improvements

1. Add a staging environment

What: A third environment between dev and prod in the GitOps repo (apps/envs/staging/). Same Kustomize structure, production-scale data, separate secrets.
How: The release workflow adds a staging deploy step before prod. Prod deploy only happens after staging passes automated smoke tests.
Impact: Catches production-only bugs before real users see them.

2. Automated rollback on failed health checks

What: Configure Argo CD to automatically roll back to the previous image tag if the new deployment fails its readiness/liveness probe within N minutes.
How: Argo CD Rollouts plugin or Kubernetes native rollback policy. The GitOps commit includes the previous image tag as a rollback reference.
Impact: Reduces mean time to recovery (MTTR) from hours to minutes for bad deploys.

3. Expose Turbo remote cache to local dev

What: Use Turborepo’s token-based remote cache API via an HTTPS endpoint exposed outside the cluster (or via VPN).
How: Configure TURBO_TOKEN and TURBO_TEAM env vars locally. Or switch to Turborepo’s managed hosted cache (turbo.build).
Impact: Local developers benefit from CI build cache — avise-api build drops from minutes to seconds on cache hit.

4. Unify frontend and backend deploy pipelines

What: Move avise-web out of Amplify and into Kubernetes (e.g., nginx container or Next.js standalone mode) or at minimum into the same GitOps/Argo CD system.
How: Add avise-web to the release.yml workflow, build a Docker image, push to ECR, deploy via GitOps like the backend.
Impact: One deployment system to understand, one env var management story, coordinated backend+frontend deploys.

5. Canary deployments for avise-api

What: Route a small percentage of traffic (5-10%) to the new pod before completing the full rollout.
How: Argo Rollouts (already in the cluster) with a canary strategy. Define success metrics (error rate, latency) in the Rollout spec — Argo automatically promotes or aborts.
Impact: Bad deploys affect a small fraction of users before auto-abort, not everyone simultaneously.

6. Automatic secret rotation

What: Use AWS Secrets Manager rotation policies + Kubernetes External Secrets Operator to automatically reload secrets into pods without redeployment.
How: Install External Secrets Operator in the cluster. Define ExternalSecret resources in the GitOps repo. When a secret rotates in AWS, Kubernetes automatically gets the new value.
Impact: Zero-downtime secret rotation. Reduces the blast radius of a compromised key.

Priority matrix

P0 Automated rollback — reduces MTTR from hours to minutes. Argo Rollouts is already in the cluster; this is configuration, not new infrastructure.
P0 Staging environment — required before enterprise client growth. Prod bugs become much more expensive at scale.
P1 Canary deployments — high impact on deploy safety. Argo Rollouts config change, no new services.
P1 Turbo remote cache for local dev — high dev velocity impact. Requires VPN/auth setup or switching to turbo.build hosted cache.
P2 Unified deploy pipeline — valuable long term. Requires evaluating whether K8s-hosted frontend fits the team’s operational model.
P3 Secret rotation + multi-region — important for enterprise compliance but requires significant infra investment.
The fastest wins are configuration changes, not new infrastructure

Automated rollback (Argo Rollouts config) and canary deployments (Rollout strategy YAML) both leverage existing infrastructure. They require days of work, not months — and they directly reduce the blast radius of every future deploy.
