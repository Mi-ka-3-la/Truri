Best practices & corrective measures

Domain 5 of GH-500 — 10% of the exam. The smallest domain by weight, but the questions are the easiest to lose points on through over-thinking. Triage workflows, security policies, advisories, and the audit log.

Triage: deciding what to fix first

Across all GHAS features (secrets, code scanning, Dependabot), alerts pile up. Domain 5 tests whether you can pick the most impactful work first instead of triaging by gut feel.

Signal Indicates Triage weight
CVSS score / Severity (critical / high) Potential impact if exploited High
EPSS / exploit availability Likelihood the vuln is being actively exploited High
Reachability / call-path analysis Whether vulnerable code is actually used in production paths High
Validity check passed (secret scanning) Token is still active — credential is live Very high — treat as breached
Alert age How long the alert has been open Medium — stale alerts may indicate process gaps
Production vs test paths Where the finding lives in the codebase Production high · test paths lower
Triage golden rule

Validity-confirmed active secrets are always priority one. An active AWS key in a public repo outranks a critical CodeQL finding in untested branch code. Treat confirmed live secrets as an active breach: rotate first, investigate after.

Security policies — SECURITY.md

A SECURITY.md file tells external researchers and contributors how to report vulnerabilities responsibly. The exam tests where it goes and what GitHub does with it.

Where the file lives

  • SECURITY.md at the repo root
  • OR docs/SECURITY.md
  • OR .github/SECURITY.md

Same lookup logic as CONTRIBUTING.md — first match wins.

What GitHub does with it

When a SECURITY.md exists, GitHub surfaces a "Security policy" link in the repository's Security tab and on the "Report a vulnerability" page. The file's content is rendered as the public report-handling guidance.

Default community at the org level

You can drop a SECURITY.md in the special .github repository of an organization. Any repo in that org without its own SECURITY.md inherits this default. The exam may test "where do you set a security policy for all org repos at once?" — the answer is the .github repo, not the org settings.

Private vulnerability reporting (PVR)

PVR is a feature that gives external researchers a private channel to report vulnerabilities directly inside GitHub, without disclosure in public issues.

1
Enable per repo

Path: Settings → Code security and analysis → Private vulnerability reporting → Enable. Once enabled, anyone with a GitHub account can submit a private report via the repo's Security tab → "Report a vulnerability" button.

2
Enable across an organization

Path: Org Settings → Code security and analysis → Private vulnerability reporting. You can enable it for all current repos, all new repos, or both. Available for free on both public and private repositories — no GHAS license required.

3
Triage workflow

Reports show up as draft security advisories in the repo's Security tab. Maintainers triage, discuss in a private collaboration space, request a CVE if needed, and publish the advisory once a fix is shipped.

Exam trap: "PVR requires GHAS"

False. Private vulnerability reporting is free for public and private repos alike. GHAS is not a prerequisite. The exam may bundle PVR with other paid features to mislead you.

Security advisories — coordinate, fix, then disclose

A security advisory is the formal record of a vulnerability in your project. The exam tests the lifecycle states and how CVEs interact with the workflow.

Once published, the advisory is searchable in the GitHub Advisory Database. Dependabot can then alert downstream consumers of your package.

Temporary private forks

Inside a draft advisory, maintainers can spin up a temporary private fork to develop the fix without exposing it publicly. When the advisory is published, the fix is merged to main from the private fork.

CVE Numbering Authority (CNA)

GitHub is an official CNA. From inside an advisory you can request a CVE ID without going to MITRE directly. The CVE is reserved during draft and assigned at publish time.

Access control and the security overview

Knowing who can see what is a Domain 5 staple. The exam tests both the default permissions and how to broaden them.

Who sees what — defaults
Role Secret scanning alerts Code scanning alerts Dependabot alerts
Repository admin Yes Yes Yes
Security manager (org role) Yes Yes Yes
Write access Not by default Yes Yes
Read access No No No

Security manager role

An org-level role designed for security teams: read access to all repos in the org PLUS read/write access to all security alerts. Granted at: Org Settings → Teams → [team] → Security manager. Up to 10 teams can be designated.

Security overview dashboard

Cross-repo dashboard at Org → Security tab. Shows enabled GHAS features, open alerts by repo and severity, and adoption trends. Filterable by team, repo, and feature. Requires GHAS for private repos.

Audit log — the record of who did what

The audit log captures security-relevant configuration changes. The exam tests where it lives, how long entries are retained, and which events are tracked.

Where it lives

  • Org-level: Org → Settings → Audit log
  • Enterprise-level: Enterprise → Audit log (aggregates all orgs)
  • Repo-level: no dedicated UI; events surface in the parent org's audit log

Retention

  • GitHub.com retains for at least 6 months; most queryable events go back further
  • Export to JSON or CSV for long-term archival
  • Stream to external SIEM via the Audit Log Streaming feature (Enterprise Cloud only)
Events the exam expects you to know are logged

Enabling/disabling Dependabot, code scanning, or secret scanning; dismissing security alerts; creating/publishing security advisories; changing branch protection rules; adding/removing security managers; modifying custom secret patterns. Not logged at user level: individual code scanning query runs — those live in the workflow run history, not the audit log.

Best-practice settings that show up across the exam

Domain 5 questions also touch general repo hygiene that supports GHAS. Internalize this checklist.

1
Branch protection on the default branch

Require pull request reviews (at least 1, ideally 2). Require status checks: CodeQL, Dependency Review. Require branches to be up to date before merging. Restrict who can push to the protected branch.

2
Required reviewers and CODEOWNERS

Use .github/CODEOWNERS to require specific teams to review changes in their areas (e.g., /security/ @org/security-team). Combine with "Require review from Code Owners" in branch protection.

3
Signed commits

Enable "Require signed commits" in branch protection. Combined with verified commit signatures (GPG, SSH, S/MIME), this prevents impersonation in the commit history.

4
Secret scanning push protection

Enable push protection at the org level so leaks are blocked at git push time, not after they land in history. Configure bypass rules for true emergencies but require justification.

5
Pin third-party Actions to SHAs

Reference third-party actions by full commit SHA, not floating tags (uses: actions/checkout@v4 is okay because GitHub maintains it; for third-party actions use the 40-char SHA). Mitigates supply-chain attacks via tag re-pointing.

Corrective measures — three playbooks the exam tests

Leaked secret playbook

  1. Treat as compromised — assume it's been used
  2. Rotate / revoke the credential at the provider
  3. Issue a new credential, update services
  4. Investigate access logs for misuse
  5. Close the secret scanning alert with a reason

Do NOT just delete the commit — git history still contains it.

Vulnerable dependency playbook

  1. Read the Dependabot alert and Advisory Database entry
  2. Check whether a Dependabot security update PR exists
  3. If yes, review and merge it
  4. If no fix exists, evaluate reachability — is the code path used?
  5. Mitigate (config, WAF, code change) or dismiss with reason

Code scanning finding playbook

  1. Open the alert in the Security tab — read the data-flow trace
  2. Confirm whether the path is reachable from untrusted input
  3. Apply the recommended fix or refactor
  4. If not exploitable, dismiss with False positive, Used in tests, or Won't fix
