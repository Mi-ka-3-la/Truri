Module 4 · Domain 2 deep dive

Configure & use secret scanning

Domain 2 of the GH-500 — 15% of the exam. Same weight as Domain 1, but more procedural: paths, settings, limits, lifecycles.

What secret scanning actually scans (more than just code)

The exam tests scope. Most candidates assume secret scanning looks only at source code files — and miss the wider net it casts.

All of git history, all branches

Not just the latest commit. Not just main. Every commit on every branch — historical content included. A secret leaked three years ago in a feature branch will still be detected.

Issues, PRs, and Discussions too

Titles, descriptions, comments — across open AND closed historical issues, pull requests, and GitHub Discussions. A secret pasted in a PR comment counts the same as one in code.

Why this matters for the exam

If a question says "a developer pasted an API key in a closed issue comment three months ago" — that's still in scope. Don't be fooled by "it was closed" or "it wasn't in the code." Issues and PRs are scanned the same way the codebase is.

Two distinct features — define them before the matrix

The next screens compare them across scopes, so anchor the difference now.

Secret scanning (the detector)

Runs after code arrives on GitHub. Looks at every commit, every branch, plus issues / PRs / discussions. Produces an alert when a pattern matches. The secret has already entered git history at this point — detection is a notification, not a block.

Push protection (the blocker)

Runs during git push. The push is intercepted server-side: if any new commit contains a detected secret, the push is rejected before the commit lands on GitHub. The secret never enters history at all. Bypass requires an explicit reason from the developer.

Both rely on the same partner-pattern library, but the timing is what differentiates them. Keep this distinction in mind for the next screens — the matrix lists them separately because they enable separately.

The single most-tested fact about secret scanning

This screen exists because one specific question appears on almost every GH-500 attempt. Read carefully.

Public repositories: secret scanning is on, and cannot be configured or turned off.

Read it again. Cannot. On a public repo, you don't enable secret scanning (it's already on by default), you don't disable it (you can't), you don't configure it (you can't either). The only way to change secret scanning behavior on a public repo is to switch it to a private repository with a GitHub Advanced Security license. Then — and only then — does configuration become possible.

Secret scanning configurability by scope
Capability Public repo Private repo (no GHAS) Private repo (with GHAS)
Secret scanning enabled? Default ON, automatic Not available Manual — must be enabled
Can you configure or disable it? No, not at all — Yes, fully
Push protection Default-on for users (partner patterns) Not available Configurable + custom patterns
Custom secret patterns No No Yes
Exam trap: the "admin permissions" distractor

A common wrong answer on public-repo questions is "get admin permissions on the repository." It's plausible-sounding but wrong. Admin permissions don't matter when the platform doesn't expose the configuration at all. Switch-to-private-with-GHAS is the only real answer.

The exact menu paths the exam tests on

The GH-500 will ask "where do you do X?" — and the wrong answers will be other plausible menu locations. Memorize the paths.

1
Enable secret scanning (private repo with GHAS)

Navigate to Settings → Security → Advanced Security. Click Enable next to "Secret Protection" and confirm. Then separately click Enable next to "Push protection". They're enabled independently — enabling secret scanning does NOT auto-enable push protection.

2
Enable secret scanning across the organization

Set up GHAS at the organization level, then configure Global Secret Scanning settings in org settings. Repos in that org will then have secret scanning enabled by default (admins of those repos will see "Disable" instead of "Enable" in their repo settings — meaning it was inherited).

3
Configure granular settings (post-enable)

Once enabled, granular settings live at a different path: Settings → Code security and analysis → Secret Protection. This is where you toggle validity checks, non-provider patterns, AI-based generic password detection, push protection bypass rules, and alert dismissal rules.

4
Add custom alert recipients

Path: Settings → Security → Advanced Security → Access to Alerts. Type the person or team name, select from matches, save. This is the ONLY correct place — NOT in "Manage Access" (that's repo-wide permissions) and NOT in "Watch settings" (that's personal user preferences, not recipient configuration).

Exam trap: two similar paths, different purposes

Settings → Security → Advanced Security is for the INITIAL enable/disable plus alert recipients. Settings → Code security and analysis → Secret Protection is for granular post-enable settings (validity checks, custom patterns toggle, AI scanning, etc.). The exam may give you a wrong path as a distractor — confirm which path serves which purpose.

The numerical limits the exam will absolutely test

GH-500 is fond of "how many" questions where three of four options are plausible numbers. Know these cold.

Limit Value What happens if you exceed it
Custom patterns per private repository 100 You can't create more — the UI rejects creation
Custom patterns per organization or enterprise 500 Same — UI rejects further creation
Repositories selectable for org-level dry run 10 You pick up to 10, or use "All repositories in the organization"
Results shown in a dry run sample 1,000 Only the first 1,000 results are shown — actual matches may be more
Entries in paths-ignore 1,000 Only the FIRST 1,000 are honored; everything after is ignored (scanned anyway)
Size of secret_scanning.yml 1 MB The ENTIRE file is ignored. Not truncated — completely ignored, as if it didn't exist.
Exam trap: paths-ignore vs file-size limits

These two limits are commonly confused on the exam. If paths-ignore has 1,200 entries, the file is still honored — but only the first 1,000 paths are excluded. If the FILE is 1.3 MB, the entire file is ignored regardless of how many paths it lists. Different limits, different behaviors.

The red node — commit author — is highlighted because that notification is mandatory. Even if the author has disabled all repo notifications, they will be notified about a secret they committed. This is a frequent exam trap.

Who gets notified (the standard list)

  • Security managers
  • Repository administrators
  • Users with custom roles having read/write access
  • Org owners + enterprise owners (if they admin affected repos)
  • Additional users/teams configured under "Access to Alerts"

Plus the special case

Commit author is always notified, regardless of their notification preferences. This is hardcoded behavior — they cannot opt out. The intent: the person who committed the secret should know immediately, even if they have disabled all other notifications.

What actually happens when a secret leaks on a public repo

Public repos are the special case worth understanding mechanically. The same secret-scanning detector runs, but the downstream chain is different: GitHub doesn't just file an alert — it tells the partner that issued the credential, and the partner can act unilaterally to neutralize it. This is the public-repo story the exam, and real incidents, both depend on.

Red nodes are the dangerous and the protective steps. Note the dual destination from Verify: confirmed-active credentials go through partner-side revocation; inactive matches still create a GitHub alert but no revocation happens.

Why partners act, not just GitHub

GitHub knows the token format, but only the partner can confirm "yes, this token is real, currently active, and belongs to customer X." Only the partner can revoke a credential they issued. The partner verification webhook is what makes this collaboration possible.

What the owner still has to do

Even when a partner auto-revokes, the owner must still: (1) rotate the underlying credential and update services that used it, (2) review provider-side access logs to assess misuse, (3) close the GitHub alert with a reason. Partner revocation prevents new abuse — it doesn't undo abuse that already happened in the time window between leak and revocation.

Public vs private: who revokes

On public repos the partner is in the loop and may auto-revoke or quarantine. On private repos with GHAS, the same partner-pattern library is used and partners are still notified for matched partner tokens, but real-world partner revocation is most aggressive on public exposures (where the credential is presumed compromised by default). Either way, GitHub itself never revokes a third-party credential — it only files alerts and forwards matches.

Custom patterns: defining your organization's secrets

Beyond partner patterns (AWS, Stripe, etc.), you can define custom patterns for secrets internal to your organization — internal API tokens, license keys, anything with a recognizable shape.

At REPOSITORY level At ORGANIZATION level

About Hyperscan regex

Most developers know PCRE (Perl-Compatible Regular Expressions) or JavaScript regex. Hyperscan is similar but not identical — some advanced PCRE features (lookbehind assertions in particular) may not be supported. If the exam asks why a custom pattern doesn't match, "wrong regex engine syntax" is a plausible cause. Test with a sample test string before publishing.
