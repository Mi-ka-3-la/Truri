Module 5 · Domain 3 deep dive

Configure & use Dependabot and Dependency Review

Domain 3 of GH-500 — 35% of the exam. The single largest domain. Miss this and passing becomes mathematically very hard even with perfect scores elsewhere.

Five tools, one supply chain security story

The exam tests "which tool does X?" constantly on Domain 3. Before anything else, internalize this map.

The 5 supply chain security tools on GitHub
Tool What it does mechanically When it intervenes
Dependency graph Reads manifest and lock files; builds an inventory of all direct + transitive dependencies Passive, continuous — foundation for everything else
GitHub Advisory Database Curated database of known vulnerabilities (CVEs + GHSAs). Dependabot queries it. External — the source of truth for "what's vulnerable"
SBOM Formal export of the dependency inventory in SPDX format On demand — for audit and compliance
Dependabot Three sub-features: alerts, security updates, version updates Continuous — on existing dependencies in the repo
Dependency Review Checks the dependency changes in a PR diff before merge Pre-merge, on every pull request
The most frequently confused pair

Dependabot watches what's already in your repo, continuously, even after merge. Dependency Review watches what you're trying to ADD in a PR, before you merge. Same dependency focus, completely different timing. The exam will put both as adjacent answer options — the timing word in the question tells you which to pick: "before merge" → Dependency Review; "continuously" or "after it turned vulnerable" → Dependabot alerts.

The dependency graph — the foundation everything else builds on

Dependabot alerts can't work without it. Security updates can't work without it. It's the prerequisite, not optional.

What the graph contains

  • Direct dependencies — explicitly declared in your manifest or lock file
  • Indirect (transitive) dependencies — packages used by your packages
  • Dependents — repos that depend on yours (public repos only — NOT on private repos)

View at: Insights → Dependency graph → Dependencies or Dependents tab

Scope conditions

  • Public repos: auto-generated, always on
  • Private repos: available but must be manually enabled by an admin

Settings → Security → Advanced Security → Dependency graph → Enable

Exam trap: manifest only vs manifest + lock file

If a repo uses only a manifest file (e.g., package.json) without a lock file (e.g., no package-lock.json), the dependency graph is still generated — but indirect (transitive) dependencies are NOT included in vulnerability checks. You can miss Dependabot alerts on transitive deps entirely. Always use lock files for complete coverage.

GitHub Advisory Database and SBOM

GitHub Advisory Database

Open-source, curated by GitHub. Uses CVSS for severity: low / moderate / high / critical.

Sources: NVD, npm Security Advisories, community contributions, ML-assisted review of public commits.

Identifiers — know all four:
  • CVE ID — the specific vulnerability (global standard)
  • GHSA ID — GitHub's own advisory identifier
  • CWE ID — the weakness type (e.g., CWE-89 = SQL injection)
  • CVSS score — the numerical severity rating

SBOM (Software Bill of Materials)

A formal, machine-readable inventory of all dependencies. Format: SPDX — not CycloneDX, not JSON, not SARIF.

Export via: the Export SBOM button in the Dependency graph, or via the REST API.

Why it matters for compliance: Executive Order 14028 requires an SBOM for software sold to the US federal government. EO 14028 in a question → SBOM in SPDX format.

Dependabot's three sub-features — know which does what

Dependabot is an umbrella for three distinct capabilities. The exam asks about each individually and tests whether you confuse them with each other.

A
Dependabot alerts

Notifies you when a dependency in your repo appears in the GitHub Advisory Database as vulnerable.

Two triggers: (1) a new advisory is added for a package you already use, OR (2) your dependency graph changes and you added something already vulnerable.

Not on by default — must be enabled manually on both public AND private repos.

B
Dependabot security updates

Automatically opens pull requests to update vulnerable dependencies to a safe version. PR is authored by the dependabot bot, labeled dependencies, and includes a compatibility score.

Prerequisites (ALL must be true): dependency graph enabled AND Dependabot alerts enabled.

Auto-enables on new repos when: not a fork, not archived, public OR private with graph+alerts enabled, not explicitly disabled.

C
Dependabot version updates

Opens PRs to update dependencies to their newest versions — regardless of whether there's a vulnerability. Requires a .github/dependabot.yml file. Without this file, version updates simply don't run.

Fork trap: version updates are NOT auto-enabled on forks. To activate on a fork: Insights → Dependency graph → Dependabot → Create config file.

Exam trap: grouped security updates vs grouped version updates

The groups option in dependabot.yml applies only to version updates. To enable grouped security updates (bundling multiple security PRs into one), you must toggle a separate feature in Settings → Code security and analysis. The exam will show a YAML with groups and ask why security updates aren't being grouped — the answer is they need the separate UI toggle, not a YAML change.

Enabling Dependabot — paths at every level

The exam tests the exact UI paths for enabling Dependabot at repo, user, org, and enterprise level. Each level has a distinct path.

1
Repository level

Settings → Code security and analysis → Enable Dependency graph first, then enable Dependabot alerts. Order matters — graph must be on before alerts.

2
User level (across all your repos)

Profile → Settings → Code security and analysis → Enable all → optionally tick "Automatically enable for new repositories".

3
Organization level

Profile → Your organizations → [org] → Settings → Code security and analysis → Enable all → optionally tick "Automatically enable for new repositories".

4
Enterprise level

Profile → [enterprise] → Settings → Code security and analysis → Enable all.

Critical: Enterprise OVERRIDES org and repo. If enterprise disables Dependabot, no org or repo can re-enable it regardless of local settings. Only an enterprise owner can change this.

Who sees Dependabot alerts by default

Users with write, maintain, or admin access plus org owners. To grant access to others: Settings → Code security and analysis → Access to alerts → type name → Save.

The dependabot.yml file — structure and key fields

Version updates require a config file at .github/dependabot.yml. Without it, version updates don't run. The exam tests valid vs invalid YAML structure.

Minimum valid structure

Three required fields per entry: package-ecosystem, directory, schedule.interval. And always version: 2 at the top.

version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "daily"

Valid interval values: daily | weekly | monthly. The registries: key is optional and used for private registries with authentication.

Grouped version updates example

The groups option — applies to version updates only, not security updates.

version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "daily"
    groups:
      production-dependencies:
        dependency-type: "production"
      development-dependencies:
        dependency-type: "development"
Grouping rules the exam will test

Dependabot WILL group dependencies from different directories if they share the same ecosystem. Dependabot WILL NOT group across different ecosystems (npm + pip = separate PRs, always). Dependabot WILL NOT group security updates together with version updates — those are always separate PRs regardless of configuration.

Dependency Review — the pre-merge gate

Dependency Review runs on every pull request and inspects only the dependency changes in the PR diff. It can block the merge if vulnerabilities are detected — but only if configured as a required status check.

Dependabot alerts Dependency Review
When? Continuous — after a dep turns vulnerable (even retroactively) Pre-merge, on every PR — inspects only the PR diff
What? Existing dependencies already in the repo Only dependencies being added or changed in the PR
Can block merge? No — alerts only; developer decides Yes — if set as a required status check
Where? Security tab → Dependabot alerts PR checks + diff annotations on the PR itself
Private repos without GHAS Free for all repos Requires GHAS license
1
Setup via Marketplace (recommended method)

Repository → Actions tab → Search "dependency review" → Click Configure → Commit dependency-review.yml to .github/workflows/.

2
Key configuration options — memorize these

fail-on-severity: critical | high | moderate | low — the value is moderate, NOT medium. NOT severe. NOT important.

allow-licenses OR deny-licenses — mutually exclusive. Using both in the same workflow causes an error. If license is unknown → action informs but does NOT fail.

3
Enforce via branch protection rules

Settings → Branches → Add branch protection rule → enable "Require status checks to pass before merging" → enable "Require branches to be up to date before merging" → search and add dependency-review as a required check.

dependency-review.yml — example workflow

Place this at .github/workflows/dependency-review.yml

name: 'Dependency review'
on:
  pull_request:
    branches: [ "main" ]
permissions:
  contents: read
  pull-requests: write
jobs:
  dependency-review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with:
          comment-summary-in-pr: always
          fail-on-severity: high
          deny-licenses: GPL-1.0-or-later

This config fails on high/critical vulnerabilities and blocks GPL-licensed deps. Note: allow-licenses and deny-licenses cannot be used together — pick one.
