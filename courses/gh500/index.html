Module 1 · Foundation

What GHAS actually is

Three features, two products, one suite. The names are layered — let's untangle them before anything else.

GHAS in one breath: three features fighting three security risks

Secret scanning

Finds secrets that have ended up in source code. Targets the risk of credential exposure.

Domain 1 · Sub-skill: Describe secret scanning

Code scanning

Analyzes your code for security vulnerabilities and coding errors. Powered by CodeQL or any tool that emits SARIF.

Domain 1 · Sub-skill: Describe code scanning

Dependabot

Tracks the open-source packages your project depends on. Alerts you when one has a known vulnerability, and (optionally) opens pull requests to update them.

Domain 1 · Sub-skill: Describe Dependabot

These three are features, not products. They live inside a suite called GHAS. The exam tests both the umbrella name (GHAS) and the individual feature names — and the relationship between them.

Domain 1 coverage: 15% of GH-500

This module addresses the "Describe GHAS features and functionality" objective. By the end, you'll be able to tell apart each feature's purpose and explain how they fit together — which is what every Domain 1 question tests.

What each feature actually does, mechanically

The exam doesn't just ask "what does secret scanning detect?" — it asks scenarios. To recognize those scenarios, you need to know the mechanism, not just the name.

1
Secret scanning — the always-on watcher

GitHub maintains a library of patterns supplied by partner companies (AWS, Stripe, Slack, etc.). Every commit to a scanned repo is checked against these patterns. When a match is found, an alert is created and (for partner tokens) the partner is automatically notified so they can revoke it.

2
Code scanning — the static analyzer

You configure it via a workflow (typically using the CodeQL action) that runs on every push or pull request. The scanner reads your source code, applies a library of security queries, and emits a SARIF file. GitHub turns each finding into an alert with a severity, a vulnerability category (CWE-numbered), and a line-level pointer in the code.

3
Dependabot — the dependency watcher

It builds a dependency graph from your manifests (package.json, requirements.txt, etc.) and cross-references it against the GitHub Advisory Database. When a dependency becomes vulnerable (or was already vulnerable when you added it), Dependabot opens an alert and, if security updates are enabled, an automated pull request to bump the version.

The shape that helps you remember

Each feature watches a different layer of risk. Secret scanning watches what's in your code that shouldn't be there. Code scanning watches what your code does that could be exploited. Dependabot watches what your code depends on that someone else might have broken. Three layers, three watchers.

Why you'll see two names for the same thing

If you read material from before 2024, you'll see "GHAS" referenced as one product with three features. If you read newer material, you'll see "Secret Protection" and "Code Security" as separate products. Both are correct — the suite was unbundled.

Where each feature works (and where it doesn't)

Same feature, different repository, different behavior. The exam tests this constantly — it's the easiest place to lose points if you skim.

The availability matrix the exam tests every single time

Three columns, three real-world repository situations. The cells tell you exactly what's available in each. Read it slowly the first time — every cell can become an exam question.

GHAS feature availability by repository type

Code scanning (CodeQL) Free Not available Available
Dependabot alerts Free Free Free
Dependency graph Free, automatic Free (must be enabled) Free
Dependency Review (PR check) Free Not available Available
Exam trap: the middle column

"Private repository without a GHAS license" is the column the exam targets most. Most features are not available there — only Dependabot alerts and the dependency graph. If a question scenario says "private repo, no advanced security license", any answer involving secret scanning, code scanning, push protection, or Dependency Review is wrong. Those features simply don't exist in that scope.

Why public repos get so much for free

GitHub makes GHAS-class security features free on public repositories. Why? Two reasons matter for the exam: open source security has spillover effects (a vulnerability in a popular OSS library hurts every project that uses it), and visibility is already public (a secret leaked in a public repo is already a serious incident regardless of whether GitHub scans for it).

On public repos, by default

  • Secret scanning alerts: on automatically
  • Push protection for partner patterns: on by default since 2024
  • Dependency graph: on automatically
  • Dependabot alerts: on automatically
  • Code scanning (CodeQL): available but requires you to set up the workflow
  • Dependency Review: available on every PR

On private repos without GHAS

  • Secret scanning alerts: not available
  • Push protection: not available
  • Dependency graph: available but must be enabled (not on by default)
  • Dependabot alerts: available (free for everyone)
  • Code scanning: not available
  • Dependency Review: not available
The pattern to memorize

Public repos get almost everything for free. Private repos without a GHAS license get only Dependabot. Buying GHAS for a private repo brings it up to parity with public repos and adds custom secret patterns on top.

Two adjacent features the exam will absolutely test

Inside the Dependabot family there are two features that watch dependencies — but they intervene at different moments. Knowing which is which is one of the most common Domain 1 exam questions.

Dependabot alerts Dependency Review
When does it intervene? Continuously — after a dependency turns vulnerable (even if it was added long ago) On every pull request — before the merge happens
What does it scan? Existing dependencies declared in the repo's manifest files Only the dependencies being added or changed in the PR diff
Where does it surface? Security tab → Dependabot alerts PR check status + diff annotations on the PR itself
Can it block? No — it alerts; the developer decides what to do Yes — if configured as a required check, vulnerable dependencies block the merge
Free on private repos? Yes, for everyone No — requires GHAS
Exam trap: the verb tells you which one

Look for the timing word in the question. "Before merge" → Dependency Review. "Already in the repo" or "turned vulnerable" or "continuously monitors" → Dependabot alerts. The two will appear as adjacent answer options on at least one question — bet on it.

The "defense in depth" framing

If you're asked why GHAS uses multiple features instead of one big scanner, the answer is defense in depth. No single gate is perfect — push protection might be bypassed, code scanning might miss a new vulnerability class, dependencies might turn vulnerable after merge. Each feature is a layer; the layers cover each other's gaps.

Where you find each feature in the UI

The exam will occasionally test "where does this show up in GitHub?" Knowing the menu path saves you on those questions.

1
The Security tab — the main entry point

On any repository, the Security tab is where all GHAS alerts surface. Subsections inside: Code scanning alerts, Secret scanning alerts, Dependabot alerts. Each can be filtered, dismissed (with a reason), or marked resolved.

2
Settings → Code security & analysis

The configuration page for the repo. Toggle individual features on or off, configure custom secret scanning patterns, enable push protection, manage Dependabot. Available at repo, organization, and enterprise level (with higher levels setting policy for the levels below).

3
Security Overview (org & enterprise level)

An aggregated dashboard across all repos in the organization. Shows alert counts by feature, by severity, by repository. The cross-repo view is what makes GHAS administration possible at scale.

4
Pull request checks (inline)

Dependency Review and Code scanning PR checks appear directly on every pull request as status checks. The reviewer sees them without leaving the PR — that's the design intent.

Module 4 · Domain 2 deep dive

Configure & use secret scanning

Domain 2 of the GH-500 — 15% of the exam. Same weight as Domain 1, but more procedural: paths, settings, limits, lifecycles.

What secret scanning actually scans (more than just code)

The exam tests scope. Most candidates assume secret scanning looks only at source code files — and miss the wider net it casts.

All of git history, all branches

Not just the latest commit. Not just main. Every commit on every branch — historical content included. A secret leaked three years ago in a feature branch will still be detected.

Issues, PRs, and Discussions too

Titles, descriptions, comments — across open AND closed historical issues, pull requests, and GitHub Discussions. A secret pasted in a PR comment counts the same as one in code.

Why this matters for the exam

If a question says "a developer pasted an API key in a closed issue comment three months ago" — that's still in scope. Don't be fooled by "it was closed" or "it wasn't in the code." Issues and PRs are scanned the same way the codebase is.

Two distinct features — define them before the matrix

The next screens compare them across scopes, so anchor the difference now.

Secret scanning (the detector)

Runs after code arrives on GitHub. Looks at every commit, every branch, plus issues / PRs / discussions. Produces an alert when a pattern matches. The secret has already entered git history at this point — detection is a notification, not a block.

Push protection (the blocker)

Runs during git push. The push is intercepted server-side: if any new commit contains a detected secret, the push is rejected before the commit lands on GitHub. The secret never enters history at all. Bypass requires an explicit reason from the developer.

Both rely on the same partner-pattern library, but the timing is what differentiates them. Keep this distinction in mind for the next screens — the matrix lists them separately because they enable separately.

The single most-tested fact about secret scanning

This screen exists because one specific question appears on almost every GH-500 attempt. Read carefully.

Public repositories: secret scanning is on, and cannot be configured or turned off.

Read it again. Cannot. On a public repo, you don't enable secret scanning (it's already on by default), you don't disable it (you can't), you don't configure it (you can't either). The only way to change secret scanning behavior on a public repo is to switch it to a private repository with a GitHub Advanced Security license. Then — and only then — does configuration become possible.

Secret scanning configurability by scope
Capability Public repo Private repo (no GHAS) Private repo (with GHAS)
Secret scanning enabled? Default ON, automatic Not available Manual — must be enabled
Can you configure or disable it? No, not at all — Yes, fully
Push protection Default-on for users (partner patterns) Not available Configurable + custom patterns
Custom secret patterns No No Yes
Exam trap: the "admin permissions" distractor

A common wrong answer on public-repo questions is "get admin permissions on the repository." It's plausible-sounding but wrong. Admin permissions don't matter when the platform doesn't expose the configuration at all. Switch-to-private-with-GHAS is the only real answer.

The exact menu paths the exam tests on

The GH-500 will ask "where do you do X?" — and the wrong answers will be other plausible menu locations. Memorize the paths.

1
Enable secret scanning (private repo with GHAS)

Navigate to Settings → Security → Advanced Security. Click Enable next to "Secret Protection" and confirm. Then separately click Enable next to "Push protection". They're enabled independently — enabling secret scanning does NOT auto-enable push protection.

2
Enable secret scanning across the organization

Set up GHAS at the organization level, then configure Global Secret Scanning settings in org settings. Repos in that org will then have secret scanning enabled by default (admins of those repos will see "Disable" instead of "Enable" in their repo settings — meaning it was inherited).

3
Configure granular settings (post-enable)

Once enabled, granular settings live at a different path: Settings → Code security and analysis → Secret Protection. This is where you toggle validity checks, non-provider patterns, AI-based generic password detection, push protection bypass rules, and alert dismissal rules.

4
Add custom alert recipients

Path: Settings → Security → Advanced Security → Access to Alerts. Type the person or team name, select from matches, save. This is the ONLY correct place — NOT in "Manage Access" (that's repo-wide permissions) and NOT in "Watch settings" (that's personal user preferences, not recipient configuration).

Exam trap: two similar paths, different purposes

Settings → Security → Advanced Security is for the INITIAL enable/disable plus alert recipients. Settings → Code security and analysis → Secret Protection is for granular post-enable settings (validity checks, custom patterns toggle, AI scanning, etc.). The exam may give you a wrong path as a distractor — confirm which path serves which purpose.

The numerical limits the exam will absolutely test

GH-500 is fond of "how many" questions where three of four options are plausible numbers. Know these cold.

Limit Value What happens if you exceed it
Custom patterns per private repository 100 You can't create more — the UI rejects creation
Custom patterns per organization or enterprise 500 Same — UI rejects further creation
Repositories selectable for org-level dry run 10 You pick up to 10, or use "All repositories in the organization"
Results shown in a dry run sample 1,000 Only the first 1,000 results are shown — actual matches may be more
Entries in paths-ignore 1,000 Only the FIRST 1,000 are honored; everything after is ignored (scanned anyway)
Size of secret_scanning.yml 1 MB The ENTIRE file is ignored. Not truncated — completely ignored, as if it didn't exist.
Exam trap: paths-ignore vs file-size limits

These two limits are commonly confused on the exam. If paths-ignore has 1,200 entries, the file is still honored — but only the first 1,000 paths are excluded. If the FILE is 1.3 MB, the entire file is ignored regardless of how many paths it lists. Different limits, different behaviors.

Who gets notified (the standard list)

  • Security managers
  • Repository administrators
  • Users with custom roles having read/write access

Plus the special case

Commit author is always notified, regardless of their notification preferences. This is hardcoded behavior — they cannot opt out. The intent: the person who committed the secret should know immediately, even if they have disabled all other notifications.

What actually happens when a secret leaks on a public repo

Public repos are the special case worth understanding mechanically. The same secret-scanning detector runs, but the downstream chain is different: GitHub doesn't just file an alert — it tells the partner that issued the credential, and the partner can act unilaterally to neutralize it. This is the public-repo story the exam, and real incidents, both depend on.

From commit to partner-side revocation. Read top to bottom.

Red nodes are the dangerous and the protective steps. Note the dual destination from Verify: confirmed-active credentials go through partner-side revocation; inactive matches still create a GitHub alert but no revocation happens.

Why partners act, not just GitHub

GitHub knows the token format, but only the partner can confirm "yes, this token is real, currently active, and belongs to customer X." Only the partner can revoke a credential they issued. The partner verification webhook is what makes this collaboration possible.

What the owner still has to do

Even when a partner auto-revokes, the owner must still: (1) rotate the underlying credential and update services that used it, (2) review provider-side access logs to assess misuse, (3) close the GitHub alert with a reason. Partner revocation prevents new abuse — it doesn't undo abuse that already happened in the time window between leak and revocation.

Public vs private: who revokes

On public repos the partner is in the loop and may auto-revoke or quarantine. On private repos with GHAS, the same partner-pattern library is used and partners are still notified for matched partner tokens, but real-world partner revocation is most aggressive on public exposures (where the credential is presumed compromised by default). Either way, GitHub itself never revokes a third-party credential — it only files alerts and forwards matches.

Custom patterns: defining your organization's secrets

Beyond partner patterns (AWS, Stripe, etc.), you can define custom patterns for secrets internal to your organization — internal API tokens, license keys, anything with a recognizable shape.

About Hyperscan regex

Most developers know PCRE (Perl-Compatible Regular Expressions) or JavaScript regex. Hyperscan is similar but not identical — some advanced PCRE features (lookbehind assertions in particular) may not be supported. If the exam asks why a custom pattern doesn't match, "wrong regex engine syntax" is a plausible cause. Test with a sample test string before publishing.

Five tools, one supply chain security story

The exam tests "which tool does X?" constantly on Domain 3. Before anything else, internalize this map.

The 5 supply chain security tools on GitHub

The most frequently confused pair

Dependabot watches what's already in your repo, continuously, even after merge. Dependency Review watches what you're trying to ADD in a PR, before you merge. Same dependency focus, completely different timing. The exam will put both as adjacent answer options — the timing word in the question tells you which to pick: "before merge" → Dependency Review; "continuously" or "after it turned vulnerable" → Dependabot alerts.

The dependency graph — the foundation everything else builds on

Dependabot alerts can't work without it. Security updates can't work without it. It's the prerequisite, not optional.

What the graph contains

  • Direct dependencies — explicitly declared in your manifest or lock file
  • Indirect (transitive) dependencies — packages used by your packages
  • Dependents — repos that depend on yours (public repos only — NOT on private repos)

View at: Insights → Dependency graph → Dependencies or Dependents tab

Scope conditions

  • Public repos: auto-generated, always on
  • Private repos: available but must be manually enabled by an admin

Settings → Security → Advanced Security → Dependency graph → Enable

Exam trap: manifest only vs manifest + lock file

If a repo uses only a manifest file (e.g., package.json) without a lock file (e.g., no package-lock.json), the dependency graph is still generated — but indirect (transitive) dependencies are NOT included in vulnerability checks. You can miss Dependabot alerts on transitive deps entirely. Always use lock files for complete coverage.

GitHub Advisory Database and SBOM

GitHub Advisory Database

Open-source, curated by GitHub. Uses CVSS for severity: low / moderate / high / critical.

Sources: NVD, npm Security Advisories, community contributions, ML-assisted review of public commits.

Identifiers — know all four:
  • CVE ID — the specific vulnerability (global standard)
  • GHSA ID — GitHub's own advisory identifier
  • CWE ID — the weakness type (e.g., CWE-89 = SQL injection)
  • CVSS score — the numerical severity rating

SBOM (Software Bill of Materials)

A formal, machine-readable inventory of all dependencies. Format: SPDX — not CycloneDX, not JSON, not SARIF.

Export via: the Export SBOM button in the Dependency graph, or via the REST API.

Why it matters for compliance: Executive Order 14028 requires an SBOM for software sold to the US federal government. EO 14028 in a question → SBOM in SPDX format.

Dependabot's three sub-features — know which does what

Dependabot is an umbrella for three distinct capabilities. The exam asks about each individually and tests whether you confuse them with each other.

A
Dependabot alerts

Notifies you when a dependency in your repo appears in the GitHub Advisory Database as vulnerable.

Two triggers: (1) a new advisory is added for a package you already use, OR (2) your dependency graph changes and you added something already vulnerable.

Not on by default — must be enabled manually on both public AND private repos.

B
Dependabot security updates

Automatically opens pull requests to update vulnerable dependencies to a safe version. PR is authored by the dependabot bot, labeled dependencies, and includes a compatibility score.

Prerequisites (ALL must be true): dependency graph enabled AND Dependabot alerts enabled.

Auto-enables on new repos when: not a fork, not archived, public OR private with graph+alerts enabled, not explicitly disabled.

C
Dependabot version updates

Opens PRs to update dependencies to their newest versions — regardless of whether there's a vulnerability. Requires a .github/dependabot.yml file. Without this file, version updates simply don't run.

Fork trap: version updates are NOT auto-enabled on forks. To activate on a fork: Insights → Dependency graph → Dependabot → Create config file.

Exam trap: grouped security updates vs grouped version updates

The groups option in dependabot.yml applies only to version updates. To enable grouped security updates (bundling multiple security PRs into one), you must toggle a separate feature in Settings → Code security and analysis. The exam will show a YAML with groups and ask why security updates aren't being grouped — the answer is they need the separate UI toggle, not a YAML change.

Enabling Dependabot — paths at every level

The exam tests the exact UI paths for enabling Dependabot at repo, user, org, and enterprise level. Each level has a distinct path.

1
Repository level

Settings → Code security and analysis → Enable Dependency graph first, then enable Dependabot alerts. Order matters — graph must be on before alerts.

2
User level (across all your repos)

Profile → Settings → Code security and analysis → Enable all → optionally tick "Automatically enable for new repositories".

3
Organization level

Profile → Your organizations → [org] → Settings → Code security and analysis → Enable all → optionally tick "Automatically enable for new repositories".

4
Enterprise level

Profile → [enterprise] → Settings → Code security and analysis → Enable all.

Who sees Dependabot alerts by default

Users with write, maintain, or admin access plus org owners. To grant access to others: Settings → Code security and analysis → Access to alerts → type name → Save.

The dependabot.yml file — structure and key fields

Version updates require a config file at .github/dependabot.yml. Without it, version updates don't run. The exam tests valid vs invalid YAML structure.

Minimum valid structure

Three required fields per entry: package-ecosystem, directory, schedule.interval. And always version: 2 at the top.

version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "daily"

Valid interval values: daily | weekly | monthly. The registries: key is optional and used for private registries with authentication.

Grouped version updates example

The groups option — applies to version updates only, not security updates.

version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "daily"
    groups:
      production-dependencies:
        dependency-type: "production"
      development-dependencies:
        dependency-type: "development"
Grouping rules the exam will test

Dependabot WILL group dependencies from different directories if they share the same ecosystem. Dependabot WILL NOT group across different ecosystems (npm + pip = separate PRs, always). Dependabot WILL NOT group security updates together with version updates — those are always separate PRs regardless of configuration.

Module 6 · Domain 4 deep dive

Configure & use Code Scanning with CodeQL

Domain 4 of GH-500 — 25% of the exam. The second-largest domain. Two setup modes, three query suites, language extraction quirks, and SARIF interoperability.

Code scanning in one breath: SARIF in, alerts out

Code scanning is a platform, not a single tool. CodeQL is the default engine, but any scanner that emits SARIF can feed into it. The exam tests the distinction.

CodeQL — the default engine

GitHub's own semantic static analyzer. Treats code as a queryable database. Ships with curated security and quality query packs maintained by the GitHub Security Lab.

Free on public repos. Requires GHAS for private repos.

Third-party scanners — via SARIF

ESLint, Semgrep, Snyk, Checkmarx — any tool that produces SARIF can upload its findings using the github/codeql-action/upload-sarif action or the SARIF upload API. Results appear in the same Security tab next to CodeQL findings.

Exam trap: "CodeQL is the only scanner GitHub supports"

Wrong. Code scanning accepts SARIF from any tool. The exam may try to anchor you to "CodeQL only" — remember the platform/engine distinction. SARIF is what makes interoperability work.

How CodeQL turns your code into a queryable database

"CodeQL treats code as data you can query" is the headline. The mechanism behind that headline is a three-stage pipeline that runs every time code scanning fires. Understanding it explains why builds are required for compiled languages, why workflows take longer the first time, and what "continuous" scanning actually means in this context.

The CodeQL pipeline — extract → analyze → upload

Runs end-to-end inside the Actions runner on every trigger.

The database is the central object. Once it exists, the same database can be analyzed by many different query suites without re-extracting.

Why interpreted languages don't need a build

For JS/TS, Python, Ruby (and Go, by exception), the source is already the program. The CodeQL extractor reads the files, parses them into ASTs, resolves imports, and writes the relational facts directly into the database. No compiler involvement, no build commands needed.

Why compiled languages DO need a build

For Java, C/C++, C#, Swift, source files alone are insufficient — types, generics, macros, and conditional compilation are only resolved during compilation. CodeQL's extractor works as a compiler tracer: it sits between you and javac/gcc/csc/swiftc, intercepts each translation unit, and records what the compiler saw. If the compiler isn't invoked, the extractor sees nothing — that's why "no source code seen" is the error you get when autobuild fails.

What "continuous scanning" actually means

Code scanning is "continuous" because the workflow re-runs the entire pipeline on every relevant event: every push to a watched branch, every pull_request against one, and on a schedule: cron (commonly weekly). Each run builds a fresh database, runs the suite, uploads a fresh SARIF. There's no live, always-on daemon — "continuous" means "re-run on every change plus a scheduled backstop."

Default setup vs Advanced setup — the central choice

When you enable code scanning, GitHub asks you to pick one of two setup modes. The exam tests when each is appropriate and what each can/can't do.

CodeQL has to extract code into its database before queries can run. How extraction happens depends on whether the language is compiled or interpreted — and the exam loves this distinction.

Three build modes for compiled languages

  • autobuild — CodeQL attempts to detect and run your build automatically
  • manual — you write the exact build commands between init and analyze steps
  • none — source-only extraction (available for C# and Java in newer CodeQL versions)

When autobuild fails

Autobuild has heuristics — Maven, Gradle, MSBuild, make. If your project has non-standard build commands, autobuild fails and the analyze step reports "no source code seen." The fix: switch to build-mode: manual and add your real build steps explicitly.

The CodeQL workflow file — anatomy of codeql.yml

Advanced setup gives you a workflow file with three core steps: checkout, init, analyze. The exam tests recognition of valid vs invalid structure.

Minimum valid CodeQL workflow

Place at .github/workflows/codeql.yml.

name: "CodeQL"
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
  schedule:
    - cron: '0 6 * * 1'   # weekly Monday 06:00 UTC
jobs:
  analyze:
    name: Analyze (${{ matrix.language }})
    runs-on: ubuntu-latest
    permissions:
      security-events: write
      actions: read
      contents: read
    strategy:
      fail-fast: false
      matrix:
        language: [ 'javascript', 'python' ]
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with:
          languages: ${{ matrix.language }}
          queries: security-extended
      - uses: github/codeql-action/analyze@v3
        with:
          category: "/language:${{ matrix.language }}"

Required permission: security-events: write. Without it the analyze step can't upload SARIF — and CodeQL fails silently as far as the Security tab is concerned.

Exam trap: missing security-events: write

A frequent scenario: "the workflow runs successfully but no alerts appear in the Security tab." The cause is almost always missing security-events: write permissions. The job logs may look green because analyze finished, but the upload step couldn't write to the security tab.

The three query suites — pick one

CodeQL ships with three built-in query suites. You set them in init via the queries: input. The exam tests the names exactly and what each contains.

1
default (used when queries: is omitted)

The baseline suite. Optimized for low false-positive rate and short runtime. Includes the most important high-confidence security queries.

Use when: you want fast, low-noise scans on a high-traffic repo.

2
security-extended

The default suite PLUS additional security queries with slightly higher false-positive rates. More coverage, more noise.

Use when: you need broader coverage and are willing to triage more findings.

3
security-and-quality

The widest suite. Includes everything in security-extended PLUS code-quality queries (maintainability, reliability, style violations).

Use when: you want the firehose — security and quality, all at once.

Suites are nested — not exclusive

The suites are concentric, not different paths: default ⊂ security-extended ⊂ security-and-quality. Picking security-extended doesn't replace default — it adds to it. You don't list multiple suites; you list the widest one you want.

Code scanning alert lifecycle and dismissal reasons

When a code scanning run finds an issue, GitHub creates an alert. The lifecycle has four states and exactly three dismissal reasons — the exam tests the names verbatim.

Alert states

  • Open — created by a scan and not yet resolved
  • Dismissed — manually closed with a reason
  • Fixed — auto-closed when a later scan no longer detects the issue
  • Reopened — was dismissed/fixed but reappeared on a later scan

The three dismissal reasons

  • False positive — the query matched but the code isn't actually vulnerable
  • Used in tests — the pattern exists only in test code, not in production paths
  • Won't fix — accepted risk; the team has chosen not to remediate
Exam trap: the dismissal reasons must be EXACTLY these three

Distractors will include plausible-sounding fake reasons: "not applicable", "accepted risk", "duplicate", "in backlog". They aren't real options. Only false positive, used in tests, and won't fix exist in the UI.

Who can dismiss alerts

Permission model — frequently tested.

Users with write access to the repository can dismiss alerts. Repository admins can additionally configure who has access to alerts under Settings → Code security and analysis → Access to alerts. The author of a PR cannot dismiss alerts they introduced without that write access.

SARIF upload — bringing in third-party scanners

Code scanning's superpower is that it accepts findings from anything. The standard format is SARIF, uploaded via either an action step or the API.

SARIF upload via the action

Drop this into any workflow that already produces a SARIF file.

- name: Upload SARIF
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
    category: "semgrep"

The category distinguishes uploads from different tools so they don't overwrite each other in the same repo. Same repo can have multiple SARIF uploads as long as each uses a unique category.

Limit Value What happens at the limit
Max SARIF file size 10 MB Upload rejected — must shrink the file
Max results per SARIF run 25,000 Only the first 25,000 are processed
Max results per rule ID 5,000 Excess results dropped silently
Max runs per SARIF file 20 Additional runs rejected
Exam trap: silent truncation

When SARIF exceeds the result limits, GitHub doesn't fail loudly — it silently caps. If a tool reports 30,000 issues but only 25,000 appear in the Security tab, this is the cause. The fix: filter at the tool level before uploading, or split into multiple categories.

Code scanning as a required check

Findings alone don't block merges — you have to wire code scanning into branch protection rules.

1
Make code scanning a required status check

Settings → Branches → Branch protection rules → Add rule. Tick "Require status checks to pass before merging" → search for and add CodeQL (or your third-party tool's check name) as a required check.

2
Configure merge blocking by severity

Under Settings → Code security and analysis → Code scanning → Protection rules, choose the severity threshold that blocks PR merges. Default values: error, warning, note (SARIF levels) — and critical, high, medium, low for security severities.

3
PR annotations — and why you only see new findings inline

When code scanning runs on a pull request, GitHub actually performs two analyses and compares them: one on the PR's head commit and one on the base branch the PR targets. The delta — alerts present on head but not on base — is what gets posted as inline annotations on the changed lines of the PR. Pre-existing alerts (present in both base and head) are kept out of the way: they appear under a separate "existing alerts" tab in the PR's Checks panel rather than as inline noise on the diff.

This is why CodeQL on a long-lived branch usually surfaces zero PR annotations even when the Security tab shows hundreds of open alerts — the PR didn't introduce any new findings, even though the repo has plenty.

CodeQL CLI — running outside Actions

The CodeQL CLI is a standalone command-line tool. The exam tests when to use it and the three-step workflow.

When to use the CLI

  • Running CodeQL outside GitHub Actions (e.g., third-party CI like Jenkins, CircleCI)
  • Developing and testing your own custom CodeQL queries locally
  • Producing SARIF files to upload via the SARIF upload API

The three-step CLI workflow

  1. codeql database create — extract code into a database
  2. codeql database analyze — run queries against it, emit SARIF
  3. codeql github upload-results — upload SARIF to the Security tab
Authentication for upload-results

The CLI needs a token with security-events: write scope to upload SARIF. Use a fine-grained PAT or a GitHub App token. The same permission requirement applies in Actions workflows — only the delivery mechanism is different.

Triage: deciding what to fix first

Triage golden rule

Validity-confirmed active secrets are always priority one. An active AWS key in a public repo outranks a critical CodeQL finding in untested branch code. Treat confirmed live secrets as an active breach: rotate first, investigate after.

Security policies — SECURITY.md

A SECURITY.md file tells external researchers and contributors how to report vulnerabilities responsibly. The exam tests where it goes and what GitHub does with it.

Where the file lives

  • SECURITY.md at the repo root
  • OR docs/SECURITY.md
  • OR .github/SECURITY.md

Same lookup logic as CONTRIBUTING.md — first match wins.

What GitHub does with it

When a SECURITY.md exists, GitHub surfaces a "Security policy" link in the repository's Security tab and on the "Report a vulnerability" page. The file's content is rendered as the public report-handling guidance.

Default community at the org level

You can drop a SECURITY.md in the special .github repository of an organization. Any repo in that org without its own SECURITY.md inherits this default. The exam may test "where do you set a security policy for all org repos at once?" — the answer is the .github repo, not the org settings.

Private vulnerability reporting (PVR)

PVR is a feature that gives external researchers a private channel to report vulnerabilities directly inside GitHub, without disclosure in public issues.

1
Enable per repo

Path: Settings → Code security and analysis → Private vulnerability reporting → Enable. Once enabled, anyone with a GitHub account can submit a private report via the repo's Security tab → "Report a vulnerability" button.

2
Enable across an organization

Path: Org Settings → Code security and analysis → Private vulnerability reporting. You can enable it for all current repos, all new repos, or both. Available for free on both public and private repositories — no GHAS license required.

3
Triage workflow

Reports show up as draft security advisories in the repo's Security tab. Maintainers triage, discuss in a private collaboration space, request a CVE if needed, and publish the advisory once a fix is shipped.

Exam trap: "PVR requires GHAS"

False. Private vulnerability reporting is free for public and private repos alike. GHAS is not a prerequisite. The exam may bundle PVR with other paid features to mislead you.

Once published, the advisory is searchable in the GitHub Advisory Database. Dependabot can then alert downstream consumers of your package.

Temporary private forks

Inside a draft advisory, maintainers can spin up a temporary private fork to develop the fix without exposing it publicly. When the advisory is published, the fix is merged to main from the private fork.

CVE Numbering Authority (CNA)

GitHub is an official CNA. From inside an advisory you can request a CVE ID without going to MITRE directly. The CVE is reserved during draft and assigned at publish time.

Security manager role

An org-level role designed for security teams: read access to all repos in the org PLUS read/write access to all security alerts. Granted at: Org Settings → Teams → [team] → Security manager. Up to 10 teams can be designated.

Security overview dashboard

Cross-repo dashboard at Org → Security tab. Shows enabled GHAS features, open alerts by repo and severity, and adoption trends. Filterable by team, repo, and feature. Requires GHAS for private repos.

Audit log — the record of who did what

The audit log captures security-relevant configuration changes. The exam tests where it lives, how long entries are retained, and which events are tracked.

Where it lives

  • Org-level: Org → Settings → Audit log
  • Enterprise-level: Enterprise → Audit log (aggregates all orgs)
  • Repo-level: no dedicated UI; events surface in the parent org's audit log

Retention

  • GitHub.com retains for at least 6 months; most queryable events go back further
  • Export to JSON or CSV for long-term archival
  • Stream to external SIEM via the Audit Log Streaming feature (Enterprise Cloud only)
Events the exam expects you to know are logged

Enabling/disabling Dependabot, code scanning, or secret scanning; dismissing security alerts; creating/publishing security advisories; changing branch protection rules; adding/removing security managers; modifying custom secret patterns. Not logged at user level: individual code scanning query runs — those live in the workflow run history, not the audit log.

Best-practice settings that show up across the exam

Domain 5 questions also touch general repo hygiene that supports GHAS. Internalize this checklist.

1
Branch protection on the default branch

Require pull request reviews (at least 1, ideally 2). Require status checks: CodeQL, Dependency Review. Require branches to be up to date before merging. Restrict who can push to the protected branch.

2
Required reviewers and CODEOWNERS

Use .github/CODEOWNERS to require specific teams to review changes in their areas (e.g., /security/ @org/security-team). Combine with "Require review from Code Owners" in branch protection.

3
Signed commits

Enable "Require signed commits" in branch protection. Combined with verified commit signatures (GPG, SSH, S/MIME), this prevents impersonation in the commit history.

4
Secret scanning push protection

Enable push protection at the org level so leaks are blocked at git push time, not after they land in history. Configure bypass rules for true emergencies but require justification.

5
Pin third-party Actions to SHAs

Reference third-party actions by full commit SHA, not floating tags (uses: actions/checkout@v4 is okay because GitHub maintains it; for third-party actions use the 40-char SHA). Mitigates supply-chain attacks via tag re-pointing.

Corrective measures — three playbooks the exam tests

Leaked secret playbook

  1. Treat as compromised — assume it's been used
  2. Rotate / revoke the credential at the provider
  3. Issue a new credential, update services
  4. Investigate access logs for misuse
  5. Close the secret scanning alert with a reason

Do NOT just delete the commit — git history still contains it.

Vulnerable dependency playbook

  1. Read the Dependabot alert and Advisory Database entry
  2. Check whether a Dependabot security update PR exists
  3. If yes, review and merge it
  4. If no fix exists, evaluate reachability — is the code path used?
  5. Mitigate (config, WAF, code change) or dismiss with reason

Code scanning finding playbook

  1. Open the alert in the Security tab — read the data-flow trace
  2. Confirm whether the path is reachable from untrusted input
  3. Apply the recommended fix or refactor
  4. If not exploitable, dismiss with False positive, Used in tests, or Won't fix
