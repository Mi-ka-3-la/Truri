The Accounting Close Process

What is a task, where does it come from, and what makes it done?

Every item on your close checklist belongs to one of four task types

You open the Tasks page in Avise and see a list of items to complete this month. Each task is the atomic unit of the accounting close process, giving every piece of work a named owner, a due date, a reviewer, and a status. Nothing falls through the cracks because the system refuses to let work exist without those fields.

Account

A general ledger account task — verify the ending balance and make sure every transaction is accounted for before the books are closed.

Reconciliation

Verifies that an account balance matches its supporting documents — bank statements, sub-ledgers, or third-party confirmations — at period end.

Category

Groups a set of related accounts under a single review — useful when a preparer owns an entire expense category rather than individual line items.

Flux

Tracks and explains unusual swings in an account balance from one period to the next — the system flags outliers so reviewers know where to look.

Closing a period is like finishing a chapter of a book

The writer (preparer) drafts and submits each section; the editor (reviewer) approves it or sends it back with notes. The accounting period is one chapter — it cannot be sealed until every section has been reviewed and signed off.

The status field is the system vocabulary — every state a task can ever be in is listed exactly once

An enum in the schema locks the field to a known set of values. If code tries to write a status of, say, pending — a word not in the list — the Prisma ORM will refuse the write before it ever reaches the database.

CODE 

enum TaskStatus {
  unprepared
  in_progress
  prepared
  reopened
  rejected
  reviewed
  wont_do

  @@map(name: "task_status")
}
PLAIN ENGLISH

This is the complete list of states a task can ever be in. No other value is allowed — ever.

unprepared — No work has started. Every new task begins here.

in_progress — The preparer has started but not yet submitted.

prepared — The preparer clicked submit. Now waiting for a reviewer.

reopened — The reviewer sent it back. The preparer must fix and resubmit.

rejected — Permanently declined; the work is recorded but not accepted.

reviewed — The reviewer approved it. The task is complete.

wont_do — Deliberately skipped this period with a recorded reason.

@@map tells Prisma what name to use for this type in the actual database table.

A status enum is the system vocabulary — it makes impossible states unrepresentable

Constraining a field to a known set means the database can never hold a value the application does not understand. Every layer of the system — the database, the API, the UI — shares the same vocabulary with no ambiguity.
