Three-layer architecture is not bureaucracy — each layer has a different job description

The controller is a receptionist. The service is the decision-maker. The data layer is the filing clerk. When you see Prisma queries in a controller or email logic in the data layer, that is a bug — not a style preference.

The data layer speaks only Prisma — no business logic, no side effects, no opinions

setTaskStatus is the simplest data layer function. It runs one Prisma update, sets the timestamp, and returns the record. No validation, no emails, no events. That is by design — the service layer above it handles those concerns.

CODE 

function setTaskStatus(
  companyId: string,
  taskId: string,
  status: TaskStatus,
): PrismaPromise<PrismaTask> {
  return prisma.task.update({
    where: {
      companyId_id: { companyId, id: taskId },
    },
    data: {
      status,
      statusUpdatedAt: getCurrentSystemJsDateTime(),
    },
  });
}
PLAIN ENGLISH

companyId + taskId as a compound key — the WHERE clause requires both. A task ID alone is not enough: the same numeric ID could theoretically exist across two companies. The compound key prevents one company from accidentally updating another company record.

prisma.task.update — Prisma generates the SQL UPDATE statement from this typed object. No raw SQL string, no injection risk, and the TypeScript compiler catches typos in field names before the code ever runs.

statusUpdatedAt — always stamped with the current system time. This powers sorting, filtering, and audit displays throughout the UI.

Returns PrismaPromise — the function can be composed into a larger Prisma transaction. The caller decides whether to run it alone or inside an atomic block with other operations.

The data layer is a filing clerk — it stores exactly what it receives and asks no questions

Email sending, transition validation, and side effects all belong one floor up in the service layer. When AI-generated code adds email logic inside a data function, that is a layer violation — and a correctness risk, because now side effects run even when the caller wanted to batch the operation inside a transaction.

The service layer decides which tasks to reopen — the data layer handles the how

reopenDueToLedgerUpdates is a service layer function that orchestrates the task reopening flow. It receives raw ledger updates, fetches only the relevant tasks, and delegates reopening to a helper — no Prisma query appears here directly.

CODE 

const reopenDueToLedgerUpdates = async (
  companyId: string,
  ledgerUpdates?: LedgerUpdate[],
): Promise<void> => {
  if (ledgerUpdates?.length) {
    // Fetch tasks linked to incoming accountIds
    const tasksWithPeriod =
      await fetchTasksForLedgerUpdates(
        ledgerUpdates, companyId
      );

    // Reopen tasks affected by the ledger updates
    await reopenQualifyingTasks(
      tasksWithPeriod, companyId
    );
  }
};
PLAIN ENGLISH

Guard on ledgerUpdates?.length — if no ledger updates arrived, exit immediately. This prevents unnecessary database queries when there is nothing to check.

fetchTasksForLedgerUpdates — a data-layer call that fetches only the tasks associated with the affected account IDs and their periods. The service does not write raw Prisma here — it delegates to the data layer.

reopenQualifyingTasks — another service-level helper that runs the balance comparison logic and decides which tasks actually need to be reopened. Decision logic stays in the service; writes go through the data layer.

No raw Prisma calls visible — the service layer is clean of database syntax. That boundary is what makes each layer independently testable and replaceable.
