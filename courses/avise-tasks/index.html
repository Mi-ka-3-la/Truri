01

The Accounting Close Process

What is a task, where does it come from, and what makes it done?

Every item on your close checklist belongs to one of four task types

You open the Tasks page in Avise and see a list of items to complete this month. Each task is the atomic unit of the accounting close process, giving every piece of work a named owner, a due date, a reviewer, and a status. Nothing falls through the cracks because the system refuses to let work exist without those fields.

Account

A general ledger account task — verify the ending balance and make sure every transaction is accounted for before the books are closed.

Reconciliation

Verifies that an account balance matches its supporting documents — bank statements, sub-ledgers, or third-party confirmations — at period end.

Category

Groups a set of related accounts under a single review — useful when a preparer owns an entire expense category rather than individual line items.

Flux

Tracks and explains unusual swings in an account balance from one period to the next — the system flags outliers so reviewers know where to look.

Closing a period is like finishing a chapter of a book

The writer (preparer) drafts and submits each section; the editor (reviewer) approves it or sends it back with notes. The accounting period is one chapter — it cannot be sealed until every section has been reviewed and signed off.

The status field is the system vocabulary — every state a task can ever be in is listed exactly once

An enum in the schema locks the field to a known set of values. If code tries to write a status of, say, pending — a word not in the list — the Prisma ORM will refuse the write before it ever reaches the database.

CODE 

enum TaskStatus {
  unprepared
  in_progress
  prepared
  reopened
  rejected
  reviewed
  wont_do

  @@map(name: "task_status")
}
PLAIN ENGLISH

This is the complete list of states a task can ever be in. No other value is allowed — ever.

unprepared — No work has started. Every new task begins here.

in_progress — The preparer has started but not yet submitted.

prepared — The preparer clicked submit. Now waiting for a reviewer.

reopened — The reviewer sent it back. The preparer must fix and resubmit.

rejected — Permanently declined; the work is recorded but not accepted.

reviewed — The reviewer approved it. The task is complete.

wont_do — Deliberately skipped this period with a recorded reason.

@@map tells Prisma what name to use for this type in the actual database table.

A status enum is the system vocabulary — it makes impossible states unrepresentable

Constraining a field to a known set means the database can never hold a value the application does not understand. Every layer of the system — the database, the API, the UI — shares the same vocabulary with no ambiguity.

02

The Task Data Model

Every task is a structured database record — here is what each field is for

A task record is a library checkout card: it names the borrower, the approver, the due date, and the book

When a task appears on screen it is a structured database record with fields for the owner, reviewer, the account it covers, the deadline, and a snapshot of the balance when work was last submitted. Every field exists to answer one question the close process cannot skip.

assignedTo

The preparer — the person responsible for completing this task. They are the writer of this chapter.

reviewerId

The approver — the person who inspects the work and either signs off or sends it back. Must be a different person from the preparer.

dueDate

The deadline for this task. Stored as a calendar date (no time component), so the same due date applies regardless of time zone.

status

The current state of the task — one of the seven values in the TaskStatus enum. Every screen and every business rule reads this field.

accountId

The general ledger account this task covers. Links the task to a specific account in the chart of accounts so reports can aggregate by account.

balanceWhenLastPrepared

A snapshot of the account balance at the moment the preparer submitted. If the live balance changes afterward, the system compares it to this snapshot and knows the task needs attention again.

balanceWhenLastPrepared is the system's memory — it makes stale approvals detectable

Without this field, the system would have no way to know whether the account changed after the preparer submitted. With it, a nightly job can compare live balances to the snapshots and automatically reopen any task whose account moved.

The Prisma Task model groups fields into four logical roles: identity, people, work, and smart controls

The Prisma model below is the single source of truth. Every TypeScript type, every API response, and every UI component derives from it. Changes to one field here ripple automatically to every layer of the stack.

CODE 

// IDENTITY — what period and company does this belong to?
model Task {
  id        String  @id @default(cuid())
  companyId String
  periodId  String

  // PEOPLE — who does the work, who approves it?
  assignedTo  String?
  reviewerId  String?
  createdBy   String?

  // WORK — what is the task and where does it stand?
  title      String
  dueDate    DateTime @db.Date
  taskType   TaskType
  status     TaskStatus
  resolution String?

  // SMART — system intelligence fields
  balanceWhenLastPrepared  Int?
  autoReviewEnabled        Boolean?
  recurringTaskId          String?
}
PLAIN ENGLISH

Identity: id is a CUID — a random collision-proof identifier. companyId and periodId are foreign keys that anchor this task to a specific company and a specific accounting month.

People: Three nullable user references. assignedTo is the preparer; reviewerId is the approver; createdBy logs who originally created it (often a system process, not a human).

Work: taskType and status are both enums — constrained to known values. resolution is nullable text: a free-form note the preparer or reviewer can add, especially when marking a task as wont_do.

Smart: balanceWhenLastPrepared is the snapshot integer. autoReviewEnabled lets the system approve low-risk tasks without human intervention. recurringTaskId links back to the template that generated this task.

Two separate user fields encode a legal requirement, not a design preference

Accounting standards (SOX, GAAP) require separation of duties: the person who does the work must not be the same person who approves it. Two distinct fields make that constraint enforceable in code, not just in policy.

A task record is assembled from three sources simultaneously when a period opens

No single actor creates a task alone. The RecurringTask template provides the who and what; the Period provides the when; the Account provides the subject. The database assembles all three into one new Task row.

03

The Task Lifecycle

Every status change is an atomic write — the status and the audit record are inseparable

A task status moves forward like a relay baton — and can be sent back before it crosses the finish line

When a preparer clicks Mark as Prepared, the task does not just change color. The system simultaneously records a new status AND creates an audit event in one single database write. No partial state is ever possible.

1
Task created — status: unprepared

The system generates the task when the period opens. The assignee can see it but no work has started.

2
Preparer starts — status: in_progress

The assignee begins working. The status signals to the reviewer that this task is claimed and active.

3
Preparer submits — status: prepared

The assignee marks work as done. The system records the current account balance in balanceWhenLastPrepared and creates an audit event. The baton is now in the reviewer's hands.

4A
Reviewer approves — status: reviewed

The reviewer signs off. The task is complete. The period can close once all tasks reach this state.

4B
Reviewer rejects — status: reopened

The reviewer finds a problem and sends it back. Status becomes reopened — not unprepared, because the audit trail must preserve that this task has been through at least one cycle. Return to step 3.

Status is the baton in a relay race — it cannot change hands without a recorded handoff

In a relay race, the baton physically moves from one runner to the next — there is no ambiguity about who has it. The TaskEvent log plays the same role: every status change leaves a permanent record of when it happened and why.

One Prisma update writes the status AND the audit record in a single database transaction

The function setTaskStatusAndEvent is the only place in the codebase where task statuses change. It uses a single Prisma update with a nested create — which means the database engine executes both writes as an atomic operation.

CODE 

function setTaskStatusAndEvent(
  companyId: string,
  taskId: string,
  status: TaskStatus,
  eventPayload: TaskEventPayload,
): PrismaPromise<PrismaTask> {

  const eventPayloadJson = {
    ...eventPayload, status
  };

  return prisma.task.update({
    where: { companyId_id: { companyId, id: taskId } },
    data: {
      status,
      statusUpdatedAt: getCurrentSystemJsDateTime(),
      autoReviewEnabled: false,
      taskEvents: {
        create: {
          type: TaskEventType.system_task_update,
          eventPayload: eventPayloadJson,
        },
      },
    },
  });
}
PLAIN ENGLISH

This function is the single gatekeeper for all status changes. Nothing else in the codebase updates status directly.

Inputs: which company, which task, what new status to set, and a payload object explaining why the change is happening.

status is written into the task row AND into the eventPayload — so the event record is self-contained and readable without joining back to the task.

statusUpdatedAt is stamped with the current system time — a precise timestamp for every transition.

autoReviewEnabled: false resets the auto-review flag on every status change — the system cannot auto-approve a task the reviewer just manually handled.

taskEvents: { create: ... } is the nested write. Prisma wraps the outer update AND this inner create into one database transaction automatically.

Atomic writes guarantee that a status change and its audit record are inseparable

If the event creation fails, the status does not change — and vice versa. The database enforces both-or-neither. This is exactly what compliance audit trail requirements demand: no status change without a reason on record.

Recurring Tasks

Templates on autopilot — configure once, generate every period forever.

Most tasks in Avise are never created manually — a template generates them every period

Think of a TV series: the show format is defined once (title, cast, runtime), and each week a new episode is produced from it. A RecurringTask is the show format; each period the system generates a fresh Task instance — its own episode, with its own status and resolution.

RecurringTask Template

The show format — stores title, assignee, task type, frequency, and the due date formula. Configured once by an admin; never has a status of its own.

Task Instance

The individual episode — inherits title, assignee, and task type from its parent template, then lives independently. It has its own status (starting at unprepared), its own resolution text, and its own computed due date.

Separating template from instance is the key design decision in this feature

It lets you reconfigure the template for next month without touching completed work from last month. Past episodes are sealed; the show format can change at any time.

The RecurringTask model separates what needs to happen from when and how often

Four fields do the heavy lifting: frequency sets the cadence, startDate and endDate bound the series run, and daysFrom + relativeTo form a due date formula that resolves fresh for every period.

CODE 

model RecurringTask {
  frequency   Frequency @default(monthly)
  startDate   DateTime  @db.Date
  endDate     DateTime? @db.Date
  daysFrom    Int
  relativeTo  RelativeTo
  taskType    TaskType
  tasks       Task[]    @relation("recurring_task")
}

enum Frequency {
  monthly
  quarterly
  yearly
}
PLAIN ENGLISH

frequency — how often a new task instance is generated. Defaults to monthly; can be quarterly or yearly.

startDate — the first period for which the system will generate tasks. Mandatory.

endDate — the last period. It is optional (marked with ?) — leave it null and the series runs indefinitely.

daysFrom + relativeTo — a formula, not a hardcoded date. Example: 5 days before period end. Computed fresh for every period so it is always correct regardless of month length.

tasks — the list of every Task instance that has ever been generated from this template. One template, many episodes.

A formula due date is always correct no matter which month it resolves in

Storing "5 days before period end" instead of a hardcoded date means February, March, and December all get the right deadline automatically. The system computes the actual date fresh each period.

Auto-Review and the Smart Reopener

Two systems that run silently in the background — one gives the all-clear, the other sounds the alarm.

Both systems compare a stored snapshot to a current value — that one decision makes everything possible

When a preparer submits a task, Avise stores the account balance at that exact moment in a field called balanceWhenLastPrepared. That single stored value is what makes both the auto-reviewer and the task reopener work.

Auto-Reviewer

Silently reviews tasks where the balance change is within configured thresholds — no human reviewer needed. Runs asynchronously in a job queue so the prepare action feels instant.

Task Reopener

Raises an alert when account balances change after a task was marked prepared. Compares balanceWhenLastPrepared to the new current balance. If they differ, the task is automatically set back to reopened with a BALANCE_CHANGED reason recorded in the audit trail.

The snapshot at prepare time is the architectural key to both features

Without storing balanceWhenLastPrepared, the system could not tell whether a balance discrepancy existed at submission time or appeared afterward. The snapshot freezes the financial state so the comparison is always meaningful.

The reopener compares two values and records a full audit event when they diverge

The core logic is a single conditional: if the current balance differs from the stored snapshot, setTaskStatusAndEvent updates the task status and logs the discrepancy with the full balance details — period-ending balance and the value stored at prepare time.

CODE 

const { balanceWhenLastPrepared } = task;

if (
  currentBalance !== undefined &&
  currentBalance !== balanceWhenLastPrepared
) {
  const balanceDetails =
    await tasksData.getBalanceDetails(
      task, TaskStatus.reopened
    );

  await tasksData.setTaskStatusAndEvent(
    companyId, task.id,
    TaskStatus.reopened, {
      reason: SystemTaskChangeReason.BALANCE_CHANGED,
      balances: { periodEndingBalance, balanceWhenLastPrepared },
    }
  );
}
PLAIN ENGLISH

balanceWhenLastPrepared — the frozen snapshot pulled from the task record. Set at the moment the preparer clicked Submit.

The first guard (!== undefined) means: only run this check if we actually fetched a current balance. If the account has no data yet, skip.

If the values differ, the balance changed after submission. This is the signal to reopen.

getBalanceDetails fetches the full balance context — period-ending balance and the stored snapshot — so we can show the preparer exactly what changed.

setTaskStatusAndEvent updates the status to reopened and writes an audit event with reason BALANCE_CHANGED and the two balance values. Both happen atomically.

The auto-reviewer runs in a job queue and applies different thresholds per task type

When a task is prepared, the auto-review function is added to a job queue rather than executed immediately. It reads company-level threshold settings, groups tasks by type, and only proceeds if auto-review is enabled for that company.

CODE 

async function attemptAutoReview(args, runSync) {
  if (config.taskAutoReviewer.runAsync && !runSync) {
    return addAutoReviewJobToQueue(args);
  }

  const company = await companies.get(args.companyId);
  const reconSettings =
    companiesService.extractAutoReconciliationSettings(company);
  const fluxSettings =
    companiesService.extractAutoFluxSettings(company);

  const allTasks = await tasksData.listWithPeriod(
    args.companyId, args.taskIds
  );
  const tasksByType = lodash.groupBy(
    allTasks, task => task.taskType
  );

  if (!isAutoReconEnabled(reconSettings) &&
      !isAutoFluxEnabled(fluxSettings)) return;
}
PLAIN ENGLISH

runAsync guard — if the config says to run asynchronously and no override is passed, the function immediately adds a job to the queue and returns. The HTTP request finishes instantly; the real work happens later.

reconSettings / fluxSettings — each company configures separate thresholds for reconciliation tasks and flux tasks. One size does not fit all.

groupBy taskType — reconciliation and flux tasks are evaluated with different logic and thresholds. Grouping them first keeps the evaluation code clean.

early return — if auto-review is disabled for both task types on this company, the function exits immediately without touching any tasks.

Running heavy checks in a job queue gives users instant feedback without sacrificing correctness

Checking thresholds across many tasks involves multiple database queries. Running this synchronously inside the prepare action would make the UI feel slow. The job queue lets the server return in milliseconds while the auto-review completes in the background.

The data layer speaks only Prisma — no business logic, no side effects, no opinions

setTaskStatus is the simplest data layer function. It runs one Prisma update, sets the timestamp, and returns the record. No validation, no emails, no events. That is by design — the service layer above it handles those concerns.

CODE 

function setTaskStatus(
  companyId: string,
  taskId: string,
  status: TaskStatus,
): PrismaPromise<PrismaTask> {
  return prisma.task.update({
    where: {
      companyId_id: { companyId, id: taskId },
    },
    data: {
      status,
      statusUpdatedAt: getCurrentSystemJsDateTime(),
    },
  });
}
PLAIN ENGLISH

companyId + taskId as a compound key — the WHERE clause requires both. A task ID alone is not enough: the same numeric ID could theoretically exist across two companies. The compound key prevents one company from accidentally updating another company record.

prisma.task.update — Prisma generates the SQL UPDATE statement from this typed object. No raw SQL string, no injection risk, and the TypeScript compiler catches typos in field names before the code ever runs.

statusUpdatedAt — always stamped with the current system time. This powers sorting, filtering, and audit displays throughout the UI.

Returns PrismaPromise — the function can be composed into a larger Prisma transaction. The caller decides whether to run it alone or inside an atomic block with other operations.

The data layer is a filing clerk — it stores exactly what it receives and asks no questions

Email sending, transition validation, and side effects all belong one floor up in the service layer. When AI-generated code adds email logic inside a data function, that is a layer violation — and a correctness risk, because now side effects run even when the caller wanted to batch the operation inside a transaction.

The service layer decides which tasks to reopen — the data layer handles the how

reopenDueToLedgerUpdates is a service layer function that orchestrates the task reopening flow. It receives raw ledger updates, fetches only the relevant tasks, and delegates reopening to a helper — no Prisma query appears here directly.

CODE 

const reopenDueToLedgerUpdates = async (
  companyId: string,
  ledgerUpdates?: LedgerUpdate[],
): Promise<void> => {
  if (ledgerUpdates?.length) {
    // Fetch tasks linked to incoming accountIds
    const tasksWithPeriod =
      await fetchTasksForLedgerUpdates(
        ledgerUpdates, companyId
      );

    // Reopen tasks affected by the ledger updates
    await reopenQualifyingTasks(
      tasksWithPeriod, companyId
    );
  }
};
PLAIN ENGLISH

Guard on ledgerUpdates?.length — if no ledger updates arrived, exit immediately. This prevents unnecessary database queries when there is nothing to check.

fetchTasksForLedgerUpdates — a data-layer call that fetches only the tasks associated with the affected account IDs and their periods. The service does not write raw Prisma here — it delegates to the data layer.

reopenQualifyingTasks — another service-level helper that runs the balance comparison logic and decides which tasks actually need to be reopened. Decision logic stays in the service; writes go through the data layer.

No raw Prisma calls visible — the service layer is clean of database syntax. That boundary is what makes each layer independently testable and replaceable.
