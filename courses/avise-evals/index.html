The Problem: AI Is Non-Deterministic

Unlike regular code — where the same input always produces the same output — AI is non-deterministic. Every time you call an LLM, you might get a slightly different response. So how do you check that the AI is doing its job correctly — at scale, across all edge cases, every time you change the code?

💡
The Core Insight

You can't unit-test AI the way you test regular code. Instead you run many real interactions against the real AI and score the responses. That's exactly what the evals system does.

This is where Evalite and Avise's evals SDK come in.

What Is an Eval? Think: a Report Card

A school report card works like this: a student (the AI) is given a task, they do their work, and a teacher (the scorer) grades the result. The grade is a number — 0 for fail, 1 for pass, or something in between for partial credit.

1
Give the AI a prompt

A natural-language instruction like "Show me journal entry #42" or "Create a 12-month amortization schedule for $12,000."

2
The AI responds

The real AI agent runs, calls its tools, and produces a response — just like a real user interaction.

3
Scorers grade the response

The response is checked against a list of expectations — did it mention the right account names? Did it produce the right artifact? Each check returns a score from 0 to 1.

4
Results are recorded

Evalite stores the scores and metadata so you can review them in a dashboard and track improvement over time.

02

Setting the Stage

Before you can grade the AI, you need real test data. Here is how the eval context sets the scene.

Why Use Real Data?

Most software tests use fake, hand-crafted data: "pretend the account name is 'Cash', the amount is $1,000." That works for regular code. But AI is different — the agent's job is to look up real records in a real database and talk about them. If you use fake data, you are testing a scenario that never exists in production.

Instead, the evals system does something clever: it connects to the actual database and picks random real journal entries to use in each test. The AI then has to find and describe those real entries. This makes the tests much more meaningful.

💡
Testing with Production-Like Data

Using real data from the database means the evals catch real problems — accounts with unusual names, entries with missing fields, edge cases that hand-crafted test data would never include.

The Stage Manager: EvalsContext

Think of EvalsContext like a stage manager in a theater — it sets everything up before the performance. It connects to the database, holds the companyId and userId that the AI will run as, and provides methods for loading test data.

CODE 

class EvalsContext {
  public companyId!: string;
  public userId!: string;
  public evalEntries: Map<string, EvalJournalEntry[]>
    = new Map();

  public constructor() {
    const { companyId, userId }
      = getEvalsEnvironment();
    this.companyId = companyId;
    this.userId = userId;
  }
}
PLAIN ENGLISH

Define a class (a reusable blueprint) called EvalsContext.

It will store a companyId — which company the eval runs for.

It will store a userId — which user the AI acts as.

It also holds a Map (like a dictionary) to remember journal entries it has already loaded.

When created, it reads the companyId and userId from environment variables.

This is the same companyId/userId the AI agent uses in production — so the eval environment mirrors real usage exactly.

Picking a Random Real Journal Entry

Instead of hard-coding a specific journal entry, EvalsContext can randomly select one from the database — filtered by type, date range, status, or other criteria. This means every eval run tests a different real entry, increasing coverage over time.

CODE 

const context = new EvalsContext();

const billEntry =
  await context.addRandomEvalEntry({
    entryType: [
      JournalEntry.Data.KnownEntryType.Bill
    ],
  });
PLAIN ENGLISH

Create a new EvalsContext — our stage manager is now active.

Ask the context to pick a random journal entry from the database...

...but only entries of type "Bill" (as opposed to invoices, expenses, etc.).

The result is an EvalJournalEntry object that wraps the real data and adds helpful methods.

Every time this eval runs, it picks a different bill — so the test suite covers many different real scenarios over time.

The Test Fixture: EvalJournalEntry

Once a journal entry is loaded, it is wrapped in an EvalJournalEntry object. This is a wrapper that adds one key feature: lazy loading of account data.

Journal lines store an accountId (a database ID), not the actual account name. To show the account name in a test, you need to look it up. EvalJournalEntry does this automatically, but only when you actually ask for it — saving time when the data is not needed.

🏦
journalEntry

The raw journal entry from the database — date, amounts, status, type, linked bills

📒
lineData

Each journal line with its accountId — the account object itself is loaded only when needed (lazy)

⚡
getLineDataWithAccount()

Call this to get all lines with their full Account objects — triggers a database lookup on first call, then caches

The Memory Trick: AccountCache

Evals often test many journal entries in one run. Each entry might share the same accounts (e.g., "Cash" appears in dozens of entries). Without caching, the system would hit the database for the same account hundreds of times.

AccountCache is a simple static class that acts as a shared memory: the first time an account is needed, it is fetched and stored. Every subsequent request for the same account ID returns the stored version instantly.

ℹ️
Why Static?

The cache is static (shared across all instances) because account data does not change between evals. All journal entries for the same company use the same account definitions — so one cache serves all eval tests in a run.

03

Grading the AI

Criteria are the individual checks that score one specific thing about the AI's response.

The Grader: What Is a Criterion?

Imagine a checklist a film critic uses after seeing a movie: "Did it have a compelling plot? Were the performances strong? Was the pacing good?" Each item on the list is checked independently and gets its own score. Together they form a picture of quality.

In the evals system, each check on the list is called a Criterion (or a Metric). Each one checks exactly one thing and returns a score from 0 to 1. They are combined to build a full picture of the AI's response quality.

ℹ️
The Score Contract

Every criterion must return a number between 0 and 1 (inclusive). 1 = fully passed. 0 = fully failed. Values in between represent partial success. This consistency is what allows scores to be averaged, combined, and compared.

Check #1: Did the AI Say the Right Thing?

The most common check is StringMatch — it looks at the AI's final text response and asks: does it contain (or start with, or exactly equal) a specific string?

CODE 

new StringMatch(
  "Acme Corp",
  {
    type: "contains",
    caseInsensitive: true,
  }
)
PLAIN ENGLISH

Create a new StringMatch check that looks for a specific vendor name.

We are looking for "Acme Corp" somewhere inside the AI response...

...using a "contains" match (not an exact match of the whole response).

Case-insensitive means "acme corp", "ACME CORP", and "Acme Corp" all count as a match.

Result: 1 if the response contains "Acme Corp", 0 if it does not.

exact The full response must equal the expected string exactly
contains The expected string must appear somewhere in the response (most common)
starts-with The response must begin with the expected string
ends-with The response must end with the expected string

Check #2: Did the AI Produce the Right Output?

Sometimes the AI does more than respond in text — it produces a structured artifact. For example, when you ask it to create a monthly schedule, it produces a propose_schedule artifact with all the schedule parameters (dates, accounts, amounts) ready for the system to use.

ArtifactsExist checks that the AI created exactly the right artifact types — no more, no less.

CODE 

new ArtifactsExist([
  "propose_schedule"
])
PLAIN ENGLISH

Check that the AI created exactly one artifact of type "propose_schedule".

Score 1 if the propose_schedule artifact exists AND no unexpected artifacts were created.

Score 0 if the artifact is missing, or if the AI also created other unexpected artifacts.

This catches cases where the AI creates an artifact when it should not, or fails to create one when it should.

Check #3: Are the Artifact's Values Correct?

Knowing an artifact exists is not enough. You also need to verify its contents. ArtifactPropertyMatch uses JSONPath expressions to extract specific fields from the artifact and compare them to expected values.

CODE 

new ArtifactPropertyMatch(
  "propose_schedule",
  {
    "$.termStart": "2025-01-01",
    "$.termEnd":   "2025-12-31",
    "$.totalAmount": 12000,
  }
)
PLAIN ENGLISH

Look at the "propose_schedule" artifact the AI created.

Check that its termStart field is exactly "2025-01-01" (the schedule must start January 1st).

Check that its termEnd field is exactly "2025-12-31" (must end December 31st).

Check that totalAmount is exactly 12000 dollars.

Score 1 only if ALL three properties match. Score 0 if any one is wrong.

Checks #4 & #5: Did the AI Use the Right Tools?

The AI agent uses tools to do its work (look up data, create schedules, etc.). Two more criteria check the tooling behavior:

🔧
ToolCallsExist

Verifies the AI called specific tools. e.g., it MUST call both findAccounts AND proposeSchedule — if it skips one, score is 0.

🔬
ValidateArtifact

Runs a custom JavaScript function against the artifact data. Use this for complex checks that cannot be expressed as a simple property match (e.g., verifying debits equal credits within 0.01).

🆔
Arbitrary (shouldNotContainLowLevelIds)

A fully custom criterion — scans the AI response for UUIDs or CUIDs and returns 0 if any are found. The AI should never expose raw database IDs to users.

04

Combining the Grades

Individual criteria are powerful, but combining them is what makes an eval really useful.

Mixing Criteria: The Composer Pattern

Think of criteria like individual instrument tracks on a recording studio mixing board. Each track captures one thing (bass, drums, vocals). But the song is the mix — how all the tracks combine into a final result.

In the evals system, metric composers are what mix individual criteria together into a final score. There are four of them, each with a different mixing strategy.

🔗

And

ALL criteria must pass. If any one fails, the whole score is 0. No partial credit — like a lock that needs every key.

🔀

Or

At least ONE criterion must pass. Returns the maximum score across all criteria. Like a backup plan — any one success is enough.

📊

AverageScores

Returns the average across all criteria. Allows partial credit — if 3 of 4 account names are mentioned, the score is 0.75, not 0.

🔀

Predicate

Only evaluate Metric B IF Metric A passes. Like a conditional: "check whether the AI called the right tool first, THEN check whether the response was good."

And: All or Nothing

And is the strictest composer. It takes a list of criteria and requires every single one to pass. If any criterion returns 0, the entire And block scores 0. Use it when the criteria are all non-negotiable.

CODE 

new And<string>([
  new ToolCallsExist([
    "findAccounts",
    "proposeSchedule",
  ]),
  new ArtifactsExist([
    "propose_schedule"
  ]),
])
PLAIN ENGLISH

Create an And check that requires ALL of the following to be true:

1) The AI must have called both findAccounts AND proposeSchedule tools.

2) The AI must have created a propose_schedule artifact.

If the AI skipped findAccounts (looking up account IDs by name), the whole thing fails — even if it created a perfect schedule artifact with wrong account IDs.

Predicate: "First Check This, Then That"

Predicate is the most sophisticated composer. It says: "I only want to evaluate the quality of the response IF a prerequisite check passes first."

Why? Because if the AI did not even call the right tool, then the response cannot be correct — and checking its details would just produce misleading noise.

CODE 

new Predicate(
  // Gate: only proceed if this passes
  mustCallFindJeAndNotHaveIds,
  // Metric: evaluate THIS if gate passed
  new AverageScores([
    shouldHaveDisplayId(evalEntry),
    shouldHaveStatus(evalEntry),
    shouldHaveTransactionDate(evalEntry),
  ]),
)
PLAIN ENGLISH

Create a conditional check with a gate and a payload.

Gate: first verify the AI called findJournalEntries with the right ID, AND that it has no raw database IDs in the response.

If the gate fails: skip evaluating the response details entirely. Score 0.

If the gate passes: now evaluate the response quality in depth.

Check whether the response mentions the display ID, the status, and the transaction date.

Average those three scores to get a final 0-1 quality score for the response details.

Let us trace through a real eval from proposeScheduleScenarios/proposeSchedule.eval.ts. The goal: verify the AI can propose a 12-month amortization schedule with the correct accounts, dates, and total.

When Composers Disagree

Watch how the different composers handle the same situation — the AI got the accounts right but missed one of the tool calls.

A
And Composer

I require all checks to pass. The AI found the right accounts and created the schedule artifact. But it did NOT call findAccounts first. My score: 0. Full stop.

AV
AverageScores

I give partial credit. 3 of my 4 criteria passed: account IDs are right, dates are right, amounts are right. Only the tool call is missing. My score: 0.75.

P
Predicate

My gate criterion failed (wrong tool call). So I will not even evaluate the response quality. Evaluating the schedule content would be misleading — maybe it hardcoded the account IDs instead of looking them up. Score: 0, gate blocked.

O
Or Composer

I only need ONE criterion to pass. The schedule artifact check passed. My score: 1. (I am best for lenient checks where any acceptable approach is fine.)

A
And Composer

For a schedule eval, I am the right choice. The tool call matters because without findAccounts, the AI might have guessed the account IDs. We need to be strict here.

The Runner: Evalite

Evalite is the engine that powers everything. It integrates with Vitest and provides a local UI to browse results during development. When you run pnpm evals:watch, it re-runs evals whenever files change — like a live coding environment, but for AI quality.

CODE 

// evalite.config.ts
import { defineConfig }
  from "evalite";

export default defineConfig({
  include: [
    "evals/**/*.eval.ts"
  ],
});
PLAIN ENGLISH

This is the configuration file that tells Evalite where to find eval files.

It looks for all files matching the pattern "*.eval.ts" inside the evals/ folder.

Every file with that suffix is an eval file — Evalite will discover and run it automatically.

The naming convention *.eval.ts makes eval files easy to identify at a glance.

Sharing Results: Export to S3

Evalite stores results in a local SQLite database file (evalite.db). But that file lives on your laptop — nobody else can see it. The export script solves this.

Running pnpm evals automatically calls scripts/exportEvaliteToS3.ts after the evals complete. This script reads the evalite output, packages it as a static HTML bundle, and uploads it to S3 under a timestamped folder.

⏱️
Timestamped folders

Each run is stored as a separate folder in S3: 2025-05-14T10:30:00Z/. This preserves the full history so you can compare runs over time.

📦
Static HTML bundle

Evalite exports its UI as a self-contained HTML app. The export script uploads this bundle to S3 so the viewer can serve it inside an iframe.

🔐
AWS IAM authentication

The script uses the AWS SDK with IAM credentials. Only developers with the right AWS permissions can upload new results — keeping the history trustworthy.

Reading Runs from S3

The listRuns() function in services/s3.ts is what populates the sidebar. It asks S3 to list all top-level "prefixes" — each one is a timestamped folder representing one eval run.

CODE 

async function listRuns(): Promise<string[]> {
  const response = await Aws.s3.send(
    new ListObjectsV2Command({
      Bucket: config.evals.s3Bucket,
      Delimiter: "/",
    })
  );

  const runs = response.CommonPrefixes
    ?.map(p => p.Prefix.replace(/\/$/, ""))
    ?? [];

  return runs.sort().reverse();
}
PLAIN ENGLISH

Define an async function that returns a list of run IDs from S3.

Ask S3 to list all objects in the evals bucket, but use "/" as a delimiter — this groups objects by folder instead of listing every file.

S3 returns "CommonPrefixes" — each one is a folder name (e.g. "2025-05-14T10:30:00Z/").

Strip the trailing "/" from each folder name to get the clean run ID.

Sort in reverse order so the most recent runs appear first in the sidebar.

The Clever Iframe Trick

The evalite UI is already a polished, self-contained web app. Rather than rebuilding it from scratch, avise-evals-viewer simply loads it inside an iframe. The assets route on the server proxies files from S3 to the browser, so the iframe can load the full evalite UI as if it were a local page.

💡
Proxy = No CORS Problems

The browser cannot fetch files from S3 directly due to CORS security restrictions. The Next.js server acts as a middleman: it fetches from S3 server-side and forwards the response to the browser. This pattern — server-side proxying — is a common solution for securely loading content from external storage.
