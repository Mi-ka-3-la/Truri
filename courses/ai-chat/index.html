The Architecture

Seven components. Three LLM providers. A dynamic tool registry. An artifact engine. Here is how it all connects.

The full system map

Every user message travels through this graph. Knowing which node owns which concern means you can add a tool, swap a provider, or debug any broken response by looking at exactly one place.

graph TD
  A["React Frontend\nAIChat.tsx + AiChatItem/"] --> B["Express Controller\naiController.ts"]
  B --> C["Conversation Loop\nai/index.ts"]
  C --> D["Provider Abstraction\nbaseProvider.ts"]
  D --> E1["OpenAI\nopenAiProvider.ts"]
  D --> E2["OpenRouter\nopenRouterProvider.ts"]
  C --> F["Tool Registry\nregistry.ts"]
  F --> G["20+ Built-in Tools\nai/tools/"]
  F --> H["MCP Tools\nmcpServerAdapter.ts"]
  C --> I["Artifact Engine\nai/artifacts/"]
  C --> J["Conversation DB\nai/data/conversations.ts"]

The tech stack, layer by layer

React Frontend (avise-web)

TypeScript + React. The AIChat component family lives in src/components/AIChat/. Uses TanStack Query mutations for sending messages. Artifact cards live in AiChatItem/artifacts/ — each artifact type (journalEntry, schedule, accounts, table) has its own renderer and action handler.

Express Controller (avise-api)

aiController.ts is the single entry point. It parses multipart form data for file uploads, validates the request, and calls createOrContinueConversation(). Route: POST /v1/companies/:companyId/ai/chat.

Conversation Loop (ai/index.ts)

The engine. An iterative for loop runs up to MAX_TOOL_CALLS + 100 iterations. Each iteration sends messages to the LLM, processes tool calls, saves to the database, and either loops again or terminates.

LLM Provider Abstraction (providers/)

BaseAiProvider defines the interface: sendMessageToProvider(), uploadFile(), generateEmbedding(). Three concrete implementations: OpenAI (default), OpenRouter (multi-model), OpenAI-Compatible (custom endpoints). Provider selected per-request via validated overrides.

PostgreSQL + Conversation Storage

Conversations and messages persisted via ai/data/conversations.ts. Artifacts in ai/data/artifacts.ts. File uploads to S3; metadata to the file library. Context is cleaned of S3 details and file content before each database write.

Provider selection is per-request, not per-server

An overrides object in the request body can switch the model or provider for a single conversation. sanitizeOverrides() validates these before use — only allowlisted models are accepted. This scopes the change to one request only.

How MCP tools get registered at startup

The 20+ Tools

Every tool the AI can call — what it does, which group it belongs to, and the stub pattern that keeps token costs low.

The stub pattern: only load what you need

Sending every tool’s full parameter schema on every request wastes thousands of tokens. Avise uses a two-stage stub pattern:

1
First call — compact stubs

The LLM gets one-line descriptions of each tool. It uses these to decide which tool it needs — low cost, fast.

2
Stub detected — registry swap

When the loop detects a stub tool call, it replaces the stub with the full implementation. Messages are NOT saved yet — the iteration is discarded.

3
Second call — full tool

The AI now sees the complete parameter schema and calls the tool correctly. This response IS saved to the database.

4
Tool executes — result returned

The executor runs, queries the database, and returns structured JSON. The LLM receives this as a tool result and formulates its answer.

Stubs save tokens on tools never called

proposeJournalEntry has 20+ parameter fields. Loading all of them for every request — even when the user is just asking a question — would waste thousands of tokens. Stubs compress this to ~10 tokens until the AI explicitly commits to that tool.

Group 1 — Data lookup (read-only)

findAccountsSearch the chart of accounts by name, classification, ID, or number. Stub tool.
findJournalEntriesSearch journal entries by displayId list, date range, status (Posted/Scheduled/Quarantined). Stub tool.
findPeriodsFind accounting periods by name (e.g. “May 2025”), date range, or UUID. Critical for resolving user mentions of specific months.
findTasksFind close tasks by period, type (flux/reconciliation/account), status, assignee, or reviewer. Stub tool.
findUsersList all company users with id, email, fullName, status. Used when filtering or attributing tasks.
findDimensionsFromValueFull-text search across dimension values. Find which dimension (Vendor, Class, etc.) contains a specific value.
listValuesForDimensionGet all possible values for a named dimension. Used before proposing entries that need dimension tags.
jeVersionsGet the full version history of a journal entry by displayId — shows all edits and who made them.
getTaskFetch full details of a single task by UUID — including events, comments, and status timeline.

Group 2 — Reports & Search

balanceSheetReportGenerate a Balance Sheet for a date range. Returns CSV-flattened account hierarchy. Supports comparison periods and dimension breakdown.
incomeStatementReportGenerate an Income Statement. Same parameters as balance sheet — compareTo, showBy, dimension pivot, account filters.
generalLedgerReportFull GL activity for one account over a date range. Paginated, dimension-filterable. Returns entries as CSV rows with balances.
fullTextSearchFull-text search across journal lines, bills, accrual numbers, customers, and messages. Min 2 chars, max 50 results.
searchDocumentsSemantic vector search (TurboPuffer) across chunked document content in the company’s file library. Used for RAG over uploaded files.
searchFileLibrarySearch the file library by name, date, content type, period, or linked entity. Returns metadata — use readFile to get content.
readFileRead the content of a specific file from the library by UUID. Handles both content-extracted text and provider-uploaded binary files.
retrieveDocumentContentRetrieve previously chunked document content by document ID. Companion to searchDocuments.
11 Avise Docs tools — conditionally registered

Tools like aiAsk, searchSpace, pageByPath connect to the Avise documentation system. They are only registered when a personal access token is configured in the environment. They enable the AI to answer questions about how Avise works as a product — separate from a company’s financial data.

Group 3 — Action tools (propose & display)

proposeJournalEntryDraft a new journal entry as an interactive artifact. Validates accounts, dimensions, balance. Creates an editable card the user can post. Stub tool.
proposeScheduleDraft a simple (single debit/credit) prepared schedule as an artifact. Calculates all monthly entries from totalAmount, termStart, termEnd. Stub tool.
proposeMultiLineScheduleDraft a multi-line schedule where each entry can have multiple debits and credits. Supports complex allocations. Stub + Feature-flagged: only available when ai-complex-schedules flag is ON.
suggestAccountsPropose new chart-of-accounts entries as an editable table artifact. Only works for Avise-platform companies. Stub tool.
displayArtifactTableRender structured data as an interactive, formatted table artifact. Columns typed as markdown, number, date, or currency. Mandatory instead of Markdown tables.

04

The Chat Loop

The iterative engine that drives every response — file processing, stub replacement, tool execution, artifact tracking, and conversation persistence.

The loop in one picture

Every message goes through createOrContinueConversation() in ai/index.ts. It runs a for loop up to MAX_ITERATIONS times. Here is the decision tree inside each iteration:

flowchart TD
  A["New message arrives"] --> B["Process file uploads\n(extract content or upload to provider)"]
  B --> C["Build ToolRegistry\n(20+ built-in + MCP tools)"]
  C --> D["Send messages + system prompt\nto LLM provider"]
  D --> E{Any tool calls?}
  E -- No --> F["Return final response\nto user"]
  E -- Yes --> G{Any stub tools?}
  G -- Yes --> H["Replace stubs with\nfull implementations\nDo NOT save messages"]
  H --> D
  G -- No --> I["Execute all tools\nin sequence"]
  I --> J["Save messages + tool\nresults to database"]
  J --> K{toolCallCount < MAX?}
  K -- Yes --> D
  K -- No --> L["Force final response\n(no more tools allowed)"]
MAX_TOOL_CALLS is the safety valve

The config sets a maximum number of tool calls per user message. Once hit, the tool registry is no longer passed to the LLM — forcing the next response to be text-only. This prevents runaway loops from burning through API budget.

File uploads — two very different paths

Before the first LLM call, processFilesForContext() handles any attached files. The handling depends on the file type:

PROVIDER path — images & PDFs

The file bytes are uploaded directly to the LLM provider (OpenAI Files API). The provider returns a providerFileId. On every subsequent turn, this ID is passed alongside the messages so the LLM can "see" the file natively.

PNG JPG PDF

CONTENT path — Excel, CSV, Word, text

The file bytes are read and converted to plain text content. This extracted text is injected into the conversation context as a string. No external upload — the content lives in the message itself.

XLSX CSV DOCX TXT
All files are also saved to the Avise file library

Before processing, every uploaded file gets a row in the files table via files.create(). The aviseFileId is stored on the message context. On subsequent turns, the loop can re-fetch from S3 if the content was not stored on the message (re-hydration).

The artifact lifecycle

Artifacts are the interactive cards rendered in the chat — proposed journal entries, tables, schedules. Here is how they are born, stored, and acted on:

1
Tool creates the artifact

When proposeJournalEntry runs, it calls createArtifact(). This writes a row to the artifacts table with type: "journalEntry", a data JSON blob, and a status: "pending". The tool returns the artifact ID to the LLM.

2
LLM references the artifact in its response

attachArtifactReferences() scans the LLM's text response for artifact IDs and replaces them with structured references the frontend knows how to render.

3
Frontend renders the artifact card

Each artifact type has its own React component in AiChatItem/artifacts/. The journalEntry card shows debit/credit lines with edit controls. The table card shows sortable columns. The schedule card shows the full monthly entry preview.

4
User acts — artifact action mutation fires

When the user clicks "Post to GL", the frontend calls useArtifactActionsMutation which hits the artifact actions endpoint. The backend validates and executes the real action (create JE, create schedule, etc.) and updates the artifact status.

Code-walk: the core loop iteration

This is the most important function in the entire AI system — the innermost logic of createOrContinueConversation() in ai/index.ts:

avise-api/src/ai/index.ts — the chat loop (simplified)
1
for (let i = 0; i < MAX_ITERATIONS; i++) {
  const assistantMessage =
    await sendConversationMessagesToProvider({
      systemPrompt: chatSystemPrompt(overrides.systemPrompt),
      inputMessages: [...conversation.messages, ...nextInputMessages],
      toolRegistry: toolCallCount < MAX_TOOL_CALLS
        ? toolRegistry : undefined,
    });

Each iteration sends the full conversation history plus any new messages to the LLM. The tool registry is included UNLESS we have already hit MAX_TOOL_CALLS — at that point we pass undefined, which forces the LLM to respond in text only. This is what stops infinite tool loops.

2
  if (toolRegistry.areAnyToolsStub(toolCalls)) {
    toolRegistry = toolRegistry
      .getNewRegistryWithStubToolsReplaced(toolCalls);
    continue; // Re-run — do NOT save messages
  }

Stub detection. If any of the requested tool calls are stubs, we swap the registry and loop again WITHOUT saving anything to the database. The user never sees this iteration — it is internal bookkeeping.

3
  conversation.messages.push(
    ...nextInputMessages, assistantMessage
  );
  await asyncMapSequential(
    nextInputMessages,
    (message) =>
      conversationData.createMessage(message)
  );

Now that we know there are no stub tools, we commit the messages to the database. Messages are saved sequentially (not in parallel) to preserve ordering. The context is cleaned of S3 metadata before writing.

4
  if (toolCalls.length === 0) {
    return { /* final response */ };
  }
  nextInputMessages = [
    assistantMessage,
    ...await executeToolCalls(toolCalls),
  ];
}

If there are no tool calls in the response, the conversation is done — return the answer. Otherwise, execute all tools, collect their results, and set them as the next input so the LLM can see what the tools returned.

Rules & Guardrails

The system prompt is the AI’s constitution — it defines what it can talk about, how it must format responses, which links it can generate, and what happens when users try to probe its internals.

The system prompt in plain English

Every conversation starts with a system prompt built by chatSystemPrompt() in ai/prompts.ts. Here is what it says, rule by rule:

Topic restriction Only accounting and finance. Programming, politics, entertainment, art, music, humor, creative writing — all off-limits. Politely declined.
GAAP compliance All answers must follow Generally Accepted Accounting Principles. The AI represents itself as an accounting expert — it must behave like one.
No Markdown tables The AI MUST use displayArtifactTable instead. No exceptions. Markdown tables render poorly in the chat UI and bypass the artifact system.
Max tool calls The prompt tells the AI its tool call budget: “You are limited to a maximum of N function calls per user request.” Once hit, no more tools are passed.
Period resolution rule When the user explicitly mentions a period, ALWAYS call findPeriods. Do NOT use the period ID from the page URL context. Explicit user request > page context.
Internals privacy If a user asks about training data, capabilities, knowledge cutoff, or tool technical details — politely decline to answer.
Internal reasoning pattern The AI internally follows THOUGHT → ACTION → OBSERVATION → VERIFICATION. But these labels must never appear in responses to users.

Linking rules — four supported paths only

The system prompt specifies EXACTLY which links the AI may generate. Generating any other URL is forbidden. The four allowed paths:

1
Journal Entry: /AVISECOMPANY/journal-entry/:displayId

Use the numeric displayId, NOT the internal UUID. Must be included whenever referencing a specific journal entry.

2
General Ledger: /AVISECOMPANY/reports/general-ledger?...

Required whenever mentioning an account balance, even in passing. The accountId param must use the UUID, not the account name.

3
Balance Sheet: /AVISECOMPANY/reports/balance-sheet?...

Optional params: hideNoActivity, showBy, compareTo, comparisonMethods. Only with actual date parameters — never a bare link.

4
Income Statement: /AVISECOMPANY/reports/income-statement?...

Same params as balance sheet. The AI must use AVISECOMPANY as a placeholder in the path — the frontend resolves it to the real company ID.

Making up URLs is forbidden

The system prompt explicitly lists forbidden patterns: vague anchors (“see more”, “click here”), settings pages, admin pages, user profiles, and any URL not on the four-path allowlist. If the AI cannot link to something, it describes it in text.

How context is injected per message

Every user message is wrapped by formatUserMessageWithContext() in baseProvider.ts before being sent to the LLM:

avise-api/src/ai/providers/baseProvider.ts — formatUserMessageWithContext()
1
return `<user_message>
${userMessage}
</user_message>

The actual text the user typed. Wrapped in XML tags so the LLM can cleanly separate it from the injected context below.

2
<current_date>
  ${getCurrentSystemJsDateTime().toISOString()}
</current_date>

Current timestamp. Critical for the AI to correctly interpret “this month”, “last quarter”, “yesterday” — without it the LLM has no sense of when “now” is.

3
<request_context>
  ${JSON.stringify(context || "")}
</request_context>`

A JSON blob containing page context — the current URL (which may include a periodId), and any other context the frontend sent. The system prompt instructs the AI to use the pageUrl only as a fallback for period detection.

06

Gaps & Architectural Improvements

An honest assessment of what the current architecture lacks — and concrete proposals to fix each gap.

Six architectural gaps

No streaming The final LLM response is returned in one batch. Users see nothing until the full answer is ready — no character-by-character typewriter effect.
No provider failover If OpenAI goes down, all requests fail. The multi-provider setup only activates via explicit override — there is no automatic fallback chain.
No context compression Long conversations send ALL messages to the LLM every turn. As conversations grow, cost and latency grow linearly — and eventually the context window overflows.
Stub pattern is fragile The stub → full tool swap requires a full extra LLM round-trip. If the AI picks a stub tool and the system re-runs, that is 2x LLM calls plus double the latency just to select a tool.
No cross-conversation memory Every conversation starts fresh. The AI has no knowledge of frequently-asked accounts, user preferences, or past corrections. Users repeat context every session.
No tool result caching If the AI calls generalLedgerReport with the same args twice in one conversation, the query runs twice. Expensive queries (large GL history) have no in-session cache.

Proposed improvements

1. Stream the final response

What: Use the OpenAI streaming API to emit tokens as they are generated.
Where: Replace sendConversationMessagesToProvider() with a streaming variant. The controller sends a text/event-stream SSE response. The frontend appends tokens in real time.
Impact: Perceived latency drops dramatically — users see the AI "thinking" rather than waiting in silence.

2. Automatic provider failover

What: Try OpenAI → if unavailable, retry on OpenRouter → if unavailable, queue or return a graceful error.
Where: Wrap resolveProviderAndModel() with a retry chain. Each provider implements a health check. The loop picks the first healthy provider.
Impact: AI Chat stays up when OpenAI has an outage — critical for production reliability.

3. Conversation summarization

What: When a conversation exceeds N messages, summarize older turns into a compact “context block” and drop the raw history.
Where: Add a summarizeOldMessages() function called before building the input message list. Store the summary in the conversation row.
Impact: Context window never overflows. Cost per turn stays bounded regardless of conversation length.

4. Replace stub pattern with intent classification

What: Before the main loop, run a cheap classifier call to predict which tools the user request needs. Load only those full tools from the start.
Where: Add a classifyIntent() step in createOrContinueConversation(). The classifier maps user intent to a tool subset. Use a small, fast model for this step.
Impact: Eliminates the extra round-trip. One LLM call instead of two for tool selection.

5. Cross-conversation memory layer

What: Store per-user preferences (frequently used accounts, preferred time ranges, past corrections) in a persistent memory store. Inject relevant memories into the system prompt.
Where: New ai/memory/ module. Write memories after each conversation turn. Read them at the start of each new conversation.
Impact: The AI gets smarter per user over time. Users stop repeating themselves.

6. In-session tool result cache

What: Cache tool results by (toolName, args hash) within a single conversation. On a cache hit, return the stored result without re-querying.
Where: Wrap tool execution in registry.ts with a Map keyed by args hash. Clear on conversation end.
Impact: Repeated queries (e.g. AI re-fetches accounts multiple times) no longer hit the database each time. Significant cost reduction for complex multi-tool conversations.

Priority matrix

P0 Streaming responses — biggest UX impact, relatively contained change. Add to OpenAI provider + SSE controller endpoint.
P0 Provider failover — production reliability. OpenAI outages currently take AI Chat completely down.
P1 Context compression — required before heavy enterprise usage. Long conversation cost is unbounded today.
P1 Intent classification / stub replacement — cuts latency and cost per turn. Medium complexity.
P2 Tool result cache — quick win for complex conversations. Low risk, session-scoped.
P3 Cross-conversation memory — high value long term but requires new infrastructure and privacy design.
