06

Gaps & Architectural Improvements

An honest assessment of what the current architecture lacks — and concrete proposals to fix each gap.

Six architectural gaps

No streaming The final LLM response is returned in one batch. Users see nothing until the full answer is ready — no character-by-character typewriter effect.
No provider failover If OpenAI goes down, all requests fail. The multi-provider setup only activates via explicit override — there is no automatic fallback chain.
No context compression Long conversations send ALL messages to the LLM every turn. As conversations grow, cost and latency grow linearly — and eventually the context window overflows.
Stub pattern is fragile The stub → full tool swap requires a full extra LLM round-trip. If the AI picks a stub tool and the system re-runs, that is 2x LLM calls plus double the latency just to select a tool.
No cross-conversation memory Every conversation starts fresh. The AI has no knowledge of frequently-asked accounts, user preferences, or past corrections. Users repeat context every session.
No tool result caching If the AI calls generalLedgerReport with the same args twice in one conversation, the query runs twice. Expensive queries (large GL history) have no in-session cache.

Proposed improvements

1. Stream the final response

What: Use the OpenAI streaming API to emit tokens as they are generated.
Where: Replace sendConversationMessagesToProvider() with a streaming variant. The controller sends a text/event-stream SSE response. The frontend appends tokens in real time.
Impact: Perceived latency drops dramatically — users see the AI "thinking" rather than waiting in silence.

2. Automatic provider failover

What: Try OpenAI → if unavailable, retry on OpenRouter → if unavailable, queue or return a graceful error.
Where: Wrap resolveProviderAndModel() with a retry chain. Each provider implements a health check. The loop picks the first healthy provider.
Impact: AI Chat stays up when OpenAI has an outage — critical for production reliability.

3. Conversation summarization

What: When a conversation exceeds N messages, summarize older turns into a compact “context block” and drop the raw history.
Where: Add a summarizeOldMessages() function called before building the input message list. Store the summary in the conversation row.
Impact: Context window never overflows. Cost per turn stays bounded regardless of conversation length.

4. Replace stub pattern with intent classification

What: Before the main loop, run a cheap classifier call to predict which tools the user request needs. Load only those full tools from the start.
Where: Add a classifyIntent() step in createOrContinueConversation(). The classifier maps user intent to a tool subset. Use a small, fast model for this step.
Impact: Eliminates the extra round-trip. One LLM call instead of two for tool selection.

5. Cross-conversation memory layer

What: Store per-user preferences (frequently used accounts, preferred time ranges, past corrections) in a persistent memory store. Inject relevant memories into the system prompt.
Where: New ai/memory/ module. Write memories after each conversation turn. Read them at the start of each new conversation.
Impact: The AI gets smarter per user over time. Users stop repeating themselves.

6. In-session tool result cache

What: Cache tool results by (toolName, args hash) within a single conversation. On a cache hit, return the stored result without re-querying.
Where: Wrap tool execution in registry.ts with a Map keyed by args hash. Clear on conversation end.
Impact: Repeated queries (e.g. AI re-fetches accounts multiple times) no longer hit the database each time. Significant cost reduction for complex multi-tool conversations.

Priority matrix

P0 Streaming responses — biggest UX impact, relatively contained change. Add to OpenAI provider + SSE controller endpoint.
P0 Provider failover — production reliability. OpenAI outages currently take AI Chat completely down.
P1 Context compression — required before heavy enterprise usage. Long conversation cost is unbounded today.
P1 Intent classification / stub replacement — cuts latency and cost per turn. Medium complexity.
P2 Tool result cache — quick win for complex conversations. Low risk, session-scoped.
P3 Cross-conversation memory — high value long term but requires new infrastructure and privacy design.
